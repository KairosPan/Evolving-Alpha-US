## ② THE DESIGN READING — what governs each connection, where enforcement sits

**a. Config-as-declaration is the backbone.** Every outbound connection is declared in `config.toml` (or environment settings, cloud-side) — MCP servers, plugins, marketplaces, projects, notify hooks. Declarations carry **references, not capabilities**: `bearer_token_env_var` and `--remote-auth-token-env` name env vars; plugin code lives in a hash-pinned cache; hooks require persisted trust (`--dangerously-bypass-hook-trust` to skip). This is structurally the same "declaration ≠ capability" move as our ConnectorEntry. [VERIFIED]

**b. Every declaration has an enable/consent gate.** Per-server `enabled` (live `computer-use` entry present but off), `required`, tool allow/deny lists, `default_tools_approval_mode`, per-plugin `enabled = true`, per-project `trust_level` (28 path-scoped entries in the live config, stored centrally in user config, not in the repo). Trust is **path-granular**, a dimension our model lacks. [VERIFIED — local config.toml]

**c. Enforcement sits at three different tiers depending on product:**
- **CLI: OS-mechanism enforcement.** Seatbelt/bubblewrap constrain writes and network; approvals interpose on escalation. But **read-side is open by design** — full env inheritance with secret-filtering off by default (source-verified on main). The CLI's boundary philosophy is explicitly "readable but can't leave": egress-off + approvals, not read denial.
- **Cloud: backend enforcement.** The strongest boundaries are held server-side where the agent can't reach them: App token in backend infra, secrets deleted before the agent exists (phase split as a **temporal** capability tier), egress proxy with domain+method allowlist, PR landing as a service-side gated action. Enforcement by topology, not policy files.
- **Prompt-tier enforcement exists but is thin:** `AGENTS.md` review guidelines, guardian reasoning. Codex does not rely on prompts for security anywhere that matters.

**d. Approvals are becoming machine-in-the-loop and granular.** The local config's `approvals_reviewer = "guardian_subagent"` + stable `guardian_approval` flag put an LLM subagent inside the approval loop; the schema replaced the simple ladder (`on-failure` gone) with a `granular` object (sandbox_approval / rules / mcp_elicitations / request_permissions / skill_approval); app-server pushes **per-destination network approvals** (host/protocol/port) with `accept | acceptForSession | decline | cancel`. Direction of travel: binary network on/off → declared, destination-scoped, approval-mediated egress. [VERIFIED locally + docs; network_proxy in 0.134.0 binary INFERRED-absent (flag false)]

**e. Inbound connections are auth-symmetric with outbound.** When Codex is the server, non-loopback listeners require capability-token/JWT auth, clients must self-identify (`initialize` clientInfo), and the one live agent→agent integration we can read (Claude Code plugin) narrows capability **at connection time** (read-only sandbox, no approval passthrough) rather than trusting the peer. [VERIFIED — code read]

**f. The two Codex products remain opposite poles** (frozen study's frame, still correct): CLI = credentials readable, egress guarded; Cloud = credentials topologically unreachable, egress proxied. The CLI is drifting toward the Cloud model (network_proxy, granular approvals, managed `requirements.toml`), not the reverse.

## ③ DELTA vs the frozen 2026-07-07 study (baseline commit `9365b08`)

**What the study got right — re-verified at source level:**
1. **CLI read-side failure mode stands, unchanged on current main.** `ShellEnvironmentPolicy::default()` still sets `ignore_default_excludes: true` (KEY/SECRET/TOKEN excludes skipped) and `exec_env_tests.rs::test_core_inherit_defaults_keep_sensitive_vars` still asserts secrets are preserved. The study's harshest CLI finding is confirmed, and local forensics show it worse in degree: beyond auth.json, a 755 MB logs sqlite, full session transcripts, and OAuth refresh tokens all sit same-UID-readable under `~/.codex` (0600 at best). [VERIFIED]
2. **Cloud phase-split model stands**, verbatim in current docs ("secrets are removed before the agent phase starts"), and the short-lived-file support quote the study cited **un-rechecked is now confirmed verbatim first-hand** (community thread 1263867). [VERIFIED]
3. The "token-in-remote-config is the warned-against path" judgment and the charter recommendations (§四) are untouched by anything found.

**What changed since the baseline (would be wrong to cite the study as "Codex's connection approach" without these):**
1. **Connection surface exploded.** Plugins + marketplaces (~24 enabled locally), app-server daemon with ws remote-control and JWT/capability-token auth, remote TUI attach, Chrome native-messaging hosts, mobile pairing + remote control, `codex cloud` subcommand, Copilot-auth option — essentially none covered by the study (fairly: it was credential-isolation-scoped).
2. **CLI is growing a Cloud-style egress proxy** — `features.network_proxy` with per-domain allow/deny, unix-socket permissions, MITM hooks (main schema; local flag present, off). The study framed proxying as Cloud-only; that line is now version-dependent.
3. **Approval model reshaped**: `on-failure` dropped from schema; `granular` object added; `approvals_reviewer = "guardian_subagent"` live locally — a machine co-reviewer absent from both the study and our charter's approval model.
4. **Linux sandbox mechanism changed**: docs now say bubblewrap (user namespaces) with bundled fallback, not the Landlock+seccomp story of the baseline (Landlock code remains in-tree).
5. **New governance layers**: `requirements.toml` managed config (`allow_managed_hooks_only`), per-project `trust_level`, keyring credential-store option, GitHub Action now fronts the key with a **Responses API proxy** + `drop-sudo` default — a mitigation of the exact CI pattern the study criticized.
6. **Docs host moved** (developers.openai.com → learn.chatgpt.com); the study's URLs are redirect-era; `llms-full.txt` at the old host is the best grep-able primary.

**The study's two evidence gaps (§五 1–2):**
- **Gap (a) "GitHub App token never enters the container": still INFERRED — confidence up, evidence class unchanged.** Nothing in the current corpus documents token location. Strengthening chain (each link VERIFIED): platform performs checkout before user code; pushes are App-permission-gated service actions; users needing **private dependencies must supply their own** GITHUB_TOKEN as a Secret (unnecessary if a platform git credential were reachable); agent-phase egress default-off. Keep the study's "很可能但无一手直证" framing.
- **Gap (b) setup→agent laundering via `~/.bashrc`: RESOLVED — against Codex, and worse.** The docs now **officially instruct** persisting env vars via `~/.bashrc` across the phase boundary; exhaustive grep of the corpus finds no scrub/sanitize of files, bashrc, or git config between phases; OpenAI Support's own private-deps workaround (`git config` with the token inside setup) writes credential material into container state. **New amplifier absent from the study:** the 12h container cache is **shared across all users of an environment** on Business/Enterprise — a laundered secret can persist into other users' task containers. [absence-of-scrub VERIFIED; cache amplification INFERRED from two verbatim statements]

## ④ BORROW/DIVERGE vs the alpha/Sonia-Kairos connector model

Our model (read first-hand): `ConnectorEntry` = pure DECLARATION (connector_id, `impl_ref` into operator registry, `env_keys` names-only, `instructions` as sole prompt-rendered field, `tier=T0_OBSERVE`, `enabled`, `scope`) — "editing an entry can never grant a capability" (`connectors.py:1-4`); tools register **only when** entry exists ∧ enabled ∧ all env keys present, else silently absent (`sonia_tools.py:131-135`); all Body changes land through the user-approved write-waist.

| Codex mechanism | alpha/Sonia-Kairos equivalent | Verdict | Why (one line) |
|---|---|---|---|
| MCP declaration in config.toml: `bearer_token_env_var` (env NAME, value out-of-band) | `env_keys` names-only in ConnectorEntry | **Adopt (already convergent)** | Independent convergence on the identical pattern — validates our design; cite `GITHUB_PAT_TOKEN` live example as calibration evidence. |
| Per-entry `enabled` gate; declared-but-disabled entries (`computer-use`, `enabled = false`) | `conn.enabled` in the registration gate | **Adopt (already convergent)** | Same declared-but-gated semantics; Codex lacks our env-presence half — ours is strictly stronger (registers only when creds resolvable). |
| Plugin marketplace: hash-pinned code cache, `~/.codex/plugins/cache/<mkt>/<plugin>/<ver>`, hooks need persisted trust | `impl_ref` into operator-registered `alpha.data.registry` | **Adapt** | Same "code comes from a registry, declarations only reference it" shape; borrow **hash/version pinning of impl_ref targets** when the registry grows; skip user-installable marketplaces (Kairos never self-extends). |
| Per-server tool allow/deny (`enabled_tools`/`disabled_tools`) + `default_tools_approval_mode` per server | `capabilities: list[str]` (descriptive today) + per-tool tier in ActivityPolicy | **Adapt** | Make `capabilities` an enforced allowlist at tool-registration time, and consider a per-connector approval posture field — cheap, matches our fail-closed ActivityPolicy. |
| Project `trust_level` (path-scoped, 28 entries, central user config, not in-repo) | No analog (our trust is per-connector/per-tier, not per-path) | **Adapt (charter question, not code)** | Trust stored **outside the trusted artifact** is the right invariant — our analog: connector trust lives in the operator registry, never in Body-editable text; path-granularity itself doesn't map to our single-workspace design. |

| CLI read-side default (full env inheritance, secrets unfiltered, filtering opt-in) | Read-side denial: creds resolved only inside registry-built sources; agent never handed raw env | **Avoid (cautionary baseline)** | The frozen study's verdict re-confirmed at source: "不可读胜过不可外泄" — our charter is stricter than the calibration reference here; keep it that way. |
