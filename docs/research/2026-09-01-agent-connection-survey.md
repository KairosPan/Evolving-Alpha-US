# 2026-09-01 — how the face may connect to local coding agents (Claude Code / Codex / Hermes)

Frozen research input, not a spec: a 5-agent survey (Claude Code surfaces, Codex surfaces, Hermes as the reference implementation, Anthropic's published terms) plus an adjudication of every method against Claude Code's terms. Read-only reconnaissance on the operator's machine (`--help`, source, official docs); no prompt was sent to any paid model. Where the public terms are silent the report says so rather than guessing. Consumer: `face/src/panels.ts` (the exec channel) and `face/README.md`.

## The one bright line

Driving the LOCAL, UNMODIFIED `claude` binary as a subprocess (execFile / `claude -p`) on the operator's own machine, under the operator's own account sign-in that Claude Code itself performs, is the SANCTIONED integration path — Anthropic explicitly documents "Run Claude Code programmatically" via `claude -p`, the Agent SDK, and CI, and explicitly does NOT prohibit "an end user ... signing in to the unmodified Claude Code binary with their own Claude subscription." Pro/Max advertised limits are stated to "assume ordinary, individual usage of Claude Code and the Agent SDK," and (as of the currently-live support article, after the June 15 2026 change was paused) `claude -p` and Agent SDK usage still draw from the subscription's usage limits. The BRIGHT-LINE PROHIBITION is credential extraction/intermediation: developers "may not collect, store, or intermediate Claude.ai credentials or session tokens," may not route requests through Free/Pro/Max credentials "on behalf of their users," and may not offer claude.ai login in their own apps — so scraping the OAuth token out of the Claude Code keychain/config and calling api.anthropic.com directly with it is a Consumer-Terms violation. For anything the face does programmatically FOR OTHER PEOPLE (a product/service, multi-tenant, reselling, preinstalling Claude Code into a distributed product), Anthropic requires API-key auth via Claude Console (each end user billed on their own key) and, for embedding Claude Code, Commercial Terms + an unmodified binary. The load-bearing distinction the task named is confirmed by primary sources: `claude -p` / Agent SDK under a subscription = OK; scrape-the-token-and-hit-the-raw-API = not OK.

  'Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users.' Developers building products/services 'should use API key authentication through Claude Console or a supported cloud provider.'  
  <https://code.claude.com/docs/en/legal-and-compliance>

  <https://code.claude.com/docs/en/agent-sdk/overview>
- **[medium] Preinstalling/running Claude Code inside a product or service you distribute (hosted sandboxes, agent infrastructure) — triggers Commercial Terms plus hard conditions: binary must be unmodified, you must not disable/restrict any built-in auth method, and you must not pay for/resell/intermediate Claude usage on end users' behalf**

### Subscription vs API

Anthropic draws an explicit product/credential boundary. Consumer Terms of Service govern Free/Pro/Max; Commercial Terms of Service govern Team, Enterprise, and Claude API (1P) as well as Bedrock/Vertex-Agent-Platform/Foundry (3P) (source: https://code.claude.com/docs/en/legal-and-compliance, License section). A subscription buys 'ordinary, individual' use of the native Anthropic apps (Claude.ai and Claude Code) — and that expressly includes running Claude Code and the Agent SDK programmatically via `claude -p` under the subscription; those calls currently still draw from the subscription's usage limits (support article 15036540; the June 15 2026 move to a separate metered 'Agent SDK credit' was announced then PAUSED and is still paused as of 2026-09-01). By contrast, if you are 'building products or services that interact with Claude's capabilities' — anything acting on behalf of other users, resold, or embedded/redistributed — Anthropic directs you to API-key authentication via Claude Console (or a cloud provider), billed to the key owner. So: subscription = personal/individual use of the unmodified Claude Code binary you signed in yourself (SANCTIONED for the face's local single-operator use); API key = the required credential the moment you productize, multi-tenant, resell, or intermediate. The Agent SDK's own license page states SDK use is governed by the Commercial Terms 'including when you use it to power products and services that you make available to your own customers and end users' (https://code.claude.com/docs/en/agent-sdk/overview).

### Credential reuse stance

Unambiguously prohibited. Anthropic's live 'Authentication and credential use' policy (https://code.claude.com/docs/en/legal-and-compliance) states OAuth auth 'is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications,' and that 'developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow.' It also forbids routing requests 'through Free, Pro, or Max plan credentials on behalf of their users.' Secondary reporting (The Register, VentureBeat, GitHub policy discussions) confirms this section was added ~Feb 19 2026 and that using OAuth tokens from consumer plans in third-party tools 'constitutes a violation of the Consumer Terms of Service'; enforcement (blocking third-party OAuth clients such as OpenClaw/OpenCode) began in early 2026. PRACTICAL RULE for the face: never read `~/.claude` / keychain OAuth tokens to call api.anthropic.com yourself. Instead spawn the UNMODIFIED `claude` binary as a subprocess and let Claude Code perform its own sign-in and its own API calls — the credential never leaves Anthropic's own client. That local-subprocess pattern is expressly carved out as permitted ('Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription'). If the face ever needs to make raw API calls itself or serve other users, use a proper ANTHROPIC_API_KEY (Console) or `--bare` mode with ANTHROPIC_API_KEY.

### Where the terms are silent

- The terms do not quantify 'ordinary, individual usage.' A face that fires heavy/continuous automated `claude -p` loops on a Pro/Max plan sits in a gray zone — permitted in kind, but volume could be judged abusive; Anthropic reserves enforcement without notice.
- The public terms don't crisply resolve the middle case: a PERSONAL local orchestrator (like the face at 127.0.0.1:3090) that spawns the unmodified binary purely for the single operator themselves. It reads as sanctioned 'ordinary use of the unmodified Claude Code binary with their own subscription' rather than 'building a product/service on behalf of users,' but the docs frame the developer-vs-user line around whether you act for OTHER users — a solo local tool is not explicitly addressed.
- Billing state is in flux: the June 15 2026 split of Agent SDK/`claude -p` usage onto a separate metered credit was announced (May 2026), then paused on the effective date; Anthropic says it is 'working on revising their approach.' Whether/when subscription-backed programmatic use gets metered separately (changing the economics of driving `claude -p` from the face) is unresolved.
- I did not fetch the full Consumer Terms (anthropic.com/legal/consumer-terms) and Commercial Terms (anthropic.com/legal/commercial-terms) verbatim — they are the linked governing documents; the load-bearing operative language lives in the Claude Code legal-and-compliance page, which quotes/implements them. If a lawyer-grade citation to the exact ToS clause number is needed, those two URLs should be pulled directly.
- The exact publish/last-updated date of the legal-and-compliance page itself is not stamped on the page; the 'Authentication and credential use' section's ~Feb 19 2026 origin is corroborated only by secondary reporting (The Register, VentureBeat), not by a date on the official page.
- Whether other agents the face drives (Codex, Hermes) have analogous credential/subscription restrictions is out of scope of this Anthropic-only research and was not investigated.

## Red flags — never port these

- Hermes-style Claude OAuth reuse: reading ~/.claude/.credentials.json and the macOS 'Claude Code-credentials' keychain entry, then Bearer-calling api.anthropic.com (and writing the refreshed token back). This is the single bright-line ToS violation ('developers may not collect, store, or intermediate Claude.ai credentials or session tokens'). The Hermes source (anthropic_adapter.py:930-996, credential_pool.py:966-1054) shows exactly HOW — the face must never port it. Signal to heed: the auto-mode classifier on this machine already blocks reading .credentials.json; treat that as a boundary, not an obstacle to route around.
- Hermes-style Codex OAuth reuse: reading ~/.codex/auth.json to hit chatgpt.com/backend-api/codex. RED on the same principle (OpenAI's terms) even though Anthropic's ToS gate is N/A there.
- Transitive drift via Hermes: driving Hermes under its DEFAULT provider config makes the face a party to the two reuse patterns above. Audit and pin Hermes' config.yaml provider BEFORE wiring Hermes at all.
- The 'just read the token, it's simpler' simplification: never collapse a spawn-based driver into a direct raw-API call with a scraped subscription token. If the face ever genuinely needs raw API calls or to serve OTHER users, use a proper ANTHROPIC_API_KEY (Console) or --bare mode — the Console key path is explicitly sanctioned; the scraped-token path is not.
- Inverse trap (cost, not ToS): a SET ANTHROPIC_API_KEY silently wins over subscription OAuth in -p and bills per-token. Ensure it is unset for subscription-backed runs; use CLAUDE_CODE_OAUTH_TOKEN (from claude setup-token) for unattended daemons that must survive login expiry.
- Supply-chain footgun (not ToS, but adjacent): a -p run without --bare silently loads a strategy dir's .claude/settings.json hooks and .mcp.json when the face runs Claude inside strategies/<x>. Control it with --strict-mcp-config / --setting-sources (or --bare + an API key).

## Appendix — the surfaces, per agent

### Claude Code

Claude Code (`claude` v2.1.257, a native arm64 binary at /Users/pan/.local/share/claude/versions/2.1.257, symlinked /Users/pan/.local/bin/claude) exposes several official, supported ways to be driven programmatically, all running the SAME agent loop and sharing ONE credential chain. The face (a Node process that already spawns children via execFile) has three strong fits: (1) one-shot headless `claude -p --output-format json` for fire-and-forget tasks; (2) a long-lived `claude -p --input-format stream-json --output-format stream-json` subprocess for multi-turn, streaming, interruptible chat — the richest CLI channel; (3) the official Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`, npm) embedded in-process, which itself spawns the same binary but hands back native message objects, a `canUseTool` permission callback, and a `startup()` prewarm. Session state is resumable across processes by session id (`--resume <uuid>` / `--session-id <uuid>` / `--continue`). `claude mcp serve` makes Claude Code act as a stdio MCP server exposing its built-in TOOLS (Read/Edit/Write/Bash/Glob/Grep/LS…) to an MCP client — the inverse of driving the agent, useful if the face's dsh host wants Claude's tools rather than its brain. Claude Code does NOT natively speak ACP; the Apache-licensed `@zed-industries/claude-code-acp` npm adapter wraps the Agent SDK and bridges to ACP JSON-RPC over stdio. Background/detached sessions (`claude --bg`, enumerated by `claude agents --json`) add a scriptable fleet-management surface. Auth on this machine is subscription OAuth (claude.ai / firstParty / Max plan), stored in the macOS Keychain with a `~/.claude/.credentials.json` (0600) fallback; every wrapper (CLI print mode, the Agent SDK, ACP adapter) uses the same documented precedence chain, so no API key is needed unless one is set (in which case ANTHROPIC_API_KEY silently wins and bills per-token). For unattended/CI use, `claude setup-token` mints a 1-year `sk-ant-oat01-` token consumed via `CLAUDE_CODE_OAUTH_TOKEN`.

#### Headless / print mode — one-shot (claude -p / --print)

- **how**: claude -p "PROMPT" [flags]. Prompt via argv or piped stdin (stdin capped 10MB). Key flags: --output-format text|json|stream-json; --json-schema '<JSON Schema>' (with --output-format json, puts validated result in .structured_output); --append-system-prompt <str> / --system-prompt <str> (full replace) / --append-system-prompt-file; --allowedTools "Bash(git *),Read,Edit" and --disallowedTools; --tools "Bash,Edit,Read" (restrict built-in set); --permission-mode manual|auto|acceptEdits|dontAsk|bypassPermissions|plan (print mode STARTS in manual on every plan, so pass the mode you want); --model fable|opus|sonnet|<full-id>; --fallback-model; --max-budget-usd; --mcp-config <file-or-json...> (+ --strict-mcp-config); --agents '<json>' (inline subagent defs); --add-dir; --bare (CI-deterministic: skips hooks/plugins/MCP/CLAUDE.md/auto-memory, forces API-key/apiKeyHelper auth — does NOT read OAuth or CLAUDE_CODE_OAUTH_TOKEN); --settings <file-or-json>. Exit 0 on success, non-zero on run failure; 143 on SIGTERM. Example: claude -p "Run the test suite and fix failures" --allowedTools "Bash,Read,Edit" --output-format json | jq -r '.result'
- **io**: Input: prompt as trailing argv OR piped stdin (cat build.log | claude -p '...'). Output on stdout: text = plain text; json = single object with .result (assistant text), .session_id, usage/.total_cost_usd + per-model cost, and .structured_output when --json-schema used. Errors: invalid flags → stderr before run; in-run failures (e.g. missing auth) → printed as the result on stdout. Startup warnings (skipped MCP servers) → stderr.
- **session**: One-shot by default, but resumable: capture .session_id from --output-format json, then claude -p "..." --resume <session_id> (works from any directory on the machine, v2.1.223+) or --continue (most recent conversation in cwd). --session-id <uuid> forces a specific id; --fork-session branches on resume; --no-session-persistence disables saving.
- **auth**: Uses the full CLI credential precedence chain. On this machine resolves to subscription OAuth (claude.ai / firstParty / Max), managed by /login, stored in macOS Keychain with ~/.claude/.credentials.json (mode 0600) fallback; CLAUDE_CONFIG_DIR relocates it. No API key needed. Precedence (first wins): Bedrock/Vertex/Foundry env → ANTHROPIC_AUTH_TOKEN → ANTHROPIC_API_KEY (silently bills per-token if set) → apiKeyHelper → CLAUDE_CODE_OAUTH_TOKEN (from claude setup-token) → Anthropic profile → subscription OAuth from /login. NOTE: --bare ignores OAuth + CLAUDE_CODE_OAUTH_TOKEN and requires ANTHROPIC_API_KEY/apiKeyHelper.
- **maturity**: stable (documented as the primary programmatic entrypoint; --bare slated to become the -p default)
- **face_fit**: Excellent, minimal-change fit. The face already does execFile(bin, ["--version"]); swap to execFile("/Users/pan/.local/bin/claude", ["-p", prompt, "--output-format", "json", "--permission-mode", "dontAsk", "--allowedTools", ...], {cwd: strategyDir}) and JSON.parse stdout. Low effort. Best for fire-and-forget strategy tasks where the face wants a single structured result. Pair with --session-id (a UUID the face generates) so follow-ups resume the same conversation.
- **sources**: https://code.claude.com/docs/en/headless; https://code.claude.com/docs/en/cli-reference; claude --help (v2.1.257, run locally)

#### Streaming JSON I/O — long-lived, multi-turn subprocess (-p --input-format stream-json --output-format stream-json)

- **how**: claude -p --input-format stream-json --output-format stream-json --verbose [--include-partial-messages] [--replay-user-messages] [--forward-subagent-text] [--include-hook-events]. Keep ONE child process alive; feed newline-delimited JSON user messages on stdin, read NDJSON events on stdout. --verbose is required for stream-json; --include-partial-messages adds token deltas (stream_event with event.delta.type=="text_delta"); --replay-user-messages echoes your stdin messages back on stdout for acknowledgment. Interrupt a turn via SIGINT (or the SDK interrupt()); SIGTERM ends the process (exit 143) leaving the turn resumable.
- **io**: Input on stdin: newline-delimited JSON user-message objects (shape {"type":"user","message":{"role":"user","content":[{"type":"text","text":"..."}]}}, one per line). Output on stdout: NDJSON event stream — first event is system subtype init (session_id, model, tools, mcp_servers[+errors], plugins[+errors], capabilities array for feature-detection); then assistant/user message events (subagent messages carry parent_tool_use_id, main convo carries null); stream_event partial deltas; system subtype api_retry / plugin_install; final line is a result message with final text, cost, and session metadata. Slow consumers: Claude drains queued output up to 30s before exit.
- **session**: Long-lived within the process (many turns over one stdin/stdout pair). Persists to disk under the session_id from the init event; resumable in a fresh process via --resume <session_id>. SIGTERM leaves the in-flight turn unfinished-but-resumable.
- **auth**: Same credential chain as one-shot print mode (subscription OAuth here). Not --bare by default, so OAuth works.
- **maturity**: stable
- **face_fit**: The richest fit for interactive chat routing from the face. Spawn a persistent child_process.spawn of claude with these flags per strategy/agent tab; write NDJSON lines to child.stdin as the user types; parse child.stdout line-by-line (readline) and stream deltas to the browser over the face's existing chat transport. Medium effort — needs a line-buffered NDJSON reader, a message router keyed by session_id/parent_tool_use_id, and interrupt wiring (SIGINT). Closest CLI-level analogue to a driven live agent without adding the SDK dependency.
- **sources**: https://code.claude.com/docs/en/headless; claude --help (--input-format, --output-format, --include-partial-messages, --replay-user-messages, --forward-subagent-text, --include-hook-events flags)

#### Claude Agent SDK — TypeScript (@anthropic-ai/claude-agent-sdk), in-process Node embedding

- **how**: npm install @anthropic-ai/claude-agent-sdk, then import { query } from "@anthropic-ai/claude-agent-sdk". Core: query({ prompt: string | AsyncIterable<SDKUserMessage>, options }) returns an async generator (a Query) yielding native message objects; for await (const message of query({...})) {}. The SDK SPAWNS the same native claude binary as a subprocess (bundled per-platform as an optional dep, e.g. @anthropic-ai/claude-agent-sdk-darwin-arm64) — NOT direct-to-API. Key options: pathToClaudeCodeExecutable (point at /Users/pan/.local/bin/claude to reuse the installed build), executable ('bun'|'deno'|'node') + executableArgs, cwd, env, stderr callback, mcpServers + strictMcpConfig, allowedTools/disallowedTools, permissionMode ('default'|'plan'|'bypassPermissions'…), canUseTool(request,opts)=>Promise<ElicitationResult> (custom per-tool approval, invoked only when the flow falls through to a prompt), model, systemPrompt (string | {type:'preset',preset:'claude_code',append?,excludeDynamicSections?}), maxTurns, resume/continue/forkSession/sessionId, persistSession. Prewarm with const w = await startup({options, initializeTimeoutMs}); w.query("..."). For single-file bundles use extractFromBunfs() + pathToClaudeCodeExecutable. A Query also exposes interrupt().
- **io**: In-process JS/TS objects: prompt is a string or an AsyncIterable of user-message objects (for multi-turn streaming input); output is an async generator of typed SDK messages (system/init, assistant, user, result, stream events) — same event model as stream-json but as native objects, no manual NDJSON parsing. stderr delivered via callback.
- **session**: Resumable: options.resume=<sessionId>, continue:true, sessionId:<uuid>, forkSession:true, persistSession:false. Same on-disk session store as the CLI, so SDK and claude -p sessions are mutually resumable by id.
- **auth**: Same credential chain as the CLI — docs state apiKeyHelper, ANTHROPIC_API_KEY, and ANTHROPIC_AUTH_TOKEN 'apply to the CLI and the surfaces that wrap it, including the VS Code extension, the Agent SDK, and GitHub Actions.' So with no API key set it uses this machine's subscription OAuth from /login (Keychain / ~/.claude/.credentials.json). Set ANTHROPIC_API_KEY (or CLAUDE_CODE_OAUTH_TOKEN for CI) to override.
- **maturity**: stable (Anthropic-official; the documented 'full programmatic control' path)
- **face_fit**: Strong fit since the face is already Node 22 hosting dsh in-process. Add the dep and call query() directly — no NDJSON plumbing, native objects, and canUseTool lets the face implement Gate-2-style approval in JS instead of pre-baking --allowedTools. Trade-off: adds a native optional-dep binary to the Node process (or set pathToClaudeCodeExecutable to the already-installed /Users/pan/.local/bin/claude to avoid the second binary). Low-to-medium effort. Best when the face wants programmatic tool-approval callbacks and typed streaming without managing a raw subprocess.
- **sources**: https://code.claude.com/docs/en/agent-sdk/typescript; https://code.claude.com/docs/en/agent-sdk/overview; https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk

#### Claude Code AS an MCP server (claude mcp serve) — exposes its tools, not its agent loop

- **how**: claude mcp serve (flags: -d/--debug, --verbose). Starts a stdio MCP server; prints nothing and blocks (silent = running, waiting for a client). A client connects by spawning it, e.g. in an MCP client config: {"mcpServers":{"claude-code":{"type":"stdio","command":"/Users/pan/.local/bin/claude","args":["mcp","serve"],"env":{}}}}. - **session**: Per stdio connection; not a resumable conversation model — a tool server bound to the client session.
- **auth**: Runs as a local process using the same machine credentials/config; the tools it runs (Bash/Edit/…) act on the local filesystem. The tool calls themselves are tool execution not inference, so effectively no OAuth/API-key model-token consumption for the tool surface.
- **maturity**: stable
- **face_fit**: Niche fit. The face's dsh runtime is already an MCP host (the project ships an MCP tool surface). If the goal is to give dsh/Kairos Claude's file+shell TOOLS, dsh could add claude mcp serve as one more stdio MCP server. But this does NOT route a task to Claude-the-agent and get Claude's answer — for that use print/stream-json/SDK. Listed for completeness; low effort but usually the wrong tool for 'drive Claude and get output back.'
- **sources**: https://code.claude.com/docs/en/mcp; claude mcp serve --help (run locally)

### Codex

Codex (codex-cli 0.152.0, /opt/homebrew/bin/codex) exposes multiple programmatic drive channels, from simplest to richest: (1) `codex exec` — headless one-shot run, prompt via argv or stdin, streams JSONL events with `--json`, writes the final message to a file with `--output-last-message`, and can enforce a JSON Schema on the final answer with `--output-schema`; resumable via `codex exec resume`. (2) `codex mcp-server` — Codex AS a stdio MCP server exposing two tools `codex` and `codex-reply` (now officially DEPRECATED in favor of the app server, but still present and the lowest-effort path for the face since dsh already mounts stdio MCP servers). (3) `codex app-server` — the modern JSON-RPC-over-stdio/unix/ws protocol daemon (replaces the old `proto`, which no longer exists) with a large method surface (`thread/start`, `turn/start`, `turn/interrupt`, `review/start`, etc.) and rich streaming server notifications; a shared local daemon variant lives at `~/.codex/ipc/ipc.sock` and is driven via `codex app-server proxy`, `codex agents`, `codex queue`, `codex apply`. (4) `codex remote-control` — the app-server daemon exposed over an authenticated websocket with pairing. (5) `codex review` — non-interactive code review. Auth is ChatGPT OAuth by default (this machine: `auth_mode=chatgpt`, tokens in `~/.codex/auth.json`, `OPENAI_API_KEY` null) with `OPENAI_API_KEY`/`CODEX_API_KEY` as the alternative; config in `~/.codex/config.toml`. For the face, `codex exec --json` (spawn + parse JSONL) is the pragmatic drive channel, `codex mcp-server` is the drop-in dsh-tool mount, and `codex app-server` is the full-fidelity option.

#### codex exec (headless non-interactive run)

- **how**: execFile/spawn `codex exec [OPTIONS] [PROMPT]`. Prompt as argv arg, or via stdin when omitted or `-` is used (`cat prompt.txt | codex exec -`); if both argv prompt and piped stdin are given, stdin is appended as a `<stdin>` block. Key flags: `--json` (emit JSONL events to stdout), `-o/--output-last-message <FILE>` (write ONLY the final agent message to a file, still prints to stdout), `--output-schema <FILE>` (path to a JSON Schema constraining the model's final response shape — combine with `-o` for structured JSON), `-m/--model`, `-C/--cd <DIR>` (working root), `--add-dir <DIR>` (extra writable dirs), `-s/--sandbox <read-only|workspace-write|danger-full-access>`, `-a/--ask-for-approval <on-request|never>`, `--dangerously-bypass-approvals-and-sandbox` (fully autonomous, for externally-sandboxed envs), `--skip-git-repo-check` (run outside a git repo), `--ephemeral` (do not persist session to disk), `--ignore-user-config`, `--ignore-rules`, `-c key=value` (TOML config overrides, dotted paths), `--enable/--disable <FEATURE>`, `-i/--image <FILE>`, `--color`. Subcommands: `codex exec resume`, `codex exec fork`, `codex exec review`.
- **io**: INPUT: prompt on argv or piped to stdin. OUTPUT default: human progress on stderr, final answer on stdout. With `--json`: newline-delimited JSON (JSONL) events on stdout using DOTTED names — `thread.started {thread_id}` (the session/thread UUID, e.g. "0199a213-81c0-7800-..."), `turn.started`, `item.started`/`item.updated`/`item.completed` (each carries a nested `item` with `type` ∈ agent_message|reasoning|command_execution|file_change|mcp_tool_call|web_search|todo_list|error and fields like `item.text`), `turn.completed` (with usage), `turn.failed`, `error`. Extract the FINAL answer three ways: parse the `item.completed` whose `item.type=="agent_message"` and read `item.text`; OR read the file from `--output-last-message`; OR use `--output-schema` + `-o` to get schema-conformant JSON. This DOTTED event vocabulary is distinct from the app-server protocol's slash-delimited JSON-RPC methods.
- **session**: One-shot by default; each run creates a session (thread) persisted under ~/.codex/sessions + thread_history_1.sqlite unless `--ephemeral`. Resumable: `codex exec resume <SESSION_ID> [PROMPT]` or `codex exec resume --last [PROMPT]` (add `--all` to disable cwd filtering, `-i` to attach images). Fork with `codex exec fork <SESSION_ID>` to branch a session into a new one.
- **auth**: ChatGPT OAuth by default (this machine: ~/.codex/auth.json auth_mode=chatgpt, tokens{id_token,access_token,refresh_token,account_id}, OPENAI_API_KEY=null). Alternative for automation/CI: `OPENAI_API_KEY=<key>` or `CODEX_API_KEY=<key>` env var. Config layered from ~/.codex/config.toml (override with `-c`, bypass with `--ignore-user-config`).
- **maturity**: stable — the documented, recommended path for scripts/CI. `--output-schema` and `--ephemeral` are stable; some flags (`--thread-source`) niche.
- **face_fit**: Cleanest fit for the Node face: `execFile('codex',['exec','--json','--skip-git-repo-check','-C',workdir, prompt])` (or spawn + write prompt to stdin), read stdout line-by-line, JSON.parse each line, stream item deltas to the chat UI, and surface the agent_message item.text (or the --output-last-message file) as the result. Capture thread_id from the first `thread.started` event to enable follow-ups via `codex exec resume`. LOW effort — no protocol handshake, just process spawn + JSONL parsing; maps directly onto the face's existing execFile pattern.
- **sources**: codex exec --help (v0.152.0); https://learn.chatgpt.com/docs/non-interactive-mode; https://takopi.dev/reference/runners/codex/exec-json-cheatsheet/; https://github.com/openai/codex/issues/14736

#### codex mcp-server (Codex AS a stdio MCP server)

- **how**: Spawn `codex mcp-server` (stdio transport). Flags limited to `-c key=value`, `--enable/--disable <FEATURE>`, `--strict-config`. Inspect with `npx @modelcontextprotocol/inspector codex mcp-server`. Exposes two MCP tools: `codex` (start a new session; params: `prompt` (string, required), `approval-policy` ∈ untrusted|on-request|never, `sandbox` ∈ read-only|workspace-write|danger-full-access, `config` (object of overrides), `cwd` (string), `model` (string)) and `codex-reply` (continue a session; params: `prompt` (string, required), `threadId` (string, required — taken from the prior response's structuredContent.threadId)).
- **io**: MCP JSON-RPC over stdio. `tools/call` returns a standard CallToolResult: `{structuredContent:{threadId, content, model, reasoningEffort}, content:[{type:'text',text:...}]}` — modern clients read structuredContent, legacy read content[]. Streaming progress arrives as MCP notifications `codex/event` whose payloads mirror core protocol event types, optionally correlated to the originating request via `_meta.requestId`. Known historical gotcha (now fixed): early versions did not return the conversation/thread id from the `codex` tool, blocking multi-turn — the fix returns `threadId` in structuredContent; use that with codex-reply.
- **session**: Stateful across the server process lifetime: `codex` opens a thread, `codex-reply` continues it by threadId. Sessions also persist to ~/.codex like any run.
- **auth**: Same as the CLI: ChatGPT OAuth (~/.codex/auth.json) or OPENAI_API_KEY/CODEX_API_KEY. The server inherits the ambient ~/.codex config and auth of the user running it.
- **maturity**: present but DEPRECATED per official docs (superseded by `codex app-server`). Tool schemas live in the repo (app-server-protocol/src/protocol/{common,v1,v2}.rs); the interface is described in codex-rs/docs/codex_mcp_interface.md.
- **face_fit**: Lowest-integration-effort path GIVEN the face already mounts stdio MCP servers in dsh: add an entry like {command:'codex', args:['mcp-server']} to dsh's MCP server config so the main agent gets `codex`/`codex-reply` as callable tools — no bespoke driver code. Effort: minimal (a config line + surfacing the two tools). CAVEAT: officially DEPRECATED (docs say prefer the app server, or the openai/codex-plugin-cc for Claude Code) — usable today but may be removed; if choosing this, pin the codex version and plan a migration to app-server.
- **sources**: codex mcp-server --help (v0.152.0); https://learn.chatgpt.com/docs/mcp-server; https://github.com/openai/codex/blob/main/codex-rs/docs/codex_mcp_interface.md; https://github.com/openai/codex/issues/8388; https://github.com/openai/codex/issues/5660

#### codex app-server (JSON-RPC protocol daemon — modern replacement for `proto`)

- **how**: Spawn `codex app-server` (default transport `stdio://`). `--listen <URL>` accepts `stdio://` (default), `unix://` / `unix://PATH`, `ws://IP:PORT`, or `off`; `--stdio` is shorthand. For non-loopback ws listeners: `--ws-auth <capability-token|signed-bearer-token>` plus `--ws-token-file`/`--ws-token-sha256` (capability) or `--ws-shared-secret-file`/`--ws-issuer`/`--ws-audience`/`--ws-max-clock-skew-seconds` (signed JWT). `--analytics-default-enabled`, `--code-mode-host <URL>`. Generate the machine-readable contract yourself: `codex app-server generate-json-schema --out <DIR> [--experimental]` (JSON Schema bundle) or `codex app-server generate-ts --out <DIR>` (TypeScript bindings — directly usable in the Node face). NOTE: the old `codex proto` subcommand no longer exists in this version (verified: `codex proto` falls through to the interactive CLI); app-server + `exec --json` are its successors.
- **io**: JSON-RPC 2.0 request/response + server notifications over the chosen transport. Client→server ClientRequest methods (147 total; drive-relevant subset): `initialize` (params: capabilities, clientInfo), `thread/start` (params incl. cwd, model, modelProvider, approvalPolicy, sandbox, permissions profile, baseInstructions, developerInstructions, projectId, ephemeral → returns {thread, model, cwd, approvalPolicy, sandbox}), `turn/start` (REQUIRED params: threadId, input[]; optional: model, effort, cwd, approvalPolicy, sandboxPolicy, outputSchema, collaborationMode → returns {turn}), `turn/steer`, `turn/interrupt`, `thread/resume` (threadId, + overrides), `thread/fork`, `thread/queue/{add,list,update,delete,reorder,start}`, `thread/read`, `thread/items/list`, `thread/turns/list`, `thread/inject_items`, `thread/rollback`, `thread/revert`, `thread/compact/start`, `thread/shellCommand`, `review/start`, `command/exec` (+ write/terminate/resize), `process/{spawn,writeStdin,kill,resizePty}`, `fs/{readFile,writeFile,readDirectory,watch,...}`, `model/list`, `skills/list`, `plugin/*`, `mcpServer/tool/call`, `remoteControl/*`, `account/*`, `config/read`. Server→client: ServerRequest (approval round-trips: ExecCommandApproval, ApplyPatchApproval, FileChangeRequestApproval, PermissionsRequestApproval, McpServerElicitationRequest, ToolRequestUserInput) and ServerNotification (streaming; ~85 methods incl. `thread/started`, `turn/started`, `turn/completed`, `item/started`, `item/completed`, `item/agentMessage/delta`, `item/reasoning/textDelta`, `command/exec/outputDelta`, `turn/diff/updated`, `turn/plan/updated`, `thread/tokenUsage/updated`, `error`). Full schemas generated to scratchpad (see sources).
- **session**: Fully stateful and multi-thread: one app-server process hosts many threads; threads are addressed by threadId, persist to ~/.codex (thread_history_1.sqlite, sessions/), and are resumable/forkable/queueable via protocol methods. Turns stream incrementally and can be interrupted/steered mid-flight.
- **auth**: Same credential base as the CLI (ChatGPT OAuth in ~/.codex/auth.json or OPENAI_API_KEY/CODEX_API_KEY). Transport-level auth is separate and only needed for non-loopback ws (capability token file or signed JWT bearer, flags above); stdio and loopback need none. There is a dedicated `chatgptAuthTokens/refresh` protocol method and `account/login/*` methods for in-protocol auth management.
- **maturity**: experimental (labeled `[experimental]` in CLI help) but is the officially-recommended successor to the deprecated mcp-server; schema/TS generators are first-class and used by the VSCode extension.
- **face_fit**: Highest-fidelity fit and the strategic choice: spawn `codex app-server` from the Node face, speak JSON-RPC over stdio (or connect to the shared daemon socket — see next method). Use `codex app-server generate-ts --out ...` to get typed bindings for the face directly. The face would: initialize → thread/start (cwd=strategy dir, sandbox/approvalPolicy set) → turn/start with input → consume item/* + agentMessage/delta notifications to stream into the chat UI → answer ServerRequest approval prompts through the face's Gate-2 surface (this is the natural home for approval routing). HIGHER effort than exec/mcp-server (a real JSON-RPC client + notification demux + approval handlers) but unlocks streaming deltas, interruption, multi-thread, queueing, and native approval round-trips. Marked [experimental] in --help.
- **sources**: codex app-server --help / generate-json-schema --help / generate-ts --help (v0.152.0); generated schema bundle: /private/tmp/claude-501/-Users-pan-Desktop-self-evolve-evolving-alpha-us/964c878d-1aa7-40fb-a748-bb298b1e4e3d/scratchpad/codex-schema/ (ClientRequest.json, ServerNotification.json, ServerRequest.json, v2/TurnStartParams.json, v2/ThreadStartParams.json, codex_app_server_protocol.v2.schemas.json); https://learn.chatgpt.com/docs/mcp-server (deprecation notice pointing to app server)

#### codex app-server daemon + proxy + agents/queue/apply (shared local daemon)

- **how**: A single durable local app-server daemon backs the interactive TUI and CLI helpers. Manage it: `codex app-server daemon {bootstrap|start|restart|stop|version|enable-remote-control|disable-remote-control}` (`daemon version` prints CLI + running app-server versions as JSON; `daemon bootstrap` installs durable management for SSH-driven use). Connect a raw stdio pipe to it with `codex app-server proxy [--sock <SOCKET_PATH>]` (default socket on this machine: ~/.codex/ipc/ipc.sock, a unix domain socket confirmed present). Convenience CLIs that talk to the daemon: `codex agents` (browse all agent sessions on the shared daemon; `--remote <ws://|wss://|unix://>` + `--remote-auth-token-env` to target a remote server, `-C` for new-task cwd), `codex queue --thread <UUID|name> --message <TEXT> [-i img][-m model][-s sandbox][-C dir]` (enqueue a message for an existing session — non-interactive, scriptable), `codex apply <TASK_ID>` (git-apply the latest diff a Codex task produced onto the working tree), plus `codex resume`/`codex fork`/`codex archive`/`codex delete`/`codex unarchive`.
- **io**: `codex app-server proxy` bridges stdin/stdout bytes straight to the daemon's control socket → same JSON-RPC protocol as `codex app-server` but against the shared, already-running instance (so the face can attach to sessions the user started in the TUI, and vice-versa). `codex queue` is fire-and-forget JSON-less argv (returns exit status). `codex apply` performs a `git apply` and reports success/failure. `codex agents` is an interactive TUI (less scriptable).
- **session**: Long-lived, cross-client shared state: threads created anywhere (TUI, exec, face) are visible to all daemon clients; `queue` and `apply` operate on existing thread ids/names.
- **auth**: Inherits the daemon's auth (ChatGPT OAuth / API key). Remote targeting adds `--remote-auth-token-env <ENV_VAR>` naming an env var holding the bearer token.
- **maturity**: experimental (`codex app-server` is [experimental]; daemon subcommands are the plumbing behind the shipping TUI). `apply`/`queue`/`resume`/`agents` are stable top-level commands.
- **face_fit**: Two uses for the face: (a) drive the SHARED daemon instead of spawning a private app-server — connect to ~/.codex/ipc/ipc.sock (or via `codex app-server proxy --sock`) so the face and the user's own Codex TUI see the same sessions; (b) cheap out-of-band controls — `codex queue --thread <id> --message ...` to nudge a running session, and `codex apply <task_id>` to land a task's diff into a strategy worktree. Medium effort for (a) (same JSON-RPC work as app-server, minus process management), trivial for (b) (execFile).

#### codex remote-control (authenticated websocket remote drive)

- **how**: `codex remote-control start [--json]` starts the app-server daemon with remote control enabled; `codex remote-control stop`; `codex remote-control pair [--json]` prints a short-lived manual pairing code to authorize a new client. **Notes.** DEPRECATION/DIRECTION: `codex mcp-server` is officially DEPRECATED — the docs (learn.chatgpt.com/docs/mcp-server) direct integrators to the Codex app server or the openai/codex-plugin-cc plugin.
