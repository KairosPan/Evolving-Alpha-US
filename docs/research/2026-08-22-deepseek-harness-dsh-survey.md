# landing
Source: https://deepseek.com/harness/en/ (DeepSeek Harness developer-preview landing page, English; fetched 2026-08-22 via two complementary WebFetch passes)

## Key points
### Product identity
DeepSeek Harness (CLI name: dsh) is DeepSeek's open-source agent harness framework, currently in developer preview. MIT-licensed, © 2026 DeepSeek. Page offers a Chinese/English toggle. Launch commands shown: `npx @deepseek-ai/dsh web` (web launch) and `git clone https://github.com/deepseek-ai/deepseek-harness` (source install).

### Agent = Model + Harness framing
The page's foundational framing is the formula 'Agent = Model + Harness'. The model is called 'the soul of an agent'; the harness is what 'lets an agent understand its environment, use tools, and keep working in real-world settings'. One section heading is literally 'Harness keeps agents working in real-world environments' — the harness's job is durability/practicality beyond raw language capability.

### Everything-is-a-plugin: full capability list
Every agent capability is a plugin that can be swapped or recomposed. The enumerated plugin surface is: models, tools, skills, sessions, sandboxes, storage, loops, scheduling, and the UI. Notably this list includes things most frameworks treat as core/fixed — the agent loop itself, session management, scheduling, and even the UI are plugins, meaning the framework core carries no agent capability of its own.

### Cordis kernel relationship / component boundary
DSH is built on the Cordis kernel's plugin system (separate project: github.com/cordiverse/cordis, with an academic paper at github.com/cordiverse/paper). Boundary as stated: 'The Cordis kernel manages plugin mounting, unmounting, and dependencies. Agent capabilities live in the plugins.' So the kernel owns only lifecycle (mount/unmount) and the dependency graph; all agent-domain behavior lives above the kernel in plugins.

### Plugin coordination mechanism
Inter-plugin communication is mediated by the kernel's primitives: 'Cordis services and events let the plugins work together.' Plugins don't import each other directly; they compose through services (provided/consumed capabilities) and events — analogous to a microkernel service registry plus an event bus.

### Configuration-over-code composition
Under 'Compose with configuration' / 'Customize your DeepSeek Harness': 'Developers can select, swap, or extend any capability in configuration without changing the DeepSeek Harness source code.' Capability selection, replacement, and extension are declarative config operations, and (per the lifecycle framing) can happen at runtime via mounting/unmounting — the source tree is never the customization surface.

### Traceability: append-only session log
'Every run is traceable' is the second pillar. Mechanism: 'Everything the model sees is recorded in an append-only session log: system prompts, reasoning, tool calls and results, subagent scheduling, and every context injection.' The invariant is completeness of the model's observation surface — not just tool I/O but system prompts, reasoning, subagent scheduling decisions, and each context injection are all events in the log.

### One event stream powers all session operations
'Resume, fork, search, and replay all operate on the same event stream.' There is no separate checkpoint/snapshot format — session continuation, branching (fork), retrieval (search), and re-execution (replay) are all derived views over the single append-only log. A 'Trajectory view' UI lets you inspect the record filtered 'by source' (i.e., which component injected each event).

### Runtime mode 1: Standard
'Full coding agent with file editing, shell, file and web search, skills, planning, goals, subagents, and workflows.' This is the batteries-included preset — the full capability roster mounted.

### Runtime mode 2: Code
'All Standard mode capabilities, with tools exposed through the Code Mode SDK so the model can combine multi-step operations in one TypeScript program.' Instead of issuing one tool call per turn, the model writes a TypeScript program against an SDK that wraps the tools, batching multi-step operations into a single program execution.

### Runtime mode 3: Minimal
'Two-tool coding agent with persistent bash and str_replace_editor.' A deliberately stripped preset (persistent bash + string-replace editor only), positioned for benchmarking in minimal environments — demonstrating that a mode is just a plugin composition, scalable down to two tools.

### Runtime mode 4: Creator
'Built for creating custom agent presets, with all Standard mode capabilities plus runtime inspection, plugin experiments, and preset-authoring guidance.' A self-hosting/meta mode: the harness used to build new configurations of itself, with live runtime inspection and plugin experimentation. Modes are thus presets = named plugin compositions, and preset authoring is itself a first-class supported activity.

### Safety / permissions / sandboxing coverage
The landing page is thin here: sandboxes appear only as one entry in the plugin capability list (i.e., isolation is pluggable, not fixed), and the footer links a 'Safe Use Policy' (/harness/en/privacy/) and a 'Data Processing Statement' (/harness/en/data-processing/). No permission model, approval flow, or sandbox mechanics are described on this page — that detail presumably lives in the developer docs.

### Developer-preview caveat / stability posture
'DeepSeek Harness remains in developer preview and is still being tested by developers building agent harnesses. Its core plugins and APIs will continue to evolve.' Explicit signal that even the 'core plugins' and APIs are unstable — the plugin contract itself is still moving.

### Ecosystem strategy
A 'Join the DSH plugin ecosystem' section points at community plugins discovered via the GitHub topic 'dsh-plugin' (github.com/topics/dsh-plugin) — distribution of third-party capabilities rides plain GitHub topic tagging rather than a curated registry, at least in the preview.

### Section structure of the page
Exact section headings, in order: 'Everything is a plugin'; 'Agent = Model + Harness'; 'Harness keeps agents working in real-world environments'; 'Design approach: Everything is a plugin. Every run is traceable.'; 'Customize your DeepSeek Harness'; 'Join the DSH plugin ecosystem'. The two-slogan pair (plugin universality + run traceability) is explicitly labeled the 'Design approach'.

## Design principles
- Everything is a plugin: every agent capability — models, tools, skills, sessions, sandboxes, storage, loops, scheduling, UI — is a swappable, recomposable plugin; the framework core owns no agent capability.
- Microkernel boundary: the Cordis kernel does only lifecycle (mounting/unmounting) and dependency management; all agent capabilities live above it in plugins.
- Plugins compose through kernel-mediated services and events, never direct coupling ('Cordis services and events let the plugins work together').
- Configuration over code: any capability can be selected, swapped, or extended in configuration without touching the harness source — the customization surface is config, not the tree.
- Every run is traceable: the complete observation surface of the model (system prompts, reasoning, tool calls/results, subagent scheduling, every context injection) goes into an append-only session log — completeness of capture is the invariant.
- One event stream, many views: resume, fork, search, and replay are all derived operations over the same append-only log; there is no separate checkpoint or state format.
- Agent = Model + Harness: the model is the intelligence ('soul'); the harness is the separable environmental layer that supplies perception, tools, and persistence in real-world settings.
- Runtime modes are presets, i.e. named plugin compositions — the same architecture scales from a two-tool Minimal agent to a full Standard agent purely by what is mounted.
- Self-hosting meta-level: Creator mode makes preset/plugin authoring a first-class in-harness activity, with runtime inspection and plugin experiments — the harness is its own workbench.
- Tool-call batching as a mode, not a hack: Code mode exposes tools through an SDK so the model composes multi-step operations in one TypeScript program, trading per-call mediation for programmatic composition.
- Isolation is pluggable: sandboxes are one plugin category among the rest, not a fixed built-in boundary (the landing page states no fixed permission model).
- Open ecosystem by convention: third-party plugins are discovered via a GitHub topic tag (dsh-plugin) rather than a gated registry.

# cordis-paper
Source: "A Programming Paradigm for Spatiotemporal Composability" — Yifan Shi (Peking University / DeepSeek-AI), Wei Zhang (PKU), Tianyi Cui (DeepSeek-AI); preprint of 2026-08-13 (active revision), 88 pp., github.com/cordiverse/paper (paper.pdf, read in full pp.1–80; pp.81–88 are remaining references). Supplemented by github.com/cordiverse/cordis README and the DeepSeek Harness docs page /reference/cordis-primer.

## Key points
### The two orthogonal dimensions of dynamic composition
The paper identifies two dimensions beyond algebraic composition. Temporal composability (the time dimension): upon removal of a component, every modification it made to the shared environment must be completely and safely reversed — requiring tracking of every resource allocation, event registration, and state mutation, with orderly reclamation. Spatial composability (the space dimension): components must declare, discover, and resolve dependencies on one another in a structured, verifiable manner, with the runtime managing dependency topology and coordinating lifecycles when dependencies change. In the static setting these reduce to lexical scoping (RAII/bracket patterns) and module import resolution; in the dynamic setting they become much harder because effects are long-lived and not lexically bounded, and dependencies appear, disappear, or change identity during execution.

### Motivating failure: VSCode as canonical plugin system
Temporal limitation: VSCode's extension host cannot unload an individual extension's code at runtime — once activate has run, disabling/uninstalling requires restarting the whole host; 87 of the top 100 extensions contain executable code and need this. The deactivate hook only runs at host termination, and crucially it separates effect disposal from effect creation (in activate), 'violating locality of concern and making complete cleanup difficult to verify.' Spatial limitation: only 7 of the top 100 extensions declare extensionDependencies; the API steers extensions toward fixed host-provided extension points (commands, views, language features) rather than depending on each other, and cross-extension access via getExtension(...).exports is untyped (any). These limitations 'recur across plugin systems generally, differing only in degree.'

### Motivating failure: self-evolving agent harnesses (directly relevant to dsh)
Modern AI agents rely on runtime agent harnesses that compose tool suites and execution environments, govern permissions and sandboxing, maintain session state and persistence, provide context management and memory, orchestrate subagents and multi-agent workflows, and expose interfaces to users and automation. A future harness may generate and deploy modifications to its own components while continuously serving requests — each such modification is an instance of dynamic composition. Because modifications occur continuously with limited or no human oversight: without temporal composability each self-modification forces a full restart discarding all process-local state, cumulative unavailability becomes substantial, in-flight tasks are disrupted, and 'a faulty self-modification can disable the very process needed to recover.' Without spatial composability each module must detect and adapt to changes in its dependencies by ad hoc means, and naive code replacement may silently break dependents or introduce circular dependencies that surface only at reload time. (References cite OpenAI's 'Harness Engineering' and Anthropic's 'Harness Design for Long-Running Application Development', MemGPT, LLM multi-agent surveys, and 'LLMs as Tool Makers'.)

### The coarse-grained workaround and the granularity mismatch
Dynamic composability got little formal attention because OSes give temporal composability at process granularity (restart the process) and container orchestrators give spatial composability at service granularity. Costs: each restart discards process-local accumulated state (caches, connections, partial computations), rebuilding takes seconds-to-minutes, and availability during rebuild requires redundant replicas; container-level orchestration cannot express dependencies between components sharing an address space and introduces network overhead for interactions that could be local function calls. 'This granularity mismatch demands a compositional abstraction that manages effects and dependencies at the same level as the components themselves.'

### Core intellectual move: reify effects and coeffects as runtime mechanisms
Effect systems formalize how a computation modifies its environment; coeffect systems (comonadic, graded) formalize what it requires from the environment. Both are classically static: effects tracked in lexically fixed scopes discharged by compile-time handlers, coeffect annotations verified against contexts determined before execution. No fixed lexical scope can delimit a plugin loaded after deployment; no compile-time context can anticipate dependencies from runtime configuration. The shift: 'rather than extending static type systems with more annotations, we reify the conceptual structures of effects and coeffects so that a runtime can operate on them directly, establishing dynamically the guarantees these systems provide statically.'

### Revertible effects: the effect context and the accumulator
An effect is modeled as a function Γ → Γ × (Γ → Γ): applied to the current context it yields the modified context together with an explicit (left) inverse, supplied by the caller at the point of application. The effect context is ∂Γ := Γ × (Γ → Γ) — a pair (γ, φ) of current state and the accumulator φ, the composite of the inverses of all effects performed so far, which recovers the context to its initial state. track composes each new inverse onto φ (LIFO order); recover applies φ and resets it to identity. The soundness invariant is φ(γ) = γ₀. Witnessed effect functions require only g(δ) = γ — the inverse must revert the effect at the state where it was applied, unconstrained elsewhere. The structure iterates into a tower (∂²Γ …): undoing an effect is itself an effect, so a child effect's inverse is an effect on the parent.

### Independence of effects and out-of-order revert
LIFO revert needs no hypothesis (Theorem 16). Reverting out of order — needed when withdrawing one component from a running system while later effects remain, or when several components' effects interleave — requires independence: every transformation of one effect commutes with every transformation of the other, and neither disturbs the inverse the other yields (Definition 19, checked on generators of the transformation monoids). Under pairwise independence the n inverses can be applied in any permutation and still reach γ₀ (Corollary 21), and an inverse run at a later state 'withdraws its own contribution and nothing else.' Where independence fails, order must be imposed elsewhere: within one component by the accumulator (LIFO), and across components by a declared coeffect that orders one activation against another.

### Reactive coeffects: IoC formalized, typed dependency table
The coeffect context Σ := (k : K) ⇀ V_k is a dependent partial function from typed keys to values — a formalization of inversion-of-control containers. get/set carry preconditions: a dependency cannot be provided twice nor revoked when absent. Critically, set(k,v) has exactly the type of an effect function on Σ, so the effect machinery applies directly and dependency registrations are automatically tracked and recovered: 'This is the synergy between reactive coeffects and revertible effects: coeffect operations are effects, and effects are revertible.' A coeffect at key k is a triple (V_k, ≈_k, A_k): value type, an equivalence up to which values are compared, and a set of operations the bound value provides to holders — each operation acts on the value alone and is confined to that binding.

### Satisfaction, notification, and the reactive invariant
A coeffect specification d ⊆ K is the set of dependencies a component declares. The satisfaction predicate σ ⊨ d (every declared key in dom(σ)) is decidable, and since all mutations pass through effect functions, changes to satisfaction are detectable at each effect boundary — 'the algebraic basis of reactivity: the effect system guarantees that every coeffect change is observed.' Every context transition is classified against d as activating, deactivating, or neutral (notify_d). The reactive invariant: an activating transition triggers execution of the component's effects (fully tracked); a deactivating transition triggers recovery by applying the accumulator. Local spatial composability criterion: a component activates only at a state satisfying its specification (never reads an absent binding), and every loss of satisfaction is detected where it happens and drives deactivation.

### Coeffect isolation: realms as runtime ad-hoc polymorphism
Isolation realms (Σ^iso = realm table ρ : K ⇀ R plus store σ : (r : R) ⇀ V_r) let the same dependency key bind to different values in different contexts — applications in multi-tenant systems, testing environments, and component sandboxes. Resolution is two-layer: k → ρ(k) → σ(ρ(k)), decoupling the logical layer from the storage layer. 'The coeffect isolation mechanism essentially implements a runtime ad-hoc polymorphism system' — dynamically adjustable, finer-grained than traditional DI. set remains an effect (revertible); isolate needs no inverse because it derives a fresh child context rather than writing the shared table — recovery just discards the derived context (the 'derived realization', vs 'in-place realization' which mutates and returns a nontrivial inverse).

### Coeffect interception: cross-cutting metadata on dependency access
Interception attaches metadata to dependency access, adding behavior without modifying the dependency value. Metadata is either context-carried (ι, installed on the context) or component-declared (d(k) in the specification); each key equips metadata with a monoid (M_k, ⊕_k, ε_k). On access the system evaluates σ(k)(d(k) ⊕_k ι(k)); the merge is right-biased so context-carried metadata takes priority and can override the component's declaration, 'letting an enclosing context constrain how a component uses a coeffect without modifying that component' — the mechanism later used for fine-grained access control. Interception is consulted only at access time, so it can be installed, reconfigured, or removed at runtime without triggering any reload or perturbing the dependency graph.

### The unified context type Γ∞ — one entity for everything
Γ∞ := μΓ. Γ × (Γ → Γ) × Σ: current recursive state, the accumulator recovering this level's effects, and the coeffect context. The ∂-tower collapses into one self-similar type. Since the type family V is unconstrained, any state the system needs to share across components can be encoded as a dependency key — 'Σ subsumes all shared mutable states, not just inter-component dependencies. Every interaction between a component and its environment passes through this single entity.' The recursive structure supports hierarchical composition: a parent context aggregates child-level effects in a tree-shaped control structure. The effect transformation 'realizes a literal plug-in metaphor': loading = executing effects (plugging in); unloading = recovering effects (unplugging, without affecting other running components); components at different levels are independently loadable/unloadable; unloading a parent cascades to its children.

### Observational equivalence and commutative keys
Recovery equality is read up to observational equivalence ≃ (physical state cannot be recovered as it stood — free doesn't restore heap layout; generative names aren't restored). Two states are related when their coeffect projections bind the same keys to values indistinguishable by the key's own operations (test words over transformation monoids). A key is commutative when any two of its operations are independent — e.g. a key whose value is a table of independently added/removed entries (route tables, event-listener registries) is commutative; a key holding an ordered middleware chain is not. Theorem 42: if two coeffect-mediated effect functions only share commutative keys, they are independent — this discharges the independence hypothesis for whole systems. The decomposition principle: 'What the decomposition divides is a computation's commuting part from its order-sensitive part. The commuting part is carried by the effects... The order-sensitive part is carried by the coeffects.' Composability is thereby had at the grain of components. Two named limits: binding every shared location at a key is 'the paradigm's discipline and not a property of the construction', and commutativity of a key is an obligation on the component providing the key, not on consumers.

### The context paradigm situated between functional and imperative poles
Explicit state threading (functional/State monad) gives strong compositional guarantees but heavy ergonomics (every function threads state; monadic stacking proliferates). Implicit mutation (imperative/OOP — React's useEffect registering on hidden fiber state, Spring's ApplicationContext.getBean service-locator with null checks and casts) has good ergonomics but effects and dependencies are invisible, scattered, refactoring-fragile. The context paradigm: effects and coeffects both mediated through an explicit context parameter, so each operation is attributable to the context (hence component) that invoked it. Developers supply the inverse of each atomic operation and the inverse of any composite follows by composition — 'a component's teardown is derived from its loading rather than written alongside it'; a component declares only the dependencies it needs and the runtime resolves and re-wires them as providers come and go. 'In both directions, correctness that would otherwise rest on developer discipline becomes a structural property of the paradigm.'

### Calculus objects: component, fiber, registry
A component is a triple (d, p, e): coeffect specification d (keys it reads), provision p (keys it may provide — no key outside p is one its effect function writes), and witnessed effect function e. d and p are the two directions of one interface. A fiber is an instantiation of a component carrying its own lifecycle state: tuple (d, p, e, π parent, σ own coeffect table, τ retirement flag, θ lifecycle state incl. accumulator g and committed view ω). Fiber names are atoms (dynamically created local names — identity that survives mutation). The registry is a tree of fibers rooted at root; the global coeffect context σ_γ is derived, not stored: the union of the tables of Active fibers only. Single-source discipline: provisions of distinct fibers are disjoint, so each key has exactly one possible provider, fixed by provisions not by state. The committed view ω maps each declared key to the name of the fiber that provided it when the transition committed — recording the provider rather than the value is what makes replacement comparisons usable (a different fiber providing an equal value would otherwise compare equal).

### Base calculus: five rules, target views, reactive-only semantics
Orchestration rules (what the orchestrator MAY do): O-Insert (add fiber; enforces fresh name, provision disjointness), O-Retire (unconditional request to stop — never sets lifecycle state directly), O-Remove (only when Inactive, children first — removing earlier would discard the accumulator and leak). Lifecycle rules (what the system does unprompted): L-Reload fires when a fiber holds no committed view and its target view is not ⊥; L-Unload when the committed view differs from the target. The target view target_n(γ) maps each declared key to its provider, and is ⊥ when the fiber ought not run (retired or unsatisfied); a state is quiescent when every fiber has reached its target. 'A transition is initiated whenever the target view changes, regardless of which of the two [retirement or coeffect resolution] moved it.' The rules are nondeterministic and 'reactive only, in that no rule mentions a scheduler; a theorem proved over all such sequences holds for every scheduling policy a runtime might adopt.' Confinement (Definition 48) bounds what an effect function may read and write: a fiber sees the coeffects it declared and no more of the registry, and cannot branch on the lifecycle state of a fiber it did not declare.

### Registration: components instantiating components
An application of a fiber's effect function may register another component (the plugin-host-loads-plugins pattern): registration takes the O-Insert of the child with π = parent, and yields as inverse the O-Retire of the registered fiber. The inverse retires rather than removes, because an inverse must apply wherever it is reached (O-Remove has premises that could fail). Retiring a child sets τ, flipping its target view to ⊥, and the ordinary rules carry it down; a grandchild is reached one level at a time, each child's own accumulator retiring what that child registered. Unloading a parent thereby cascades to its children through plain effect reversal.

### Four-state lifecycle with transitions in progress
Real transitions are not atomic/immediate/infallible, so the two-state model extends to Inactive / Reloading / Active / Unloading (the two transition states outlined). Rules: L-Begin, L-Iter, L-Finish (activation as iteration), L-Divert and L-Raise (two early exits from Reloading), L-Leave and L-Unload (deactivation). A fiber in transition in either direction reads its coeffects through the committed view it holds, and provides none of its own (σ_γ unions Active tables only) — a key its own transition has already written is not yet one a dependent may activate against.

### Withdrawal ordering — the load-bearing teardown guarantee
Dependents activate after their dependencies (from satisfaction preconditions), but the substantive half is withdrawal: 'A component being torn down because its provider is going away is running its own teardown code, which may need the very coeffect that is being withdrawn; closing a connection pool typically means handing the connections back to whatever provided them.' The consumer must be able to read k throughout its own deactivation, and the provider's withdrawal of k takes effect only afterwards. L-Leave records the decision to deactivate — the fiber stops providing (leaves σ_γ) while keeping its committed view and everyone else's intact; L-Unload (the only rule that applies an accumulator) is guarded by ¬relied_n(γ): held back until every consumer that resolves a key to n has gone. The guard doesn't deadlock: once L-Leave marks n, no target view can name n any longer, so every committed consumer is itself on its way out (Theorem 66 proves the guard always releases). The guard orders deactivations along coeffects, not along the fiber tree — a parent may run its inverse while a child is still Unloading.

### Effect iterator = reified delimited continuation; partial rollback
An activation executing multiple effects is modeled as an effect iterator: each iteration yields (new context, inverse, Maybe continuation). Inverses compose onto the accumulator in application order → LIFO recovery. The Maybe continuation 'makes a boundary available between any two consecutive iterations, at which the context is whatever the iterations so far have made it and the accumulator recovers those and nothing more. In this sense the effect iterator is a reified delimited continuation, the structure that mainstream languages expose through the yield operator, so the model maps directly onto the generators they already provide.' Between iterations the system may divert the transition if its target view changed — aborting applies the inverses accumulated so far (partial rollback within a single transition), routing through Unloading like any other deactivation.

### Asynchrony and inertia
Iterations may be asynchronous (yield a Future; external state may change between submission and resolution). The layer adds inertia: once launched, an iteration lands and its landing cannot be declined — a target-view change during flight is answered only after the iteration lands, then the fiber deactivates (the landing alternative of L-Divert). The fiber needs somewhere to be while its inverse runs and the only sound place is Unloading; routing through Active instead would let the fiber provide its coeffects for one step and oblige dependents to activate against a component already leaving. A deactivation may chain straight back into an activation (L-Unload → L-Begin), the mutual chaining of reload and unload in the implementation.

### Failure semantics: per-fiber error, siblings unaffected, no auto-retry
Effects reach outside the context and may refuse (port bound, missing file, unresponsive peer). A raising iteration exits Reloading via L-Raise into Unloading carrying the error: the accumulator built so far is applied, the fiber arrives at Inactive(ξ) 'having installed nothing.' L-Begin requires Inactive(⊥), so the lifecycle is not re-entered from an error outcome — 'this withholds a fiber whose effect function has shown itself to be unsound in the state it ran against rather than retrying it against an unchanged environment.' A failed fiber obstructs nothing (no committed view, cannot make relied hold). 'A failure is recorded on the fiber rather than propagated to its parent, so a component whose transition fails leaves its siblings running, which is the behavior a plugin host wants.'

### Metatheory: recovery exactness and terminal recovery
Theorem 61 (Recovery exactness): under pairwise independence, applying a fiber's accumulator yields (up to control fields) the state the interleaved steps of all other fibers would have produced had this fiber never begun — running an inverse 'withdraws the fiber's contribution and nothing else', even with arbitrary interleaving. Corollary 62 (Terminal recovery): over a closed episode, whatever outcome the fiber arrives at (including failure), the final state is as if the fiber's steps never happened — 'a fiber removed by O-Remove leaves nothing behind.' The independence hypothesis is discharged by the commutative-keys result: coeffect set operations touch disjoint keys across fibers (provision disjointness), so they need no hypothesis at all.

### Metatheory: ordering, resolution coherence, progress
Theorem 63 (Ordering): a fiber begins a transition only where its dependencies are provided; a provider's episode strictly outlives the episodes of its consumers (provider outlives consumer), and a consumer's binding stays constant and readable through its own teardown. Theorem 64 (Resolution coherence): every iteration of a transition runs against the one resolution ω committed at L-Begin — no transition straddles two resolutions; a change in target view takes the fiber out of the transition (L-Divert), with inertia meaning an in-flight iteration lands first and the fiber deactivates afterwards (the guarantee is a disjunction, the second branch making the first safe). Theorem 66 (Progress): given the precedence relation ≺ (provider-before-dependent) is acyclic, iterators bounded, and finitely many names: no deadlock (some rule always applies when not quiescent) and termination (bounded steps per fiber) — every maximal sequence of lifecycle steps ends in a quiescent state; the withdrawal guard always releases. Finiteness excludes only 'a component that registers instances of itself without bound.'

### Metatheory: confluence — dynamic history leaves no trace
Theorem 73: 'the property that characterizes the system as a whole is that its dynamic history leaves no trace: whatever sequence of activations and deactivations a running system has been through, the state it quiesces at is the one the same insertions and retirements would have produced had each component that ends up active been loaded once, in dependency order, and none ever unloaded. The lifecycle relation is confluent, and the normal form it converges on is the statically assembled one.' This is 'the analogue, for dynamic composition, of the consistency with a from-scratch evaluation that change propagation establishes for incremental computation.' It 'licenses reasoning about a Cordis application as though it were statically assembled': an orchestrator that adds, removes, replaces, and reverts is guaranteed to arrive at the state writing the final composition down at the outset would have produced; a component author reasoning about which coeffects are in scope may reason about the quiescent state alone. Failure is excluded as a genuine source of divergence — two schedules may differ in whether a fiber failed — but a failed fiber's contribution to the state is nothing (differ only in that fiber's lifecycle state). The guarantee speaks of state, not of emissions produced along the way.

### Cordis: a meta-framework in three tiers
Cordis realizes the formal model. 'Unlike application frameworks that target a specific domain (e.g., web routing, ORM, UI rendering), it prescribes no concrete scenario; its sole responsibility is to supply universal dynamic composition semantics.' Three tiers: (1) core library implementing effect tracking and coeffect resolution; (2) component loader adding declarative configuration reconciliation and HMR; (3) application frameworks (e.g. Koishi — and dsh) building domain-specific functionality on top. Theory-to-implementation map: Γ∞ = ctx; effect functions = ctx.effect(callback); Σ/Σiso/Σinter = ctx[@@store], ctx[@@isolate], ctx[@@intercept]; get/set/isolate/intercept = ctx.get/set/isolate/intercept; fiber = the instantiation (fiber.uid, fiber.inject=d, component's provide=p, fiber.apply=e, fiber.parent, fiber.ctx the derived child context, fiber.state, fiber.dispose=accumulator, fiber.committed=ω, fiber.target, fiber.inertia = handle of the in-flight transition); O-Insert/O-Retire = ctx.use and its callback inverse; L-rules map onto execute's iteration loop, refresh, reload/unload chaining.

### ctx.effect — the single mutation primitive; witness is author's obligation
'Every context mutation in Cordis flows through a single primitive, ctx.effect: coeffect provision, component instantiation, and every other context-mutating operation reduces to a ctx.effect call, so any operation performed through the context is automatically tracked and recovered upon component unloading.' It accepts plain effects and iterators via one operation, returns a dispose closure; dispose flips an armed flag (halting in-flight iteration, making recovery fire at most once — firing twice would apply an inverse at a state no application produced), and dispose is prepended to the enclosing context's accumulated ctx.dispose so a child effect's inverse is itself an effect on the parent (the ∂²Γ recursion). Notably: 'What the operation does not check is the witness... the callback supplies an inverse, and that the inverse recovers the effect it accompanies is an obligation on the component author rather than a property the runtime verifies.'

### Reactive notification and provider identity by uid
set installs a binding and returns a dispose that removes it; both invoke notify, which for each live fiber whose inject contains a changed key resolving to the same realm calls refresh — the reactive classification made operational; refresh's idempotence renders neutral changes harmless. A binding counts as available only while its installing fiber is ACTIVE, so a provider entering UNLOADING has already stopped providing and dependents begin their own teardown while its bindings are still in place. fiber.target digests each declared key to the uid of the providing fiber: 'Identifying a binding by its provider rather than by its value is what makes a single comparison against the recorded target sufficient: a uid is drawn fresh and never reused, so a provider that is replaced cannot be mistaken for the one it replaced, even when the two provide equal values.' Consequence: 'A provider that overwrites its own binding in place is not observed; a component that wants its replacement to propagate withdraws the binding and installs it afresh.'

### Inertial lifecycle algorithm and the three ordering lines
refresh recomputes fiber.target and, if not already in transition, spawns reload or unload; reload commits the resolved view, runs apply via execute with a guard testing target stability at each iteration boundary, then checks the target at completion — matching enters ACTIVE, otherwise chains into unload; unload recovers all tracked effects in LIFO order then either goes INACTIVE or chains into reload. Two complementary levels: transition-level inertial chaining, and iteration-level staleness checks enabling partial rollback within a transition. The coeffect ordering (Theorem 63) hangs on three lines: reload commits the view before running effects and unload discards it only after every inverse has run (a fiber reads the same bindings for as long as it is loaded, its own teardown included); refresh marks UNLOADING before the transition task is created (the L-Leave step — dependents recompute before any inverse is scheduled); unload awaits every notified dependent reaching INACTIVE before disposing (the L-Unload guard) — the wait sits ahead of the whole recovery since dispose runs a fiber's effects concurrently. The provider graph is traversed on demand rather than analyzed in advance.

### Proxy-mediated context access = capability mediation at point of use
Beyond the reflective ctx.get/set API, Cordis offers property access: ctx[key] via a Proxy whose get trap walks the fiber chain upward — at the first fiber whose committed view binds the key, access is authorized and the binding returned; a fiber that declares the key without having committed throws INACTIVE_ACCESS; reaching root without declaration throws UNDECLARED_ACCESS. 'The proxy resolves against the accessing fiber's own view and enforces the coeffect specification d at the point of use' (bare ctx.get is a store lookup that never fails). Reading the view rather than the store is also what keeps a dependency readable to a component whose teardown was triggered by that dependency going away. Since d is declared statically, the same violation is in principle detectable at compile time.

### Component loader: declarative configuration and reconciliation
Core library serves component developers (imperative primitives); the loader serves application orchestrators: the desired composition is specified as a persistent declarative configuration the loader realizes as fibers and keeps in step with. Each entry declares one fiber: id (stable reconciliation key), url (component module), isolate, intercept, config, disabled — 'an entry can serve as a faithful specification because what supports a fiber is exactly what an entry records.' The binding is bidirectional: the loader responds to entry changes by adjusting the fiber, and a component that revises its own configuration or disables itself has the change written back to its entry. Entries form a configuration tree (group and include components are ordinary components on the registration primitive). Reconciliation is incremental, not teardown-rebuild, and is sound because of the metatheory: confluence makes the quiescent state a function of the final configuration alone; progress proves the system quiesces; terminal recovery means rebuilding one entry leaves surrounding fibers as they were; ordering means entries can be instantiated together with no load order to arrange — 'a dependency constrains when a fiber activates rather than when its module is fetched and evaluated, so the loader loads modules concurrently.' Per-field least-disruptive dispatch: id/url rebuild; isolate reassigns realms; intercept updates in place (no reload); config handed to the component to diff; disabled unloads/reloads.

### Managed realms: local vs global isolation scoping
The loader manages realms: isolate: true asks for a local realm private to the entry, tagged by its id, carried with the entry wherever it moves; a string value asks for a global realm shared by every entry naming that string — moving such an entry changes which entries it shares a binding with. A realm is discarded once no entry names it. Realm reassignment uses per-key delimiter symbols to decide whether a binding is the entry's own and must move with it, and which dependents to notify.

### Hot module replacement without acceptance boundaries
HMR applies the revertible-effect pattern at the module level. 'Because a fiber already bounds all of its component's effects and coeffects, a module that is itself a component can be replaced through fiber operations alone: disposing the old fiber recovers everything the component installed, and a new fiber instantiated from the reloaded module reinstalls it. HMR therefore needs no developer-annotated acceptance boundaries, as opposed to Webpack or Vite HMR.' Three phases: module classification (fixed point accepting modules whose imports are accepted, declining externals and import cycles), stale-entry detection (entries whose transitive dependency tree reaches a changed module), transactional reload (invalidate caches with backup; on any import failure restore caches and rebuild every stale entry from backup — 'the system never enters a half-reloaded state').

### Koishi case study: production validation
Koishi, an open-source chatbot framework on Cordis, has accumulated over 4000 community-contributed plugins over four years (IM adapters, database drivers, admin consoles, end-user features). Every feature is a plugin over the context primitives; 'Koishi itself contributes only the chatbot-domain vocabulary.' The same model runs in a wholly different runtime — Koishi's web console is a second, independent Cordis application composing browser primitives. Demonstrated properties: expressiveness (primitives suffice to carry a complete production system) and generality (fixes how effects and coeffects compose while leaving their meaning to each application — presupposes neither domain nor runtime). Temporal: orchestrator disables a plugin from the console and its effects are withdrawn in place; HMR re-applies edited plugins on save while preserving cache state and live connections elsewhere; 'even an inexperienced author obtains ordered cleanup for a plugin's context-mediated effects without writing an uninstall path... correctness that would otherwise rest on each author's diligence is instead discharged once, by the abstraction.' Spatial: genuine dependency topology across independently authored code; reconfiguring a provider at runtime reactivates only the dependents whose resolved dependency changed; 'a plugin whose dependency is unavailable stays inactive until it appears, without erroring'; authors 'coordinate on nothing beyond the coeffect that connects them.' Threats to validity: single ecosystem, single host language, observational not controlled; existence-and-adoption result, not quantitative.

### System boundary: inside vs outside, acquisition vs emission
What an inverse amounts to is settled by the system boundary: a location lies inside when the system can modify it exclusively and restore prior state (tracked and recoverable); outside when either ability fails (operations act as identity on Γ — neither tracked nor recovered). The boundary is drawn per location, not per medium (a memory region is inside when the system alone writes it; a scratch file under a private path is inside, a shared path outside), and a coeffect moves the boundary by reifying an external location — confining access to operations it supplies inverses for. Operations reaching outside proceed in two stages: acquisition (open/malloc/fork install a record inside the boundary — a revertible effect that is also the channel) and emission (write/send push data through the channel, acting as id — the data leaves). Recovering from an emission has two approaches: withholding output until state is certain to persist (the output-commit problem of rollback-recovery) or compensation (an action restoring state up to an application-supplied coarser equivalence — deleting a created file, refunding a charge); compensations compose in the same LIFO order as inverses, but the metatheory's commutation must be re-established against the coarser equivalence.

### Service multiplexing: exclusive binding vs service broker
The coeffect model echoes OSGi-style services: providers provide a key, consumers inject it. Multiplicity in two forms: exclusive binding (several implementations, at most one bound; switching perturbs every consumer momentarily) vs a service broker (a central entrypoint service injected by both backing providers and consumers; the broker dispatches; updating a backing provider leaves the broker in place so consumers see no change and no reload triggers). The broker underlies load balancing (providers register through revertible effects, so unloading drops them from the routing set automatically), rolling updates (load new provider, shift traffic, unload old once no in-flight requests — 'turns what is traditionally an infrastructure-level operation (container orchestration, blue-green deployment) into an application-level composition pattern'), and cross-process invocation (each process hosts its own Cordis context; remote providers linked via RPC transparently; cross-process interfaces must be designed against an asynchronous contract).

### Access control and sandboxing
Two complementary mechanisms: constraining what dependencies a component may access, and sandboxing untrusted code. The first is structural: 'a component can only access dependencies it has declared; an undeclared access raises an error. This is structurally similar to capability-based security... The inject declaration acts as a capability request, and the context proxy acts as a capability mediator. Since these requests are declared statically, the complete set of proxy-mediated capabilities a component requires is known before it runs, letting the orchestrator review and approve them at load time rather than discovering accesses as they happen.' Interception generalizes this to fine-grained policy (e.g. filesystem dependency carrying metadata declaring readable/writable paths, checked by the provider per call); because interception lives on the context, an orchestrator can attenuate any component's access without modifying the provider, at runtime, without reload. Sandboxing untrusted code is explicitly out of language-level scope — it 'requires an execution boundary beyond the reach of language-level means' (SFI, separate runtime, sandboxed process, virtualized container); the untrusted component then reaches host dependencies through a bridge that is an ordinary fiber whose capabilities can be attenuated by the same access control.

### Language independence: minimum host-language requirements
The context paradigm is language-agnostic. Temporal composability requires closures (an inverse captured as a value with the state it restores) and runtime introducibility/retractability of component code — via a programmatic module registry in managed runtimes (Node.js require.cache), dlopen/dlclose or LoadLibrary/FreeLibrary for native code, either path for WebAssembly; loading is treated as an effect on the context whose inverses undo symbol/type/handler registration. Spatial composability reduces to dependency injection at two levels: typing (typeclasses in Haskell, traits in Rust, TypeScript module augmentation let a provider extend the context type from its own module) and mediation (transparent interposition on access — JS Proxy, Python __get__; absent such a primitive, runtime reflection at the cost of type safety). Metaprogramming (annotations, decorators, Rust proc macros, Scala macros, Zig comptime) can supply typing and mediation together.

### Mutual dependencies: cycles are inert and predictable, and can be decomposed away
A dependency cycle simply leaves the involved components permanently inactive (neither satisfaction predicate can become true) — 'unlike deadlock in concurrent systems, which depends on the schedule and must be detected as it happens, this condition is predictable from the dependency declarations alone, so a runtime can report it when components are loaded.' Most apparent mutual dependencies decompose into finer-grained components eliminating the cycle (example: server + access controller → server-core, access-control-core, request-mediation, policy-management; the cores depend on nothing, integration components depend on both). Always possible in principle (every bidirectional interaction factors into unidirectional bindings) but integration components can grow quadratically; mitigations are engineering: package bundling, convention-based wiring, scaffold tooling. Finer granularity is itself beneficial: users load only the integration bindings they need.

### Dependency typing and versioning: nominal linking gap (open problem)
The formal model links purely by key identity, which breaks across independently developed components in two ways: interface drift (provider changes the interface behind k across versions while consumers still declare k — satisfied at the coeffect level yet behaviorally divergent) and key collision (unrelated interfaces under the same key name). 'The coeffect model provides only nominal linking (by key name) but no versioned or structural linking.' Three approaches: key namespacing (K × P, package-qualified keys — most direct, most infrastructure-coupled); peer dependencies via the host package manager — 'the approach Cordis currently adopts': component dependencies are semantically peer dependencies (a component does not bundle its dependencies but expects the runtime context to supply them), npm enforces version compatibility at install time — limited by trust in semver and single-version resolution; structural compatibility (replace key membership with a structural subsumption predicate — language-agnostic definition is hard, undecidable with bounded quantification). Unifying them while preserving the dynamic-composition guarantees 'remains an open problem.'

### Co-design with languages and operating systems
A language co-designed with the paradigm could make the context implicit again while preserving its semantics (ergonomics + safety: no context parameter threading, and a component cannot reach another component's context by mistake — an effect installed there would leak out of its lifecycle, a coeffect read there would escape its dependency specification); compile effects (emit a single state machine for a whole iterator holding inverses in its frame) and admit coeffect specifications into the type system (dependency cycles reported at compile time; structural row-type comparison instead of key identity). An OS co-designed with it would support fine-grained composition: making the coeffect specification the whole of what a component can reach, supplying declared dependencies at load and leaving nothing else reachable (as a Wasm module receives imports from its embedder) — the OS itself supplying the sandbox; providing OS resources (memory, file descriptors) as coeffects with the kernel keeping the acquisition records; and making more of the boundary revertible via transactional or copy-on-write storage.

### Related work positioning (deltas that define the design)
vs monadic effect systems (ZIO, Effect-TS): they buy tracking with a monadic embedding (program must be written inside the effect type) and discharge requirements by interpretation; 'Cordis tracks effects as an overlay over ordinary host code' and re-resolves requirements as providers come and go. vs Effekt's capabilities: Effekt makes effects visible for modular interpretation, statically at type level; Cordis for tracking and reversion at runtime. vs reversible semantics (Heunen et al. dagger/inverse arrows): they demand global invertibility by construction; Cordis 'tracks inverses at runtime and requires less of them: not that the whole computation be reversible, but that each atomic effect admit a one-sided inverse, supplied by the caller at the point of application, from which the inverse of any composite follows by composition.' vs graded modal types (Granule): static annotations over lexically fixed scopes; Cordis lifts the same notions to runtime. vs context-oriented programming: resemblance is nominal — COP layers neither track nor revert side effects and activation is not governed by dependency satisfaction. vs AOP: 'its analogue of an aspect is a coeffect: a shared point of mediation many components declare a dependence on, so that crosscutting behavior can be reshaped there without editing any of them'; declaration versus obliviousness — reach is exactly the declared surface, inspectable and governable at the configuration layer; lifecycle-integrated rather than standalone weaving. vs DSU/Erlang code_change/webpack-Vite HMR (stateful forward migration): those migrate in-memory state forward through hand-written transformation functions at quiescent points; Cordis reverts the old component's tracked effects and reapplies the new one's from a clean slate — needs no hand-written migration functions and supports unloading entirely, recovering resources. vs developer-authored recovery (OSGi callbacks, Command pattern undo, sagas, event-sourcing compensation): 'the inverse is an unenforced duty, decoupled from the operation, so that a forgotten one leaks resources silently.' React's useEffect comes closest but hooks can't compose (top-level only, no async, no iterator); Cordis effects are ordinary operations composing freely. vs statically scoped reversal (STM, reversible computing, RCCS, linear types/RAII/Rust ownership): each fixes the scope and reach of reversal statically; 'Cordis, by contrast, fixes no such scope in advance: it reverts arbitrary context operations over a component's lifecycle.' vs interposed reclamation (Nooks, shadow drivers, Akeso): platform fixes what can be recorded; a Cordis component introduces effects of its own with per-effect inverses. vs OSGi Declarative Services/iPOJO: recovery there is a hand-written synchronous callback; Cordis deactivation reverts accumulated effects and inertial Unloading runs asynchronous teardown to completion before acting on further change. vs FRP/signals: value-level vs component-level reactivity — complementary; FRP has glitch freedom, Cordis instead guarantees no single transition straddles two resolutions; a coeffect can itself carry reactive values, spanning both levels.

### Conclusion's agent-harness thesis
The paper closes by naming self-evolving agent harnesses as the compelling future validation target: 'where an AI agent generates and replaces its own harness components continuously and with little human oversight. Applying Cordis in such a setting would validate the temporal guarantees of complete recovery under rapid component replacement, as well as the spatial guarantees of dependency coordination under frequent topological change. Such validation would demonstrate the paradigm's applicability as a foundation for recoverable, coordinated, and continuous self-evolution in agent harnesses and other autonomous systems.' This is precisely the role dsh (DeepSeek Harness) plays as a Cordis-based agent harness.

## Design principles
- Two orthogonal guarantees define dynamic composition: temporal composability (a removed component's side effects are completely reverted) and spatial composability (dependencies are declared as data and reactively resolved by the runtime).
- Every effect carries an explicit inverse supplied at the point of application; the runtime tracks and composes inverses so complete environment recovery is a structural guarantee, not developer discipline — teardown is derived from loading, never written alongside it (the anti-pattern is VSCode's activate/deactivate split, which 'violates locality of concern').
- Reify effects and coeffects as runtime mechanisms rather than static type annotations: establish dynamically the guarantees static systems provide at compile time, because no lexical scope can delimit a component loaded after deployment.
- One unified context is the sole mediator: every interaction between a component and its environment passes through the context; all shared mutable state is encoded as coeffect keys; every mutation flows through a single primitive (ctx.effect) so it is automatically tracked and recovered — one write-waist for the entire system.
- Coeffect operations are themselves effects, and effects are revertible: dependency provision inherits automatic tracking/recovery for free; the two mechanisms are one machine.
- A component is (d, p, e): what it reads (inject), what it may provide, and a witnessed effect function — the two declarations are the two directions of one interface, and nothing outside them is writable or readable (confinement).
- Reactive lifecycle driven by satisfaction: a component activates only when every declared dependency is provided, deactivates when satisfaction is lost, and stays harmlessly inactive (never erroring) while unsatisfied; loading order is never orchestrated manually — it falls out of the dependency graph.
- Ordered teardown is load-bearing: a provider stops providing immediately (dependents recompute at once) but its withdrawal is guarded until every dependent has finished deactivating, and a consumer can still read the dependency throughout its own teardown (connection pools need the pool to hand connections back to).
- Transitions are inertial and resolution-coherent: once begun, a transition (and any in-flight async iteration) runs to completion before the system responds to target changes; no transition ever straddles two dependency resolutions; interruption lands only at iteration boundaries (the effect iterator is a reified delimited continuation, i.e. generators/yield).
- Failure is contained per component: a failed activation is rolled back to nothing, recorded on that fiber, never propagated to the parent, leaves siblings running, and is not auto-retried against an unchanged environment.
- Confluence as the master invariant: dynamic history leaves no trace — the quiescent state equals what a from-scratch static assembly of the final configuration would produce; this is what licenses declarative configuration reconciliation, incremental reload, and reasoning about a running system as though statically assembled.
- Provider identity, not value equality: a binding is identified by the uid of its providing fiber (fresh, never reused), so replacement always propagates and in-place overwrites are deliberately unobservable — to publish a change, withdraw and reinstall.
- Effects carry the commuting part of a computation, coeffects the order-sensitive part: keys whose operations commute (registration tables) make components independent and revertible in any order; where order matters it must be surfaced as a declared coeffect, imposing activation order structurally.
- Recovery is exact only up to observational equivalence, assembled per-key from what each key's own operations can distinguish — commutativity of a key is an obligation on its provider, not its consumers.
- Isolation realms give runtime ad-hoc polymorphism (same key, different values in different contexts — tenants, tests, sandboxes); interception layers cross-cutting metadata on access with the enclosing context able to override the component's own declaration — governance from outside without modifying the governed.
- Dependency declarations are capability requests and the context proxy is the capability mediator: undeclared access fails structurally; the complete capability set is known before a component runs, so an orchestrator can review and approve it at load time; interception refines it to per-call policy, adjustable at runtime without reload; true sandboxing of untrusted code is explicitly delegated to an execution boundary outside the language, bridged back in as an ordinary attenuated fiber.
- Meta-framework discipline: prescribe no domain — 'its sole responsibility is to supply universal dynamic composition semantics'; the host application contributes only domain vocabulary and every feature is a plugin over the context primitives (validated by Koishi's 4000+ plugins and adopted wholesale by dsh's 'everything is a plugin').
- Orchestration is declarative and reconciled: the desired composition lives in a persistent configuration tree; the loader applies least-disruptive per-field changes; hot module replacement needs no developer-annotated accept boundaries because a fiber already bounds all of a component's effects, and reload is transactional (never a half-reloaded state).
- Semantics is reactive-only and scheduler-free: no rule mentions a scheduler, so every guarantee holds for any scheduling policy a runtime adopts.
- Dependency cycles are inert, not fatal: they leave the participants inactive and are predictable from declarations alone at load time (unlike deadlock); resolve them by decomposing into finer unidirectional components — cores depend on nothing, integration components depend on cores.
- Draw the system boundary per location: acquisitions (open/malloc/fork) are revertible effects inside the boundary; emissions cross it and can only be withheld or compensated — compensation composes LIFO like inverses but weakens the equivalence the metatheory must be re-proved against.
- Nominal key linking is a known gap (interface drift, key collision); Cordis currently leans on host package-manager peer dependencies for versioning, with namespacing and structural compatibility as the alternatives — a unified model is an open problem.
- The paradigm's stated destiny is self-evolving agent harnesses: complete recovery under rapid component replacement plus dependency coordination under frequent topological change is offered as 'a foundation for recoverable, coordinated, and continuous self-evolution.'

# architecture-doc

## Key points
### Cordis foundation — everything is a plugin
Cordis is the vendored plugin framework under dsh: plugins contribute services, typed events, and reversible effects to a shared context. Every part of the product is a plugin — explicitly including the model adapter, the tool registry, the session log, and the agent loop itself — so every part is replaceable from configuration. There is no privileged core to patch: you extend dsh by mounting a plugin beside the others, and registrations are effects that unwind when their plugin unloads. Cordis also powered the Koishi chatbot framework for four years before becoming dsh's kernel.

### Plugin model (lifecycle + DI)
A plugin is an object that implements Service: either a function with optional `inject` and `apply(ctx)` fields, or a `Service` subclass whose lifecycle Cordis mounts into the current context. A context is a repository of services: a service claims a stable `ctx.<key>` (ctx.tools, ctx.llm, ctx.sessions); other plugins find services via key instead of importing a concrete implementation. Dependency is declared via `inject`: a plugin that names required services waits until those services exist, so load order is expressed through service requirements rather than manual boot sequencing. Registrations (prompt sections, tool schemas, adapters, providers, listeners) are installed through `ctx.effect()` or `ctx.on()` so reload and teardown unwind them predictably.

### Profiles and bundles — boot composition
A running dsh is a plugin tree composed at boot from ordered layers. A profile is a named composition stored in the Harness home: it lists the bundles it stacks, holds any out-of-tree plugins it installs, and keeps the user's own cordis.patch.yml; `web` and `headless` ship as templates. A bundle is a distribution format for Cordis config rows and the code they mount, designed so whatever it inserts stays patchable by the layers above it. Each declares itself in its own package.json under a `dsh` field: `dsh.profile` lists a profile's bundles, `dsh.bundle` points at a bundle's patch file.

### Layer application order and patch semantics
Layers apply to an empty entry list in this order: each bundle in the profile's listed order, then the profile's cordis.patch.yml, then the home-level one, then any `--patch` overlay. A patch targets a row by id and replaces its whole config, or inserts new rows. `dsh --profile web --dump-config` prints the tree your machine actually boots, and any row it prints can be replaced by a patch of your own. dsh-base is the first layer of every profile (model adapters, tools, persistence, sandbox and approval policy, settings, credentials, telemetry); dsh-web-app adds the browser application; dsh-headless adds a one-shot runner with no server at all.

### Core packages and their ctx keys
core/session owns the append-only SessionEvent log and in-memory store (ctx.sessions). core/system-prompt owns prompt-section and tool-schema assembly (ctx.systemPrompt). core/tools owns the scoped tool registry and guarded execution pipeline (ctx.tools). core/agent owns the Agent interface, live registry, and agent/* events (ctx.agents). core/agent-loop is the default driver implementing that interface (ctx.agentLoop) — note the loop is a separate, swappable package from the Agent interface. core/scope is the per-agent scoped-registration primitive (a library, no ctx key). llm/llm owns the message and stream vocabulary plus the adapter seam (ctx.llm).

### Three event domains
Events are the extension points, and picking the right domain is the first decision in most changes. (1) Session events are durable facts appended to the log and broadcast through session/event — use one when the fact must survive a reload. (2) Agent events (agent/*) carry a live Agent — inbox, step, status, request, validation, continuation — used to observe or intercept work in flight. (3) Capability events attach policy and adapters to a seam (fs/*, tools/*, telemetry/*) without importing the loop. A generated event map (event-producer-consumer.md) lists every event's producers and consumers.

### Turn flow / agent loop structure
A step is one model request plus the tools it calls. A turn is zero or more steps: it opens before its first input is claimed and closes once nothing is owed. Flow: turn/start → claim next-step input plus one queued message → assemble prompt sections + tool schemas → agent/pre-step (reject | enter(messages); reject or a first enter rewritten empty closes the turn with no step) → step/start → append entered messages as user/message → derive model history from the log → agent/request → llm/stream → assistant/chunk* → assistant/message → tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* → step/end; if tools owe another request or next-step input arrived, claim and run the next step; then agent/turn-stopping → turn/end.

### Durable vs live events in the turn; waterfall points
turn/*, step/*, user/message, assistant/*, and tool/* are durable session events; the rest are live extension points across the three domains. agent/pre-step, agent/request, llm/stream, and the three tools/* events are waterfalls whose listeners must call next() to delegate; agent/turn-stopping is serial and has no next(). agent/pre-step decides what the model sees: listeners may rewrite the claimed messages or reject them outright; a rejected or empty first claim still closes a durable turn that spent no step, so the log records the attempt. Each step reads the prompt sections and tool schemas that plugins registered.

### Inbox model
Input reaches the driver through one inbox. Some messages wake it immediately; injected context waits in the inbox until another message does. Model-facing context is added via agent.inject() and lands in the next admitted request — injection is passive, never itself waking the loop.

### Session log as the single source of model context
The session log is the source of the context the model sees. deriveMessages() projects model history from it, and raw assistant/chunk events preserve replay and UI fidelity. Fork, resume, transcripts, telemetry, and persistence all derive from this one stream. Sessions can be forked live via ctx.sessions.fork(source, boundary?, childSessionId?).

### Invariant: model-visible means logged
Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it. Consequence: a new model-visible input requires a new session event — extend SessionEventMap and render from the log. This is the doc's only bolded invariant and the backbone of replay/fork/persistence.

### Capability seams — three-role contract
A seam is a swappable capability with three roles: a Service Definition declaring the interface, a Service Provider implementing it, and a Consumer using it (commonly a model-facing tool). A package may combine roles, but one role alone is not a seam; adding a capability means designing all three. There is a dedicated capability graph document (capability-seams.md).

### Seam payoff — one swap moves the whole product
Seams are why one provider swap changes the whole product. Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks. Subagent providers vary just as widely behind one interface — from a fresh child agent to a delegated turn in another product entirely (the packages tree shows subagent-acp, subagent-claude-code, subagent-codex, subagent-dsh-sdk, subagent-fork-in-process, subagent-spawn-in-process behind one subagent interface).

### Experimental Agent Teams
A private opt-in coordination seam on ctx.agentTeams, with a durable roster, task board, and mailbox layered over continuable subagents. Lives in packages/experimental.

### Extension map — where new behavior goes
New behavior attaches to a documented extension point, and 'changing the loop itself updates this map' (the map is a maintained contract). Highlights: model provider → adapter on ctx.llm; model-facing capability → register on ctx.tools, its schema joins prompt assembly automatically; per-session capability set → compose an agent preset, where a service row needs an `isolate` realm; shell execution → ctx.shell backend (the local one spawns through ctx.subprocess); persistent terminals → ctx.terminals backend + dsh-tool-terminal; human command → ctx.commands, dispatching without a model turn; background work → ctx.jobs with job_* tools to collect or stop it; filesystem access/policy → ctx.fs provider or fs/* events; process confinement → ctx.sandbox backend, consumers wrap argv before spawning; interception → agent/* or tools/* events, agent/turn-stopping stops a turn; UI/editor integration → drive ctx.agents and render from session/event; Web Client Chat node → ConversationNodeDefinition + keyed renderer; durable session state → extend SessionEventMap, render and replay from the log; session titles → the sole ctx.sessionTitle provider (a deliberately single-provider seam); same-session objective → ctx.goals, continued through agent/*; scoping a registration to one agent → that agent's agent.ctx.

### Event dispatch modes (Cordis)
Four dispatch modes, each event permanently bound to one: emit (not awaited, listeners observe in registration order, no return value), waterfall (not awaited, registration order, has return value), parallel (awaited, all listeners in parallel, no return), serial (awaited, registration order, has return). The dispatch mode is part of the event's public contract; new harness events document it with an @mode tag so the generated catalog can check declarations against dispatch sites — the docs are machine-checked against the code.

### Waterfall semantics — around-middleware
ctx.waterfall is around-middleware: a listener receives (...args, next); call next() to delegate the possibly-wrapped result to the next service, return without next() to short-circuit; values propagate through next()'s return value. Cooperative listeners usually mutate a shared request or decision object and then delegate; a listener can also replace the result entirely, and downstream listeners only see the replaced result. prepend:true is reserved for listeners that must run before ordinary registrations. For single-decision events, short-circuiting is the design: a policy listener returns without next() when it owns the decision, while a listener that only annotates or observes must delegate.

### Loader configuration and dynamic config
@deepseek-ai/cordis-plugin-include parses !!js into expression nodes. The loader interpolates an entry's config after declared injections activate, evaluated against that plugin's context (ctx.serviceName), and its disabled field at every mount decision against the loader context; Include preserves nested row expressions until target activation. Other entry metadata stays literal. Overlays are the recommended mechanism when the environment selects plugins.

### Practical placement and teardown rules
Encapsulate behavior into plugins: a tool pipeline event belongs to ctx.tools, model streaming belongs to ctx.llm, live agent coordination belongs to ctx.agents. Prefer events for interception and policy; prefer service methods for direct capability calls. Every registration should have a disposer, either returned from ctx.effect() or via a Cordis helper; if teardown order matters, keep the related work in one effect so disposal unwinds in the intended sequence.

### Repo shape corroborating the architecture
The packages/ tree mirrors the seam doctrine: nearly every capability family is a directory holding an interface package plus sibling providers (fs + fs-local/fs-sandbox/fs-e2b, shell + bash-local/bash-sandbox/pwsh-*, session-persistence + jsonl/sqlite, storage + json/sqlite, web + web-fetch-http/web-search-deepseek/exa/perplexity, llm + llm-deepseek/llm-pi-ai/llm-retry, subagent + six providers, compaction, spill, jobs, schedule, goal, plan, skill, mcp, lsp, terminal, sandbox incl. sandbox-windows-acl and a native landlock-run helper). Cordis itself plus cosmokit/hmr/loader/schemastery are vendored under vendor/ with a documented sync procedure. Docs include a subsystems/ reference per seam, an invariants doc, a postmortem directory, generated catalogs (config, tools, persistence, event producer/consumer, module graph, graph atlas), and the repo keeps bilingual (en/zh) agent notes.

## Design principles
- Everything is a plugin: every product capability — model adapter, tool registry, session log, the agent loop itself — is a plugin, so every part is replaceable from configuration.
- No privileged core: you never patch a core to extend the system; you mount a plugin beside the others. The kernel (Cordis) does exactly one job — mount, unmount, track dependencies.
- Registrations are reversible effects: every registration (tool schema, prompt section, adapter, listener) is installed through ctx.effect()/ctx.on() and unwinds predictably on unload/reload; every registration should have a disposer, and related work shares one effect when teardown order matters.
- Dependency injection by service key, not import: plugins declare needs via `inject` and discover services at stable ctx.<key> addresses; load order emerges from service requirements, never manual boot sequencing.
- Composition is layered and patchable: a running system is a plugin tree built from ordered layers (bundles → profile patch → home patch → CLI overlay); anything a bundle inserts stays patchable by the layers above it, and any row the boot dump prints can be replaced by a user patch.
- Model-visible means logged (runtime-asserted invariant): anything that reaches a model request must be reconstructable from the append-only session log; new model-visible input requires a new session event type. The log is the single source of model context, and fork/resume/transcripts/telemetry/persistence all derive from it.
- Events are the extension points; picking the right domain (durable session fact vs live agent event vs capability seam event) is the first design decision of most changes.
- An event's dispatch mode (emit/waterfall/parallel/serial) is part of its public contract, documented with @mode and machine-checked against dispatch sites.
- Waterfalls encode policy: around-middleware where delegation via next() is cooperation and returning without next() is owning the decision; for single-decision events short-circuiting is the design.
- A seam is three roles — Service Definition, Provider, Consumer; one role alone is not a seam, and adding a capability means designing all three. Seams are why one provider swap changes the whole product.
- Shared execution world: filesystem and subprocess providers point at the same world, so retargeting to a remote sandbox moves Bash, PTY, and LSP together with no provider forks.
- One inbox, passive injection: all input reaches the driver through a single inbox; injected context never wakes the loop, it rides the next admitted request.
- Failed attempts are still facts: a rejected or empty first claim still closes a durable turn with no step, so the log records the attempt (auditability over tidiness).
- Docs are load-bearing contracts: 'New behavior attaches to a documented extension point. Changing the loop itself updates this map' — plus generated catalogs (events, config, tools, persistence) checked against code.
- Prefer events for interception and policy; prefer service methods for direct capability calls.
- Interface and default implementation are separate plugins even at the center: core/agent (the Agent interface) vs core/agent-loop (the default driver), so even the loop is swappable.
- Scoped registration: capabilities can be scoped to a single agent via agent.ctx, and per-session capability sets are composed as agent presets with isolate realms.

### Identity and status
DeepSeek Harness (`dsh`) is DeepSeek AI's open-source agent framework, MIT-licensed, in developer preview with breaking changes expected. Tagline: 'DeepSeek Harness: Everything is a Plugin.' Built on Cordis (github.com/cordiverse/cordis), a composability kernel whose theoretical grounding is the paper 'A Programming Paradigm for Spatiotemporal Composability' (github.com/cordiverse/paper). Entry point: `npx @deepseek-ai/dsh web` → Web UI at 127.0.0.1:3080. Community plugins are tagged `dsh-plugin` on GitHub.

### Monorepo top level

The monorepo also ships AGENTS.md and CLAUDE.md at packages/ level (agent-consumable dev docs are first-class).

### packages/ decomposition — full enumeration
50 package groups under packages/<group>/<pkg>/ (naming @deepseek-ai/dsh-<pkg>), ~40+ npm packages across 25 groups: acp, api, attachment, boot, bundle, client, code-runtime, compaction, context, core, credentials, e2b, examples, experimental, extensions, feedback, fs, goal, guard, hooks, host, identity, interaction, jobs, llm, lsp, mcp, plan, preset, runtime-diagnostics, sandbox, schedule, sdk, session, session-query, settings, shell, skill, spill, storage, subagent, subprocess, terminal, test-support, todo, typert, util, web, workflow, workspace. ### What the kernel keeps vs what is a plugin
The kernel is Cordis itself (external dependency, not a package in this repo). It keeps ONLY: the context as a service repository (stable keys like ctx.tools/ctx.llm/ctx.sessions), plugin mount/unload lifecycle, dependency resolution via `inject` (load order is implicit from service requirements, no explicit boot sequencing), four typed event dispatch modes (emit / waterfall / parallel / serial), reversible effect registration (ctx.effect()/ctx.on() unwind on unload), and per-agent scoping. EVERYTHING else is a plugin: the model adapter, tool registry, session log, sandbox, policy, settings, credentials, telemetry, and the agent loop itself — 'no privileged core to patch: you extend dsh by mounting a plugin beside the others', 'every part is replaceable from configuration.'

### core/ group — the product API spine
core/ owns 'the session log, system-prompt assembly, tool registry, agent vocabulary, deployment-default model selection, and concrete loop that form the harness's default control spine.' Seven sub-packages: scope/ (scoped-context registration primitive — a library, no ctx key), session/ (event-sourced session log, ctx.sessions), system-prompt/ (prompt + tool-schema assembly registry, ctx.systemPrompt), tools/ (scoped tool registry + execution pipeline, ctx.tools), agent/ (agent interface/registry/event vocabulary, ctx.agents), agent-default-model/ (deployment default used only when a session has no selection of its own, ctx.agentDefaultModel), agent-loop/ (the default concrete driver, ctx.agentLoop). Deliberately NOT in core: runnable compositions — 'Runnable compositions belong to examples/agent-spine-demo; this group owns only the swappable spine pieces.'

### Loop is a swappable default, not the core
Key boundary: 'agent owns the public contract, while agent-loop is its default implementation; extension plugins depend on the seam so the driver remains swappable.' UI, hook, and tool plugins use the abstract agent interface, never the concrete loop. This is the strongest expression of the no-privileged-core doctrine — even the agent loop is one provider behind a seam.

### Seam pattern (component-boundary doctrine)
A 'seam' = the complete capability as three roles: Service Definition (interface ownership), Service Provider(s) (implementations), Consumer(s). Glossary insists: 'The seam is the complete capability, never one role.' Services are classified three ways: seams (swappable, multi-provider), core services (single-owner state/orchestration that dependents 'must respect but cannot replace'), and bundle/composition points. Packages split into definition/provider/consumer sub-packages precisely when the roles evolve independently. Companion plugins (e.g. fs-observation-policy) contribute through event gates rather than direct integration.

### Shared execution world
All providers within an execution seam inhabit one process/session world, so one provider swap moves the whole product: 'Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks.' E2B filesystem+subprocess providers 'inhabit the same Linux runtime' via a ctx.e2b core service. Deployment chooses backends at composition time; application code is unchanged.

### Composition model: Profiles / Bundles / patch layers
Profiles are named compositions stored in the Harness home listing bundled dependencies; Bundles are the distribution format for Cordis config rows + code. Layers apply in strict order: profile bundles → profile patch file → home-level patch → CLI overlays; each config row is patchable by layers above. Core bundles: dsh-base (model adapters, tools, persistence, sandbox, policy, settings, credentials, telemetry), dsh-web-app (browser app), dsh-headless (one-shot runner, no server). preset/ builds per-session agent composition from cordis.yml files; bundle/ makes installable `dsh --profile` patch layers.

### Lifecycle: turn/step model
A step = one model request + the tool executions its response causes; a turn = zero or more steps ('one drain of admitted input in a session, ending after the model and its tools stop or a terminal policy intervenes'); a round = an outer policy iteration containing a turn (round counters belong to that policy). Flow: turn/start → claim next input + queued message → assemble prompts + tool schemas → agent/pre-step [reject|enter] → step/start → append user/message → derive history from log → agent/request → llm/stream → assistant/chunk* → assistant/message → tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result* → step/end → agent/turn-stopping → turn/end.

### Two event planes: durable vs live
Durable session events (turn/*, step/*, user/message, assistant/*, tool/*) are the replay facts on session/event; live extension points ride agent/* channels: waterfalls (agent/pre-step, agent/request, llm/stream, tools/*) require next() delegation, agent/turn-stopping is serial. Explicit guidance: 'SDK users that need replayable transcript data should consume session/event; agent/* is the live coordination API for queue/status, prompt interception, request construction, steering, continuation, and errors.' assistant/message records EVERY successful provider call including content-less/max-tokens finishes; empty content stays out of derived history but the durable event keeps usage + sourceEventSeqs.

### Master invariant: model-visible means logged
'Model-visible means logged.' Anything reaching a model request must be reconstructable from the session log; new model-visible input requires a new session event type. Replay fidelity, forking, resumption, transcripts, and persistence all derive from the one durable stream — the append-only session log is the single source of truth.

### Per-agent scoping model
scope is 'the unit of per-agent registration: a contribution (tool, prompt section, variable, restriction, listener) is either global (visible to every agent) or scoped (owned by exactly one scope key)' — two flat levels, no inheritance to subagents. agent.ctx registrations are 'scope-visible AND scope-lifetime (one fact drives both)'. Shadowing = most-specific-wins within a scope only. Restrictions compose the global tool set by intersection; filtered tools are absent from prompts AND refuse execution. A 'setup window' exists after scope+agent objects exist but before the agent/session is published. Lineage (parent/child) is carried as metadata and 'never affects visibility.'

### Capability families (execution)
subprocess/ = service definition + local process-tree provider; shell/ = bash executor seam + local impl + model-facing tool (providers bash-local, bash-sandbox, pwsh-local behind ctx.shell); terminal/ = persistent PTY capability with owner-scoped sessions; code-runtime/ = code execution service + worker-thread provider + Code Mode consumer; fs/ = filesystem seam + local impl + file tools + bash-backed discovery; lsp/ = LSP seam + stdio provider + lsp tool; e2b/ = E2B remote-sandbox providers (POC) that satisfy the same fs/subprocess interfaces.

### sandbox/ — confinement family
Applies 'per-session confinement policy to process execution' for same-world subprocesses via three packages: sandbox/ (core service + shared escalation vocabulary, ctx.sandbox), sandbox-local/ (platform backends: bwrap/Landlock/Seatbelt), sandbox-policy/ (durable per-session policy resolution, ctx.sandboxPolicy). Sharp boundary: 'isolated environments replace complete capability implementations instead of registering here' — i.e. heavyweight isolation (E2B) swaps the whole execution world at the seam rather than being a sandbox backend. Fail-closed error behaviors documented in docs/subsystems/sandbox.md.

### session/ + session-query/ — durable data plane
session/ owns durable persistence with semantic checkpoint policies, log-derived projection units, title generation, and OpenTelemetry telemetry (FULL/FEEDBACK_ONLY/DISABLED). Sub-packages: session-persistence (write coordination service), session-checkpoint-policy (semantic durability checkpoints wrapping LLM/tools contexts), session-persistence-jsonl, session-persistence-sqlite (packed physical chunk rows), session-projection(+cache), session-stats, session-title(+two LLM providers + deterministic fallback). ### skill/ family
Provider-neutral catalog + loader for reusable agent instructions, kept 'outside the core control spine.' skill/ (registry, ctx.skills), skill-filesystem/ (local discovery), skill-badge/ (bundled optional skill), tool-skill/ (catalog publishing + model-facing loader on ctx.tools). The system 'can use local, embedded, or remote providers without changing the model-facing contract.'

### subagent/ family
Three layers: core infra (registration, delegation mechanics, continuation semantics on ctx.subagents), drivers (in-process fresh spawn, fork-based init inheriting parent history, out-of-process via ACP / Codex servers / Claude Code SDK / Harness TS SDK — foreign harnesses mount as dormant profile-bundle providers), and tools (tool-subagent delegation, tool-subagent-control child messaging/enumeration, tool-subagent-report parent-bound status streams). Children run in isolated scopes with private runtime closures; removing a provider package 'withdraws only that provider and its private runtime closure on the next Profile start.'

### llm/ family
llm/ owns the abstract LLM service, content-block vocabulary, StreamChunk protocol and stream-chunk assembler (ctx.llm); adapters (llm-deepseek direct, llm-pi-ai multi-provider, plus a Replay adapter) register provider routes on the seam; token-meter/ (replay-aware token measurement, ctx.tokenMeter) and llm-retry/ (provider-scoped retry listening to agent/request-error) 'remain separate consumers.' The agent loop and compaction call provider-neutral operations only.

### interaction/ — human-collaboration plane
Five packages: commands/ (ctx.commands — slash 'human commands' executed by human-facing adapters 'without becoming a model message'), user-approval/ (one-shot approval decisions, ctx.approval), permission-presets/ (user-facing permission presets + persistence), user-questions/ (provider-neutral Q&A seam), tool-ask-user/ (exposes questioning to the model). Doctrine: the group layers human collaboration 'through existing agent and session contracts rather than changing the loop.' Interactive apps provide concrete adapters; automation delegates to the acp/ transport.

### extensions/ — agent runtime self-modification
'Model-facing tools over the live cordis runtime the agent itself runs inside.' The agent can inspect live plugins/services and define, mount, and later retract new packages without restart (hot-load/unload). cordis-host-runner/ keeps a definition registry and sandboxes model-written plugin code in Node's `vm`; cordis-client-runner/ evaluates browser-half definitions; tool-cordis/ exposes inspection + dynamic-package manipulation as tools; ui-cordis/ gives operational panels + read-only inspection for auditability. Invariants: runtime inspection read-only by default; browser-half stays separate from host aggregate ('each face keeps its own compiler program'); dynamic packages integrate through the normal cordis service architecture (same seams, same reversible effects).

### Goal / schedule / plan / workflow / jobs — long-horizon state
goal/ = 'one durable completion objective attached to an existing session' with revisioned active/paused/blocked/complete phases and a goal-round cap; goal activation (armed/disarmed) is process-local and 'deliberately absent from durable replay' (live authority vs durable fact separation again). schedule/ = session-local scheduled follow-ups. plan/ = plan collaboration state with 'direct entry command and reviewed exit.' workflow/ = seam + worker-thread engine + model-facing workflow/ralph tools. jobs/ = background-job runtime with model-facing job control tools. Ralph loop = 'one foreground fresh-agent workflow run toward an immutable objective... composed from workflow and subagent primitives'; each Ralph round is a fresh child session with NO parent or prior-child conversation seed; rounds pass a normalized bounded structured handoff (status, summary, evidence, next steps, blocker text).

### Context-budget & hygiene plugins
compaction/ = compaction service definition + basic provider + command consumer; spill/ = storage seam + tool-result spill policy (large tool results spilled out of context); guard/ = loop-hygiene guards (repeat-call reminders, deadline enforcement); context/ = model-visible request context (workspace instructions, time context); todo/ = the model-facing todo_write tool. All of these are ordinary plugins — context management is not baked into the loop.

### Persistence & config plugins
settings/ = user-settings seam + file-backed provider; credentials/ = credential reference/record seam + env-over-.env provider — consumers resolve per-operation 'so credential rotation reaches the next request immediately'; storage/ = non-session storage hub + JSON and SQLite backends registering side-by-side, with 'data forms' translating typed operations into opaque key-value primitives; workspace/ = workspace entity; attachment/ = durable attachment identity, validation, content-addressed storage; identity/ = shared anonymous identity.

### Interface / transport layer
sdk/ = out-of-process runtime SDK (JSON-RPC protocol + TS client/server); acp/ = automation-only Agent Client Protocol server; api/ = remote backend-for-frontend assembly + Typert RPC gateway; typert/ = type-graph generation, artifact loading, runtime registry; host/ = web-GUI host (API gateway + HTTP routes); client/ = web-GUI browser (shell, wire, object services, slots, ui plugins); boot/ = shared app-bin boot glue; hooks/ = hook bridges + shared Claude Code/Codex wire-protocol library (interop with competing harnesses is a plugin); mcp/ = MCP integration; runtime-diagnostics/, feedback/, util/ (zero-dependency, 'harness-dep-free' branded types/path/timeout/retention helpers).

### Python SDK design
python/sdk launches the matching bundled runtime (python/sdk-runtime carries the binaries) as a subprocess, speaking newline-delimited JSON-RPC over stdio. Stated split: 'The client selects the channel and supplies default configuration; the runtime itself always requires an explicit configuration' — client convenience vs runtime determinism. Python is a thin out-of-process client to the TypeScript harness, not a reimplementation.

### Runtime invariants machinery (self-verifying architecture)
Invariants are themselves a service/plugin with mechanical verification: selection invariant (enabled + allowlist match + no blocklist match; 'a blocklist match overrides an allowlist match'; malformed entries throw at startup instead of being skipped); name-reservation invariant ('two plugins can never silently claim the same package name' — reservation holds even when filters keep an installer inactive); failure-attribution invariant (InvariantError with code:'INVARIANT' + packageName, 'attributable without the registry importing any product package'); companion-contract invariant — every package ships an invariant companion, and 'a companion installs a check only when its package owns an observable event or mutable-data relationship; otherwise it exports an empty installer whose leading comment starts `No runtime invariant:` and explains, package-specifically, why nothing is checkable', mechanically enforced by `pnpm run verify-package-invariants` which rejects generated markers, unexplained empty installers, and installers that ignore the reporter.

### Defensive patterns doctrine (docs/defensive-patterns.md)
Seven mandated patterns: (1) report orthogonal outcomes independently ('Surface each independent fact (timedOut, signal, exitCode) on its own; never nest one flag's report inside another's branch'); (2) honor public contracts on both sides — normalize provider/middleware/consumer errors into one canonical failure mode at the API boundary; (3) async state is not synchronous state — 'Never treat agent/status or whenIdle() as the result of one follow-up', handle the nothing-to-wait-for branch explicitly; (4) dispose must reach quiescence — 'Make cleanup async and await the children's exit (kill → await done)', no orphans; (5) contain callback exceptions in the dispatcher — 'one bad subscriber never breaks core lifecycle'; (6) never hand untrusted output ambient environment or predictable paths — 'Spawned commands get a scrubbed env (drop *KEY*/*SECRET*/*TOKEN*/*PASSWORD*)', 0700 dirs, random names, exclusive owner-only opens; (7) unlink link-shaped paths — lstat-then-unlink so link targets are never followed during removal.

Package READMEs are mandated to cover purpose, APIs, extension points, and 'Model Experience' (with specified omission allowlists) — docs treat the model as a first-class reader.

### Documentation-stated dependency rule
The extension/composition rule from packages/README.md: 'Extension plugins depend on Service Definitions, never concrete providers.' The agent loop is swappable; UI, hook, and tool plugins use the abstract agent interface; only composition bundles may depend on spine plugins. Consumers depend on seams, not implementations; core services maintain invariants dependents must respect but cannot replace.

### Error/authority details in the lifecycle
agent/pre-step is a waterfall whose 'returned decision is authoritative; listeners wrapping next() preserve downstream messages unless replacement is intentional.' agent/request-error is a waterfall allowing retry decisions or error preservation, with optional pruning between failed step closure and turn completion. Tool executions are classified by execution mode with barriers and bounded pools; tools/pre-execute → execute → post-execute are ordered phases within barriers.

## Design principles
- Everything is a plugin — 'every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so every part is replaceable from configuration'; there is 'no privileged core to patch: you extend dsh by mounting a plugin beside the others.'
- The kernel keeps only composition mechanics (context/service repository, inject-driven implicit load order, typed events, reversible effects, scoping); all product behavior — including the loop — lives in swappable plugins.
- Seams over implementations: a capability = Service Definition + Provider(s) + Consumer(s); 'Extension plugins depend on Service Definitions, never concrete providers'; packages physically split into the three roles when they evolve independently.
- Contract/default split: 'agent owns the public contract, while agent-loop is its default implementation' — the default driver is just one provider behind the seam it defines.
- Shared execution world: execution providers (fs, subprocess, shell, PTY, LSP) inhabit one world, so a single provider swap relocates the entire execution surface 'with no provider forks'; heavyweight isolation replaces whole capability implementations rather than registering as a sandbox backend.
- Model-visible means logged: anything that reaches a model request must be reconstructable from the append-only session event log; new model-visible input requires a new durable event type; replay, forking, resumption, and transcripts all derive from the one stream.
- Two planes, never confused: durable session events are replay facts; agent/* events are live coordination — process-local authority (e.g. goal activation armed/disarmed) is 'deliberately absent from durable replay.'
- Reversible registrations: all contributions install through ctx.effect()/ctx.on() 'so reload and teardown unwind them predictably' — clean unload is a first-class invariant, which is what makes runtime self-modification (mount/retract model-written plugins) safe.
- Composition by ordered patch layers: profile bundles → profile patch → home patch → CLI overlays, every config row patchable by the layer above; deployment chooses providers at composition time and application code never changes.
- Per-agent scope discipline: contributions are global or owned by exactly one scope key, two flat levels, no inheritance to subagents; scoped registration is 'scope-visible AND scope-lifetime (one fact drives both)'; restrictions intersect the tool set and filtered tools both vanish from prompts and refuse execution; lineage is metadata and 'never affects visibility.'
- Human collaboration layers on top, never into, the loop: the interaction plane works 'through existing agent and session contracts rather than changing the loop'; human commands execute 'without becoming a model message.'
- Self-modification is governed, not forbidden: the agent gets tools over its own live runtime, but model-written code runs in a vm sandbox, inspection is read-only by default, dynamic packages ride the same seam/effect machinery, and a UI surface keeps them auditable.
- Invariants are code, not prose: every package ships a runtime-invariant companion or an explicitly justified 'No runtime invariant:' empty installer, mechanically verified in CI; violations carry attributable InvariantError codes without the registry importing product code.
- Fail closed and independently observable: orthogonal outcomes reported at top level, one canonical error contract at public boundaries, teardown awaits quiescence, dispatchers contain subscriber exceptions, subprocesses get scrubbed env and unpredictable private paths.
- Prefer events for policy and interception; use service methods for direct capability access; 'encapsulate behavior into plugins: a tool pipeline event belongs to ctx.tools, model streaming belongs to ctx.llm.'
- Fresh-context iteration as a primitive: the Ralph loop composes workflow + subagent seams into fresh child sessions with no inherited conversation, connected only by a bounded structured handoff — long-horizon work via composition, not a special loop.
- Docs are load-bearing and model-facing: package READMEs must document purpose, APIs, extension points, and Model Experience; the repo ships AGENTS.md/CLAUDE.md and per-subsystem docs in three languages.

## Key points
### Project identity & status
DeepSeek Harness (dsh) is an MIT-licensed, Node.js-based open-source agent harness in developer preview ('THERE WILL BE COMPATIBILITY-BREAKING CHANGES'). Built on the vendored Cordis plugin framework; the README grounds the design in 'A Programming Paradigm for Spatiotemporal Composability'. Plugin ecosystem discoverable via the dsh-plugin GitHub topic.

### Core architecture: everything is a plugin
'Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so every part is replaceable from configuration.' 'There is no privileged core to patch: you extend dsh by mounting a plugin beside the others.' Registrations are reversible effects that unwind when plugins unload — HMR and disposal come free because listeners/registrations are Cordis effects.

### Fundamental invariant: model-visible means logged
'Anything that reaches a model request must be reconstructible from the log, and a runtime invariant asserts it.' Governs all data-model decisions: new model-visible inputs require extending SessionEventMap; requests are deep-frozen and their content is 'a pure function of the session log'; a logged EpochHeader records call config, rendered prompt, and tool ordering so requests are fully reconstructable without re-running adaptation logic.

### Cordis kernel primer
Plugins are functions/Service subclasses with optional inject and apply(ctx). Context is a service repository where plugins claim stable keys (ctx.tools, ctx.llm, ctx.sessions); services are accessed by key, never direct import (loose coupling). Load order emerges implicitly from inject dependency graphs, not manual sequencing. Every registration (prompt sections, tool schemas, adapters, listeners) is installed via ctx.effect()/ctx.on() for predictable teardown. Events are typed via TS declaration merging.

### Cordis event dispatch modes (deliberate taxonomy)
emit = synchronous fire-and-forget notification; parallel = awaited fan-out where every listener gets an independent chance (used for the session/flush durability checkpoint); serial = awaited in order until one bails (agent/turn-stopping); bail = sync serial; waterfall = around-middleware with a next() continuation — calling next() delegates, omitting it vetoes/short-circuits (agent/pre-step, agent/request, agent/request-error, tools/pre-execute, tools/execute, tools/post-execute, llm/stream, system-prompt/assemble). The microkernel note chose pure Cordis events over a koa-compose middleware stack or a phase state machine because Cordis already provides dispatch, disposal, and reload semantics.

### Cordis Context/Fiber/Service API
Context is a proxy: property reads go through the service resolver; extend()/isolate()/intercept() create scoped children without mutating the parent. ctx.provide() registers fiber-owned services; only providing fibers may modify their services. isolate(name,label) creates independent service scopes; same labels JOIN realms across calls. A Fiber is 'one loaded plugin instance: its lifecycle state, validated config, and registered effects'; disposers run in reverse registration order (LIFO), may be async, and unloading awaits them; assertActive() throws CordisError('INACTIVE_EFFECT') on dead contexts. Service subclasses self-register as ctx.<name> via super(ctx,name).

### Three event domains
Session events = durable facts appended to the log, broadcast on session/event, survive reload — SDK/replay consumers use these. Agent events (agent/*) = live layer carrying agent instances (inbox, step, status) for observing/intercepting in-flight work. Capability events (fs/*, tools/*, telemetry/*) = attach policy/adapters to seams without importing the loop. The agent-lifecycle page states the split 'keeps durable replay facts on session/event and live control/status on agent/*'.

### Turn/step lifecycle
A step = one model request plus its tool calls; a turn = zero or more steps, opening before the first input claim and closing when nothing remains owed. Flow: turn/start → claim input → agent/pre-step (waterfall; compaction pressure checkpoint, decision 'authoritative') → step/start → message assembly → agent/request (waterfall) → llm/stream → tool calls (tools/pre-execute → tools/execute → tools/post-execute) → step/end → repeat or close turn. Steering/injected context 'pass through the same waterfall after a later claim operation takes their next-step batch'. Retry recovery reopens a fresh retry turn only when 'pruning or summarization advances the surface replacement generation'; otherwise the original error stays authoritative. agent/request-error is the canonical context-overflow marker.

### Agent handle & inbox model
ctx.agents.create()/resume() return AgentHandle; the factory provider is a structural owner ('provider unload stops and drains every live handle it made'). Agent exposes id (shared SessionId), options, session, inbox, status; control: cancel(), whenIdle(), runMaintenance(); delivery: send(), followup(), steer(), inject(). Status idle ⇄ running ('running spans entire driver drain interval'). Inbox = two ordered pending lists (next-turn, next-step); claim(target) removes the proposed step batch by pure deletion splices; inbox state is reconstructed from durable splice events agent/inbox/{inserted,claimed,discarded}. Setup compositions are transaction-covered: failures roll back without publishing IDs; agent/created sync listener failure vetoes creation.

### Capability seams — three-role pattern
A seam = Service Definition (interface) + Service Provider (implementation) + Consumer. 'Seams are why one provider swap changes the whole product' — e.g. pointing filesystem and subprocess at a remote sandbox moves Bash, PTY, and LSP without forking. Services are classified: swappable seams (ctx.llm, ctx.sessionPersistence, ctx.settings, ctx.credentials, ctx.subprocess, ctx.shell, ctx.web, ctx.skills, ctx.subagents); unswappable core spine (ctx.sessions, ctx.tools, ctx.invariants, ctx.tokenMeter); composition points (ctx.agentLoop — 'the one concrete loop plugin', itself swappable, nothing outside may depend on it). No cross-seam dependencies permitted; companion plugins extend without overriding (e.g. fs-observation-policy).

### Composition layering: profiles, bundles, patches
Profiles are named compositions in $DSH_HOME/profiles/<name>/ (package.json + dsh.profile ordered bundle list + cordis.patch.yml). Bundles are distribution formats with Cordis config rows + code (declared via package.json fields); shipped bundles: @deepseek-ai/dsh-base (adapters, tools, persistence, sandbox, credentials), dsh-web-app, dsh-headless. 'Layers apply to an empty entry list in this order: each bundle in the profile's listed order, then the profile's cordis.patch.yml, then the home-level one, then any --patch overlay.' Patches target rows by ID and replace whole configs or insert rows — every row in boot config is targetable by patches above it.

### CLI surface (dsh launcher)
dsh --profile <name> boots the named profile; dsh --profile headless "job" runs one fresh session, prints result, exits; dsh web = shorthand for --profile web (npx @deepseek-ai/dsh web, default http://127.0.0.1:3080, --no-open); dsh plugin --profile <name> <pnpm args> manages a profile's plugins by forwarding to pnpm (dsh plugin add). Launcher flags: --profile, --patch <file>, --dump-default-config, --dump-config, --help. 'The launcher parses only its own flags and hands everything after them to the booted profile.' Bundle resolution: dsh installation first, then profile node_modules. $DSH_HOME defaults to ~/.dsh.

### Agent presets — the four shipped modes
Shipped under apps/cli/config/agent-presets/: standard (标准模式/'Standard', order 1) = full coding agent — bash/pwsh, fs read/edit/write/read_image, glob/grep, jobs, skills, goal, plan mode, compaction+pruner, subagent/subagent_fork (spawn/fork, continuable) + disabled codex/claude-code rows, workflow engine + tool, ralph (maxRounds 64), ask_user, todo, web (search only, fetch:false); code (PTC 模式/'Code Mode', order 2) = standard unchanged + tool-presentation row (dsh-agent-tool-presentation mode:code) — 'instead of one tool call per action, the model writes a TypeScript program against a generated SDK and run_code executes it, so a sequence that would be five round trips becomes one'; minimal (极简模式, order 3) = two-tool agent: persistent bash (or pwsh on win32) PTY + str_replace_editor, persona is the COMPLETE system prompt (complete:true, includeRuntimeContext:false), no compaction — a clean benchmarking scaffold; cordis (创造模式/'Creator', order 4) = standard + self-referential cordis toolset (cordis_define/run/inspect/…), a bundled editing-cordis-compositions skill, and a persona teaching the two-plane split. Its header warns: 'TRUST: cordis_mount evaluates model-written JavaScript against the live runtime… Treat a session on this preset as shell access.'

### Preset mechanics: two planes, isolate realms
A preset is a directory with one agent.cordis.yml mounted as a Cordis include subtree into the agent's scope context via the factory's setup(agentCtx); registrations land in that agent's layer and unwind with the agent. Composition splits into HOST plane (one instance: registries themselves — tools/systemPrompt/agents/agent-loop/sessions, persistence, query, projections, storage, settings, credentials, telemetry, sandbox+approval stack, model route, subagent registry+backends, web host) and AGENT plane (one per session: tool plugins, persona, prompt sections, compaction policy). Rule: 'A row that publishes a service belongs in the host composition, or inside an isolate realm if the preset genuinely owns that service and nothing outside one agent reads it.' A preset may NOT publish into the root service realm — the mount rejects it (second session would collide). Mount cost measured ~3ms/~600KB per session, so per-session isolation is the cheaper default; isolate:true = entry-local realm; named labels pool one instance process-global.

### Preset governance & switching invariants
Default preset = user setting agent-presets.default layered over the composition's own default, read per resolution, never snapshotted — new value applies to the next session; running sessions keep the composition they were built from. The preset id is model-visible and logged: it rides SessionHeader beside cwd, an agent-preset/selected event records blank-session switches, and readers resolve the pair (resolveSessionPreset), never the header alone — a resume rebuilds the composition its history was produced under. Switching allowed only while a session is blank ('agent-preset-locked' once a turn has run — swapping tools would strand logged tool calls); swap is unmount-then-mount with rollback. Preset authoring is an RPC: roster read/write/remove are loopback-pinned ('reading one is reconnaissance and writing one is arbitrary capability'); list/select stay ordinary; shipped presets are refused for writes/deletes, making 'duplicate, then edit' the authoring path; id containment is checked as grammar ([a-z0-9][a-z0-9-]*) before it becomes a directory name.

### Permission model: approval subsystem (full detail)
ApprovalRequest identifies agent + tool action for routing and audit and deliberately OMITS tool arguments (answerers attach prompts to already-streamed tool calls via callId instead of duplicating args). Four closed decision values: 'allowed-once' (one-shot grant), 'rejected', 'cancelled', 'unavailable'. Deterministically fail-closed: callers deny on rejected/cancelled/unavailable; 'A missing, non-owning, throwing, or non-conforming answerer becomes unavailable rather than opening the gate.' ApprovalPolicy is per-session with two values: 'ask' (delegates to composed answerers over the scope-filtered approval/request waterfall; first answer occupies the decision slot; no answerer → unavailable) and 'never' (deterministically rejected without dispatch). Effective policy = last approval/policy event in the session log, falling back to service config; setApprovalPolicy() is the single write path (replay-reconstructible). Audit: log-only approval/asked and approval/decided events, never in model transcripts; model-visible behavior derives from the tool result + runtime-context snapshot.

### Permission presets (sandbox × approval knobs)
dsh-permission-presets 'bundles the two independent enforcement knobs — sandbox mode and approval policy — into named presets' and 'owns no enforcement: execution, prompt narration, and replay keep reading their knob folds, and a preset switch only records intent and writes through each knob's canonical setter.' Defaults: workspace-write (sandbox workspace-write + approval ask) and danger-full-access (sandbox danger-full-access + approval never). current() folds effective knobs, prefers a still-matching recorded selection, falls back to first matching table entry, else CUSTOM_PRESET ('custom' — derived-only, never a switch target). set() appends a log-only permission/preset event only when the preset actually changes. Config: presets{} name→PresetSpec{sandbox,approval,name,description}, defaultPreset.

### Sandbox subsystem
Three layers: dsh-sandbox (abstract policy seam), dsh-sandbox-local (Linux bwrap/Landlock, macOS Seatbelt, Windows ACL), consumers (dsh-bash-sandbox, dsh-pwsh-sandbox). Scope is FILESYSTEM ONLY — network, process visibility, IPC are out of scope; 'Containers, microVMs, and remote execution are sibling implementations of whole capability seams, not providers.' Three modes: read-only (denies writes except required sinks like /dev/null), workspace-write (writes under workspace root + backend temp areas), danger-full-access (bypasses confinement — consumers spawn original argv without calling ctx.sandbox). SandboxExecutionPolicy {mode, workspaceRoot (canonicalized fs-semantics-first), sessionId} is resolved and carried PER CAPABILITY CALL — approved escalations override session policy at call time without mutating provider state. Enforcement is a reported fact, not a guarantee: 'full' vs 'partial' (older Landlock ABIs, Windows ACL Everyone/hard-link gaps); consumers requiring absolute boundaries must reject partial. confine(argv, policy) returns wrapped ConfinedArgv or throws SandboxUnavailableError (SANDBOX_UNAVAILABLE) — 'silent unconfined passthrough is prohibited'. Two orthogonal stderr classifiers: denialSignatures (per-backend dialect: EROFS/bwrap, EACCES/Landlock, EPERM/Seatbelt) vs runnerFailureRules (fatalSignatures + allowedExitCodes gate, informational lines stripped); 'Exit status alone never proves runner failure'; runner-failure checked before denial. The model can request strictly-wider retries via sandbox_permissions plus justification.

### Session log format (traceability core)
SessionEvent envelope: type (key of merge-extensible SessionEventMap), seq ('monotonic sequence number within the session', contiguous, seq = log.length), time (Unix epoch ms), data (lossless JSON, validated at Session.append), optional ignorable (forward-compat skip marker), and for surface events surfaceOp + sourceEventSeqs. Exactly three surface event types produce LLM messages: user/message, assistant/message, tool/result; 60+ log-only types record durable replayable state with no model contribution (turn/step boundaries, chunks, request headers, approvals, compaction markers, plan mode, goals, schedules…). SurfaceOp = 'append' or {op:'replace', start, end} (replaces a surface-node range with explicit shadowed-seq tracking). sourceEventSeqs cite the originating events (e.g. chunks that built a message). Format pinned at SESSION_FORMAT_VERSION = 0; unknown event types without ignorable:true refuse reconstruction (fail-safe against silent data loss). Events are immutable and deep-frozen once appended; raw chunks are stored verbatim in the same seq space for 'token-level replay fidelity' — 'the canonical log persists every event losslessly, including assistant/chunk'. History is derived lazily via deriveMessages() (frozen Message[], cached per node, replace rebuilds by shadowing); the pure deriveEventMessage() applies identical projection rules across all consumers. session/end-seed marks where this process's live writes begin after a seed (locate the LAST occurrence). Core invariants (dsh-session/invariant): turn/step numbering coherence, execution-event enclosure in turns, same-step tool call/result pairing.

### Persistence backends & crash recovery
SessionPersistence seam (ctx.sessionPersistence): location resolution, create, append, prepare, load, inspect, list over the append-only log; no parallel persisted event type. Invariants: append synchronous after durability; logs contiguous and losslessly JSON-serializable; load balances incomplete final turns WITHOUT rewriting committed history; unknown format versions refuse rather than migrate ('written by a newer harness' distinguished from corruption). Crash recovery: a reload finding open turn/start synthesizes turn/end {reason:{kind:'interrupted'}} — the only TurnEndReason never emitted by the loop; cold sessions get synthetic closers in memory while torn physical tails are preserved; only torn final records discarded. Write batching: fixed-window deadline coalescing; session/flush cancels waiting and drains to quiescence as THE ordering checkpoint before the next turn; rejected writes retain events and pause auto-retry. SessionHeader travels separately from the event log: format version, id, createdAt, cwd, lineage (parentSession, seedLength), origin:'subagent', delegationDepth, agentPreset. JSONL backend: one logical append-only file per session, checksummed concatenated Zstandard frames (configurable raw), crash-safe atomic writes. SQLite backend: schema 17 on node:sqlite, single DB for all sessions, packs same-block delta runs into bounded text-chunks/reasoning-chunks/tool-call-chunks rows, rejects older schemas without migration. SessionPersistenceSnapshot pairs header with an opaque revision token for cheap change detection; readFrom(fromSeq) is the raw suffix primitive for watermark-resuming read models.

### Session query, references, projections, titles
Query: SessionRecord / SessionEventRecord (lightweight raw-log projection with surface classification current|shadowed|log-only) / SessionLogSnapshot (complete detached replay-validated log for resume preflight). Semantic filters are provider-independent; 'text is a literal, case-insensitive, whitespace-flexible semantic-text scan'; 'full-text query interpreted as data, never executable FTS syntax'; structural events and stream chunks contribute no semantic text. SessionLineageTrace (parents immediate-to-outward + descendant forest) and SessionEventTrace (positional replacement vs source citation, replacement chains to final resolution). References: canonical mention @[label](dsh-session:…); discovery filters on id/cwd 'never transcript text'; prepared context is one aggregated untrusted snapshot; self-reference rejected. Projections: pure synchronous folds (init/apply/view), state-carrying events contain 'the complete post-change state, never a bare delta'; unchanged state must return the same reference (Object.is) for zero downstream work; async units would 'tear the carriers' consistency cut'. Titles: latest-wins fold with source attribution fallback|provider|user; user rename 'pins the title — automatic generation stops scheduling'; each title LLM request is durably recorded before the call.

### Session telemetry (OTel)
Capability seam: dsh-session-telemetry (capture coordination) + dsh-session-telemetry-otel (OpenTelemetry JS SDK pipeline). Modes: FULL | FEEDBACK_ONLY | DISABLED (default), disclosed via SessionTelemetrySharingStatus. Redaction is deployment's job via the session-telemetry/record waterfall — 'The seam ships NO rules of its own: with no listener mounted, records reach the backend exactly as captured'; the canonical log is never modified. Ledger records mirror session events 1:1 (session.id, event.type, event.seq; only the FIRST assistant/chunk per turn ships); ops records (agent-error, shutdown) intentionally omit event.seq. Non-blocking emit (sync queue-push only); best-effort at-least-once; receivers dedupe on (session.id, event.seq); 'the harness's aspect ends at emit()'.

### Tool execution pipeline (9 stages)
1) input materialization: args losslessly JSON-serialized and deep-frozen once; identity (callId, rootCallId, token) readonly. 2) tools/pre-execute waterfall: reorderable allow/deny/ask policy — 'ask' requires an approval service returning allowed-once; missing support DENIES. 3) monotonic guards (ctx.tools.guard()): scope-aware final checks that can only reduce permission — 'Because guards have no allow result, listener ordering cannot turn a denial back into permission.' 4) tools/execute waterfall: around-dispatch wrappers (timeouts) may replace but not remove the signal; registry re-fuses caller signal before the body. 5) tool body with ToolRunContext (deferContext(), concludeTurn()). 6) tools/post-execute waterfall: accept/replace/block results; blocking becomes isError with corrective feedback. 7) definition-owned finalizeContent() invoked exactly once on every normalized outcome including failures ('synchronous content-only invariant'). 8) result materialization: canonical value is execution-local, never persisted — only content, error, meta reach durable events. 9) tools/result emit: final immutable lossless-JSON observation; failures contained. 'This lets hooks span tool families without coupling the tools to one policy service.'

### Tools subsystem: definition, DSL, scoping
ToolDefinition = ToolSchema + ToolOutputDefinition (canonical JSON schema + pure render() to content blocks + optional presentationMeta()) + async execute + optional finalizeContent/timeoutMs/isConcurrencySafe/presentCall/presentResult (pure, replayable during live streaming and session replay). Schema DSL (ValueSchemaSpec): string/number/integer/boolean/null/array/object/json/oneOf; InferValue honors literals through 16 container levels; runtime validation walks the whole schema. Scoping: global ctx.tools.register() vs agent.ctx.tools.register() shadowing; ToolRestriction applies per-scope allow/deny filters that intersect, with a scope's OWN registrations exempt; run_code is a reserved name. Registry 'preserves caller cancellation through signal replacement' but 'cannot hard-kill same-process code'.

### Code Mode
run_code executes a model-written TypeScript program (async function body) against host bindings; 'Owned by the tool registry as a reserved transport outside filterable capability layers'. Sub-dispatches get deterministic identity <parent>:code:<n> and nest in the call tree; model-direct calls without a parent token cannot execute native tools (UNKNOWN_TOOL before policy). The tools/code-dispatch-log waterfall lets listeners reshape the LOGGED copy of each settled sub-call before the tool/code-dispatch event — 'Only the logged copy is affected — the program already received the complete value, and the model sees neither.' Sub-dispatch context ferried to the outer result via deferContext().

### Tool catalog scale & notable tool rules
28 tool packages, 80+ model-visible tools, statically generated by booting plugins and reading ctx.tools.schemas(). Notables: str_replace_editor requires unique literal match; fs read/edit/write enforce read-before-write via the separate dsh-fs-observation-policy plugin; glob/grep cap at 100 inline paths and spill full lists; goal create/update require 'direct-human root authority' and blocked needs ≥3 admitted rounds by default; schedule_create takes exactly one of after_seconds/every_seconds(≥300)/at; todo_write replaces the ENTIRE list each call; lsp is one-based UTF-16 at the tool layer over a zero-based wire; cordis tools are opt-in and 'a running package may register ADDITIONAL model-visible tools until stopped, undefined, or DSH restarts'; team tools (agent-team) are experimental, disabled in base, with CAS task updates (expected_revision); subagent prompt must be self-contained ('It does not share this conversation's context, so include everything it needs').

### LLM seam & streaming protocol
Immutable Message objects with provider-neutral roles and merge-extensible ContentBlock map (Text/Reasoning/Image/ToolCall/ToolResult); AssistantProvenance carries provider route, model id, adapter-private replay state. StreamChunk closed union: block-start/end, text/reasoning/tool-call deltas, usage, finish — 'Usage before finish, nothing after finish.' Tool arguments stay raw JSON strings end-to-end. Adapter imperatives: throw or finish{kind:'error'|'aborted'} normalizing to one LlmFailure; 'Context overflow has one canonical code' (CONTEXT_WINDOW_EXCEEDED); empty stop → EMPTY_RESPONSE; every request carries attribution headers; single attempt per call (library retries disabled — agent-level recovery opens a new durable turn); streamIdleTimeoutMs watchdog (5 min default). Registration: ctx.llm.registerAdapter(providers, adapter) with atomic duplicate rejection and atomic replace(). Retry policy resolves to normal (default 5 retries) or always mode, captured immutable at registration. 'Advisory catalogs, authoritative adapters': listModels() is advisory; validation never rejects on catalog membership. BlockAssembler drops truncated tool calls on max-tokens finish (unsafe to execute) and prunes aligned replay-envelope entries — one keep/drop decision covers content and metadata.

### Token meter & compaction
TokenMeter is a replay-based estimator producing detached immutable snapshots: logRevision, totalTokens (request pressure), surfaceTokens (sum of positional node prices), signed surfaceDeltaTokens vs a baseline anchor. Dual anchors: provider usage baseline reused only under strict envelope-match conditions, else heuristic repricing; surface order is authoritative. Compaction is a seam (dsh-compaction / dsh-compaction-basic / dsh-command-compact) with three log-only events: compaction/start (lock; numeric turn = automatic, null = manual), compaction/summary (safe projection, shadowed range/seqs, token count), compaction/end (lock release; error field records failures) — crashes leave orphaned start events as detectable failures, never false-positive ends. Triggers: 'pressure' (at agent/pre-step, threshold default 0.8 of window, retain 0.16) and 'context-overflow' (provider-confirmed, allows aggressive reduction). The summary is a user/message with surfaceOp {op:'replace', start, end} — the ONLY surface mutation compaction performs, deliberately avoiding extending SurfaceEventType. Tool-pairing balance validated at region boundaries. Optional ctx.toolResultPruner does deterministic head/tail pruning (8192/4096/1024 chars default) with compaction/prune shadow-price events. 'A surface replace event is priced by the metering event immediately before it.'

### System prompt assembly
Sections concatenate in ascending order (convention: -100 harness identity, 0 deployment persona, 100–199 tool guidance); static text or dynamic (AssembleContext)=>string. One effective 'complete' section becomes the sole prompt section (minimal preset uses this to own the whole prompt). Scoped sections shadow global sections of the same name. PromptContext = 'dynamic model context materialized as a durable user-role snapshot', suppressible via suppressRuntimeContext(). system-prompt/assemble is a cooperative waterfall whose returned assembly is authoritative ('listener authors own preserving active Code Mode'). ToolProviderResult carries schemas + knownNames (distinguishing config typos from deliberately hidden tools). {{variable}} interpolation decouples structure from substitution; invalid names/duplicate sections/multiple complete sections throw.

### Shell / subprocess / terminal / jobs
Shell seam (ctx.shell → dsh-bash-local / dsh-bash-sandbox → dsh-tool-bash): callers 'hand over the exact argv they are about to spawn'; resolve() turns optional request fields into a fully-specified spec ('explicit > implicit at package boundaries'). Same-world guarantee: model and plugin execution share one environment; harness-owned DSH_* vars merge last and 'an entry here can never displace' them; credentials scrubbed from ambient env. 'run rejects only for infrastructure failures. Nonzero exits, timeout kills, and abort kills resolve'; timedOut vs aborted mutually exclusive by first-cause on one fused deadline. Subprocess seam applies NO defaults ('every disposition, limit, and directory is explicit on the spec'); offset-based non-consuming readers; terminate() escalates SIGTERM→grace→SIGKILL tree-scoped on every platform; exits carry facts only — no timeout/cancel classification, callers classify from their own signal; relative paths with separators rejected ('fail loud instead of guessing'). PTY: authorization compares 'the exact owning Agent, not a name or guessed id'; one exclusive send per session; state process-local, sessions survive plugin reloads. Jobs: branded JobId '<kind>-N' — 'Access control relies on owner authorization, not id secrecy'; producer/consumer split with fresh snapshot projections; first-wins settlement; ownership fenced by session id; admission refused with no attached controller; default maxConcurrentJobsPerOwner 10.

### Filesystem capability
Four packages: dsh-fs, dsh-fs-local, dsh-fs-observation-policy (optional), dsh-tool-fs. Opaque FsTarget with branded targetKey ('must not parse targetKey… or assume it is a local absolute path'); opaque FsVersion freshness tokens. Guards: createIfAbsent (FS_NOT_OBSERVED on existing) and replaceIfVersion (FS_STALE_VERSION on mismatch, checked BEFORE literal matching); omitted guard = unconditional bare-provider behavior. Stable 12-code FsErrorCode taxonomy; FS_SANDBOX_DENIED (policy fence) distinct from FS_PERMISSION_DENIED (kernel). Observation policy is a WeakMap keyed by opaque session identity, fed by fs/observed events (firewall pattern — the tool never imports policy code). No implicit timeouts: 'A timeout could not force an in-progress fsync/rename to stop, so a timeoutMs here would be a deadline the seam cannot enforce.' Writes/edits atomic critical sections; before/after are raw LF-normalized storage text, never diffs; windowed reads still authorize later guarded writes (no partial-observation concept); lstat() is the no-follow trust-boundary primitive; listing is metadata-only.

### Code runtime & web access seams
Code runtime (ctx.codeRuntime): 'runs one model-written program against host-provided async bindings and reports what it printed and returned'; descriptors language ('typescript'|'python') and isolation ('worker-thread'|'process'|'container' — 'diagnostic label, not a security guarantee'). Results resolve on failure, never reject; six orthogonal failure kinds: exception, timeout, abort, worker-exit, invalid-output, output-limit. Bindings are null-prototype global namespaces; lossless JSON both ways; programs treated as hostile peers; runs isolated from each other. Worker-thread config: computeMs busy budget, maxWallMs, maxOutputBytes, heap ceiling. Web (ctx.web): search+fetch deliberately one middle layer for unified provider selection/error vocabulary; available() must be a cheap LOCAL check, no network calls; six-rule deterministic provider selection (configured → missing/unavailable errors; else auto-select single, WEB_PROVIDER_AMBIGUOUS on multiple). HTTP status is resource state, not failure. Caveat: 'the local backend does not block private-network targets; do not enable web_fetch where it can reach sensitive internal ones.'

Markdown files (dir bundle <name>/SKILL.md or flat <name>.md), kebab-case names. ### Workflows & Ralph
Workflow = model-written orchestration SCRIPT (plain JS, top-level await, must end in return) that starts subagents; WorkflowMeta {name, description, whenToUse, phases}. Engine: one worker per run, vm context inside; single engine provider replaces predecessors. WorkflowResult {value plain JSON, stopReason completed|cancelled|error, agentsStarted}; fatal WorkflowError for hook misuse/caps/schema violations; parallel()/pipeline() combinators re-throw fatal errors. Invariants: one start per run in chat; no run ends with open members; missing terminal facts indicate interruption, not corruption. ralph tool: fresh agent per round, immutable objective, foreground only, maxRounds cap (64 in shipped presets).

### Subagents subsystem
Named provider registry (ctx.subagents; multiple coexist, unlike single-executor bash): in-process spawn/fork + remote acp/codex/claude-code/dsh-sdk transports. Capability split: static SubagentCapabilities flags (outputSchema, depthLimit, toolFilter, persona) checked at start — unsupported requests fail loud with SubagentError('UNSUPPORTED_CAPABILITY'); continuable capability = presence of prepareContinuable() ('Method presence IS the capability'). One-shot = 'one disposable foreground delegation with one result, never a durable child handle'; continuable = durable background sessions, at most one live Activation per Session, state preserved across cold resume, parent holds turns through the child's own inbox (FIFO, 'a follow-up cannot redirect a turn already underway'). Depth persisted as SessionHeader.delegationDepth + AgentOptions.subagentDepth, seam-owned ('the loop neither sets nor reads them'); cold resume cannot lower depth. Children get 'a new flat scope rather than inheriting parent registrations' — inheritsParentContext covers only conversation seeding (fork true, spawn/acp false), never tools/services/authority. Tool filter applies as scoped tools.restrict() in the creation window: 'the named tools vanish from the child's prompt AND refuse to execute (one visibility)'. Follow-up authority requires the exact live parent recorded in SessionHeader.parentSession; child-first disposal; descriptor log-only, never in model history.

### Plan mode
'Soft guidance' — log-only {active:boolean} plan/mode events; state is 'always a pure fold of the session log' (foldPlanMode), surviving resume/fork/compaction; enforcement belongs to sandbox+approval, not plan mode. ### User questions, commands, goals, schedules
User-questions seam: provider-neutral vocabulary for human-blocking decisions; single active UserQuestionProvider per context, effect-bound; stable error codes EMPTY_QUESTIONS/NO_PROVIDER/ASK_ABORTED/CALLER_NOT_LIVE/DELEGATED_CALLER — validity depends on runtime ownership, not lineage ('an owned child has no human answerer and would block forever'); intent tags (plan-review) fall back to generic option lists when unknown. Commands: ctx.commands is a slash-command registry for UI adapters executing plugin handlers WITHOUT the model; scoped shadowing per agent; logged as command/run + command/done; admission failures log nothing. ### Platform: web server, typert, client modules, storage, workspaces
WebServer: exact vs prefix routes, deterministic match (exact → longest prefix → single fallback), duplicate registrations throw; 'there is no TLS, auth, or origin policy' — only 127.0.0.1 (default) or explicit 0.0.0.0; 'not part of the agent loop and not a capability seam'; Electron bypasses it via IPC. Client modules: WebBootGraph is the single source of truth Node↔browser; content-hash cache busting; fail-fast at activation, graceful in steady state; HMR dev-only. Storage: hub (ctx.storage) performs no I/O — 'backends own media, data forms own semantics, and product packages never touch backends directly'; zod-typed DomainSpec with versioned refusal; sync reads from authoritative memory, queued per-domain write chains; rejected writes leave memory untouched. Workspaces: stable id over canonical realpath; delete removes registration only ('the directory, user files, live sessions, and persisted logs are never touched'); 'invisible to models (no tools, no prompt text, no session events)'.

### Settings & credentials
Settings: three-layer resolution — schema defaults → composition base (cordis.yml, plugin-owned) → user section; schemastery schemas registered fiber-scoped; deep-equality gating on settings/updated; separate settings/document-updated detects inherited→overridden transitions; per-namespace serialized writes with expectedRevision optimistic locking (SettingsConflictError); validate() callback for cross-field constraints; redactSecrets:true strips role('secret') fields for wire surfaces. Credentials: branded env-var-style CredentialRef vs plugin-scoped CredentialKey; 'consumers re-resolve at each operation and never cache across operations — that per-operation read is the hot-update mechanism' (rotation reaches the very next request); 'an empty stored value is absent everywhere'; writes shadowed by ambient process env are rejected rather than silently ineffective; serialized read-modify-write for token refresh; describe() exposes source layer + writability without values.

### Runtime invariants subsystem
ctx.invariants is a registry for package-owned runtime checks (support group, not a seam): selection via enabled + case-sensitive regex allowlist/blocklist (blocklist overrides). Failures throw InvariantError (code 'INVARIANT', message 'invariant violated by "<package>": …') with package attribution and no product imports in the registry. Companion contract: EVERY workspace package must own a ./invariant plugin registering checks under its exact npm name, or export an empty installer commented 'No runtime invariant:'; mechanically verified by pnpm run verify-package-invariants. Checks may assert authoritative event streams or mutable data, never service/method presence. Name reservations persist even when filtered off, preventing silent collisions.

## Design principles
- Everything is a plugin; there is no privileged core to patch — extension means mounting a plugin beside the others, and every part (model adapter, tool registry, session log, agent loop) is replaceable from configuration.
- Model-visible means logged: anything reaching a model request must be reconstructible from the append-only session log, asserted by a runtime invariant; the log is the single source of truth and derived history is never stored separately.
- Event-sourced sessions with lossless, token-level replay fidelity: immutable deep-frozen events, contiguous seqs including raw chunks, surface vs log-only split, sourceEventSeqs citations, and refusal (not migration) on unknown formats.
- Capability seams over implementations: Service Definition / Service Provider / Consumer triads make one provider swap change the whole product; no cross-seam dependencies; companion plugins extend without overriding.
- Two-plane composition: the host plane owns registries and anything shared across sessions (persistence, sandbox+approval stack, model route); an agent preset owns only what one session contributes to those registries — decided by what must be shared, not by what feels agent-related.
- Fail-closed permissioning: approval outcomes are a closed set and a missing, non-owning, throwing, or non-conforming answerer becomes 'unavailable' rather than opening the gate; sandbox confinement throws rather than silently passing through unconfined.
- Enforcement knobs are independent and canonical; presets are derived UI intent: permission presets bundle sandbox mode and approval policy but own no enforcement — a switch only records intent and writes through each knob's single setter, and 'custom' is derived-only.
- Policy is monotonic where it matters: tool guards can only reduce permission (no allow result), so listener ordering can never turn a denial back into permission; deliberate bypass paths do not exist at the waist.
- Enforcement is a reported fact, not an assumed guarantee: sandbox results carry full/partial enforcement reports and orthogonal denial vs runner-failure classifiers; consumers needing absolute boundaries must reject partial enforcement.
- Explicit over implicit at package boundaries: subprocess specs carry every disposition/limit/directory with no hidden defaults; requests resolve to fully-specified specs; relative executables fail loud instead of guessing.
- Durable facts and live control are separate channels: session/event for replayable facts, agent/* for in-flight coordination — SDK consumers read the former, orchestration uses the latter.
- Dispatch mode encodes semantics: waterfall for transform/veto middleware, serial for ordered checkpoints, parallel for independent-chance fan-out (durability flush), emit for contained notifications.
- Registrations are reversible effects with deterministic LIFO teardown; fiber ownership bounds every service, listener, and tool, so unload/rollback is structural, not best-effort.
- State is derived by pure folds: plan mode, presets, goals, projections, and token metering are folds of the log (whole-value snapshots, Object.is short-circuits), never live mirrors that can disagree under replay.
- Crash recovery preserves rather than truncates: interrupted turns get a synthetic 'interrupted' closer distinct from anything the loop emits; only torn final records are discarded.
- Immutability as an API discipline: frozen requests, frozen arguments, frozen events, snapshot-only job/workflow payloads, and execution-local canonical values that never reach durable storage.
- Per-operation resolution is the hot-update mechanism: credentials, sandbox policy, and the default preset are re-read at each use, so rotation and reconfiguration reach the very next operation while running sessions keep the composition they were built from.
- Authorization binds to exact live identity, not names or lineage: PTY/goal/user-question/subagent operations compare the exact owning Agent object; id secrecy is never the access-control mechanism.
- Fail loud on unsupported capability, degrade gracefully on absent capability: unsupported subagent capabilities are typed errors, while absent persistence makes enumeration live-only — absence of capability is not failure.
- Stable error taxonomies over message parsing: every seam publishes closed or namespaced error codes (Fs*, LSP_*, WEB_*, SANDBOX_UNAVAILABLE, INVARIANT) so callers route on codes.
- The trust boundary is named, not hidden: the Creator/cordis preset that can edit the live runtime is documented as equivalent to shell access; preset authoring RPCs are loopback-pinned; the web server explicitly has no TLS/auth/origin policy.
- Documentation is generated and drift-checked against source; the feature→mechanism map is the standing proof obligation of the microkernel claim; every package must publish (or explicitly waive) its runtime invariant.

# develop-docs
Source: https://deepseek-harness.github.io/deepseek-harness/en/develop/ (basic/ index + 14 subpages: basic/tool, basic/config, basic/publish, framework/, framework/service, framework/events, practice/, practice/llm-adapter, cordis-tutorial/ 0–7)

## Key points
### What Cordis is / relationship to dsh
Cordis is the plugin kernel underlying DeepSeek Harness: 'a small runtime where every capability — tools, LLM adapters, file access, the agent loop itself — is a plugin mounted into a shared context.' Harness plugins are loaded from configuration files and driven through a web UI; Cordis plugins are the more fundamental runtime layer. Functionality is decentralized rather than monolithic — even the agent loop is just a plugin.

### Plugin definition and three forms
A plugin is a TypeScript module exporting an `apply(ctx: Context)` function (plus optional `name` export used only as display metadata for diagnostics). Three shapes: function form (recommended default), object form (declares `name`, `inject`, `apply`), and class form extending Cordis `Service` — used when the plugin provides a service to other plugins. The framework invokes `apply` at load time passing the Context, the sole interface for registering capabilities.

### Context object
The Context (`ctx`) is the central registration surface: `ctx.on()` for events, `ctx.tools.register()` for tools, `ctx.llm.registerAdapter()` for LLM adapters, `ctx.effect()` for custom resources, `ctx.plugin()` for mounting child plugins, `ctx.get()` for optional service lookup. Services mount as properties on ctx (e.g. `ctx.tools`, `ctx.llm`, `ctx.agents`, `ctx.greeter`), with TypeScript declaration merging on the `Context` interface providing compile-time typing (runtime works without it).

### Fiber lifecycle state machine
Every plugin instance owns a Fiber scope with states PENDING → LOADING → ACTIVE (or FAILED if apply/validation throws) and ACTIVE → UNLOADING → DISPOSED. PENDING = required service unavailable — explicitly 'a legitimate state, since the provider may be mounted later', so unsatisfiable inject waits indefinitely WITHOUT an error; diagnosis is iterating the context registry checking for FiberState.PENDING. Load failures in apply() are fatal (process terminates loudly), but module-path resolution errors report through the logger service and can be lost before console export activates.

### Everything a registration does is an 'effect'
Core lifecycle invariant: 'Registrations made through Cordis APIs are effects and are undone when their owning plugin unloads.' Event listeners, tool registrations, service registrations (the `super(ctx, name)` call itself is an effect), child plugins, and adapters all auto-dispose on unload. Resources outside Cordis's management (timers, network connections, watchers) must be wrapped in `ctx.effect(() => disposer)`. Plugins can be unloaded via config edits, hot reloads, explicit disposal, or a required service disappearing.

### Disposal ordering guarantees
During unload, disposer invocation starts in reverse registration order, BUT multiple async disposers run concurrently — so order-dependent teardown must be wrapped in a single `ctx.effect()` call with sequential awaits inside one disposer. `fiber.dispose()` resolves only after all cleanup completes, including async disposers, and recursively unloads child plugins. `ctx.plugin(child)` creates a child Fiber with independent lifecycle but inherited context; child disposed with parent.

### Services: definition and consumption
A service is 'a capability one plugin exposes to other plugins', mounted on ctx. Built-ins: `tools`, `llm`, `agents`. Providers extend the `Service` base class, registering via `super(ctx, 'name')`; a service can itself declare `static inject` to depend on other services. Consumers declare required services in an `inject` array; 'when apply runs, every service declared by inject is ready. If a service is not ready, the plugin waits instead of running.' Optional dependencies use `ctx.get('serviceName')` — returns undefined without blocking, plugin runs regardless.

### Dynamic dependency tracking (continuous, not boot-time)
Dependencies are continuously monitored, not checked once at boot. If a required service disappears (provider unloaded or hot-replaced), dependent plugins dispose automatically and reload when the service returns — this structurally prevents runtime calls to unavailable services. Load ordering comes entirely from service dependencies: cordis.yml 'entries start concurrently, so list position guarantees nothing about which plugin loads first.'

### Service namespace and isolation
Service names live in one flat namespace per application; authors must prefix/namespace their own services distinctively to avoid colliding with harness-reserved names like `tools` and `llm`. cordis.yml supports `isolate` blocks giving plugin groups their own independent instances of the same service 'with no cross-group effect'. Groups nest sub-lists that load/unload as atomic units.

### Tool declaration API
Tools are declared with `defineTool()` from `@deepseek-ai/dsh-tools`: `{name, description, parameters: {key: {type, required, description}}, output: {schema, render}, async execute(args)}`. Plugins declare `inject = ['tools']` and register via `ctx.tools.register(defineTool(...))`; Cordis waits for the tools service before applying the plugin. defineTool infers the type of `args` from the parameters schema and validates model-supplied arguments before execute runs. Execution goes through `ctx.tools.execute()` with a CallId correlation identifier.

### Tool output: canonical value vs rendered presentation
Tools separate what they compute from how the model sees it: 'execute returns the canonical value declared by output.schema, and output.render converts that value to model-facing content.' This is an explicit abstraction boundary between tool logic and the presentation layer — the canonical typed result exists independently of its LLM serialization.

### Event system: five dispatch modes
Registration `ctx.on(name, handler)`, broadcast `ctx.emit(name, ...args)`. Modes: emit (synchronous broadcast, return values/promises ignored, all listeners run); parallel (`await ctx.parallel()`, concurrent + awaited together); serial (`await ctx.serial()`, registration order, async awaited, first non-null/false/undefined result stops the chain and becomes final); bail (synchronous serial variant, first meaningful result short-circuits); waterfall (`ctx.waterfall()`, around-middleware — each listener gets args plus a `next()` continuation and can transform what next() returns or short-circuit by not calling it).

### Waterfall as the interception/policy seam
The waterfall mode is how dsh does interception and gateway patterns: the harness uses waterfalls for `agent/request` (a plugin can replace model-call configuration) and `approval/request` (a policy can answer instead of the user). Critical rule: 'A waterfall listener that only observes or annotates must call next(); returning without it is a deliberate short-circuit.'

### Typed events and naming convention
Events are typed via TypeScript declaration merging on an `Events` interface (method signature defines payload types and mode). Naming convention `namespace/action` keeps the flat event namespace organized. Harness Cordis events include `agent/step`, `agent/request`, `agent/request-error`, `tools/result`, `session/event`. Listeners registered with ctx.on are removed automatically on plugin unload — listeners are effects.

### Durable session records vs live Cordis events
Durable session-event types (`turn/*`, `step/*`, `tool/call`, `tool/result`, `compaction/*`) are NOT same-named Cordis events — they are persisted session records; live observation is via a `session/event` Cordis listener inspecting those records. So there is a deliberate two-layer distinction: an in-process event bus vs a durable session log.

### Configuration: dual export, schema-validated
Plugins export both a TypeScript `Config` interface and a same-named runtime Schemastery schema object ('The exported Config is both a TypeScript interface and a runtime schema with the same name'). A plain object as Config is forbidden — it doesn't implement the Standard Schema interface Cordis requires (Cordis accepts any Standard Schema validator, Schemastery is the shipped one). Validation runs before apply(): defaults filled, invalid config fails plugin loading with structured actionable errors (exit status 1) — plugins never start with incomplete or invalid config; failure is at load time, not runtime.

### cordis.yml, !!js dynamic values, entry identity
cordis.yml is a list of plugin entries {id, name (module path or npm package), config, disabled}. The YAML loader supports `!!js` tags for computed values at load time (e.g. `!!js process.env.X ?? 'default'`) — but only inside `config` blocks and entry `disabled` fields, not static metadata. `id` gives an entry stable identity so the loader can tell an edit apart from removal-plus-addition; entries without explicit id get regenerated identifiers on every read, causing full remount on each config edit and defeating HMR.

### Hot module replacement semantics
With `@deepseek-ai/cordis-plugin-hmr`, file or config edits trigger unload → load → apply: 'the old instance unloaded (all its effects unwound), the new code loaded, apply ran again.' Because registrations clean themselves up, 'hot replacement does not retain registrations from the old instance' — no accumulation across reloads. Config edits use the same mechanism (unload old instance, load new one). HMR itself depends on two support plugins (logger-console for visibility, timer for debounce) and silently sits PENDING without them — even HMR obeys the dependency rules.

### Bundle vs profile (packaging model)
Two concepts, two manifests: 'A bundle is what you author and distribute; a profile is what a user boots with dsh --profile <name>. Nothing is both.' Bundles answer 'what does this package contribute?'; profiles answer 'which bundles compose this setup, in what order?'. A bundle package declares `dsh.bundle.patch` in package.json pointing at a cordis.patch.yml whose plugin rows reference the package by name (not relative path) so Node resolution finds installed code. Naming: `dsh-<plugin-name>` packages; profiles live under `$DSH_HOME/profiles/<name>`.

### Layered configuration composition
Effective config applies layers sequentially: (1) each bundle patch in dsh.profile.bundles order, (2) the profile's own cordis.patch.yml, (3) home-level $DSH_HOME/cordis.patch.yml, (4) each --patch overlay in argv order. 'Later layers win per row, and a patch replaces a row's entire config value rather than deep-merging keys' — row-level replacement, no deep merge, so authors should ship sensible schema defaults. A patch file contributes configuration but does not change the profile directory from which the loader resolves module paths.

### Install flow
`dsh plugin --profile <name> add <package>` initializes the profile (base bundle `@deepseek-ai/dsh-base`), forwards to pnpm for dependency management, and auto-appends the bundle to `dsh.profile.bundles` if the package declares `dsh.bundle`; a package without it installs as a plain dependency. Git installs never run the `build` script — authors must ship a `prepare` script producing self-contained entry points; recommended alternatives are npm publish with pre-built artifacts or pnpm-pack tarballs, both avoiding requiring build permissions from users. In-box bundle names resolve from dsh itself; only out-of-tree packages go through pnpm.

### Capability layering: the three-role pattern
When a capability is general enough to need replaceable providers (e.g. Bash execution), Harness separates three roles: Service Definition (declares the Cordis service interface and owns the Request/Result types), Service Provider (implements it, e.g. dsh-bash-local for local execution), and Consumer (exposes it as a model-callable tool, e.g. dsh-tool-bash, injecting the definition via inject:['shell']). Provider and Consumer depend only on the definition, never on each other, so providers swap via cordis.yml without touching definition or tool, and 'Service Providers can improve performance and security independently.' The complete capability is the 'seam'; individual roles are not. Counter-principle: 'Do not split preemptively — use separate packages only when the roles need to evolve independently.'

### LLM adapter architecture
Adapters extend `LlmAdapter` and implement `stream()`, translating provider-neutral requests to provider APIs and responses back to standardized chunks. Registration: `ctx.llm.registerAdapter(['my-provider'], adapter)` — the provider string routes requests while model identifiers remain adapter-owned. `resolveModel()` performs provider/model identity lookup returning context-window and reasoning metadata (opaque ids, display names, optional defaults); the adapter preserves its authoritative model list 'including off when its upstream capability API returns it'. GenerateOptions carries model selection, history, system prompts, tool schemas, generation params, stop sequences, abort signals.

### StreamChunk protocol and adapter error contract
Streaming protocol: block-start (index + type) → text-delta chunks → block-end (finalized block object); tool calls flow separately via tool-call-delta with raw JSON in argumentsDelta; usage chunks precede the final finish chunk. Invariant: 'Every block-start has a matching block-end.' Errors: transport/protocol failures must throw `LlmError` with stable codes for diagnostics and policy decisions; unsupported GenerateOptions fields should raise LlmError rather than being silently dropped; HTTP requests must include attributionHeaders() and forward options.signal for cancellation propagation.

### Decoupled observation via registry + events
Tutorial ch.7 demonstrates the composition idiom: a tool plugin registers via the tools service; a separate logger plugin listens to `tools/result` events — 'Neither of your plugins knows the other exists — the registry service and the event connect them.' Registry services plus typed events are the two coupling mechanisms; direct plugin-to-plugin coupling is absent by design.

### Composition requirements for a working agent
The tool pipeline requires `@deepseek-ai/dsh-system-prompt` and `@deepseek-ai/dsh-tools` in the composition because tools contribute their schemas into the system prompt; without them dependent plugins sit PENDING. A complete agent = that composition + an LLM adapter plugin + an agent loop plugin + a persistence layer + entry points (reference example: examples/headless-agent/cordis.yml in the GitHub repo). The agent loop itself is a plugin like everything else.

### Dev workflow
Local development: create the plugin TS file, register it in cordis.yml with an absolute path, launch the Web UI with a patch overlay: `pnpm dsh web --patch ./plugin-path/cordis.yml`. Plugins can parse their own command-line arguments via `@deepseek-ai/dsh-cmdline`. Tutorial chapters are each runnable keyless examples aimed at 'agent developers' without deep TypeScript expertise.

## Design principles
- Everything is a plugin: every capability — tools, LLM adapters, file access, the agent loop itself — is a plugin mounted into a shared Context; the kernel (Cordis) is deliberately small and functionality is decentralized, never monolithic.
- All registrations are effects: anything registered through ctx is automatically undone when the owning plugin unloads; this single invariant is what makes hot reload, config-edit reload, and provider swapping safe (no state retained across instances).
- Dependency-driven, not order-driven, loading: cordis.yml entries start concurrently and list position guarantees nothing; only declared service dependencies (inject) determine when a plugin runs, and a plugin waits (PENDING) rather than failing when a dependency is absent.
- Dependencies are monitored continuously, not checked once at boot: when a required service disappears, dependents dispose automatically and reload when it returns — availability is structural, so plugins can never call an unavailable service at runtime.
- Plugins define contributions; configuration files compose applications — no bootstrap code lives in plugin files; assembly is declarative and external (cordis.yml, bundles, profiles, patch layers).
- Three-role capability layering for replaceable capabilities: Service Definition (owns Request/Result types) / Service Provider (implementation) / Consumer (model-facing tool); provider and consumer depend only on the definition, and providers swap via configuration alone. The complete capability is the seam; individual roles are not.
- Do not split preemptively — separate packages only when the roles need to evolve independently.
- Explicit > implicit: resolve defaults in an explicit resolve(request): Spec step; unsupported LLM options must throw a typed error rather than be silently dropped; a waterfall listener that only observes must explicitly call next().
- Separation of canonical value from presentation: a tool's execute returns the canonical value declared by output.schema, and output.render converts it to model-facing content — tool logic and model-facing serialization are distinct layers.
- Fail at load time, not runtime: config is schema-validated (Standard Schema / Schemastery) with defaults applied before apply() runs; a plugin never starts with incomplete or invalid configuration, and apply() throwing is loudly fatal.
- Configurability mandate: anything two deployments may want to set differently must be a configuration field; validation rules live entirely in the schema (self-contained), while service dependencies use injection instead.
- Coupling only through registries and typed events: plugins never know each other exist — the registry service and namespace/action events connect them; the waterfall event mode is the sanctioned interception/policy seam (agent/request, approval/request).
- Two concepts, two manifests: a bundle is what you author and distribute, a profile is what a user boots — nothing is both; effective config is layered with later layers winning per row and whole-row replacement (never deep merge).
- Flat namespaces with naming discipline: one flat service namespace per application (prefix your own; harness reserves tools/llm) and namespace/action event names; isolation when needed is explicit via isolate blocks giving groups independent service instances with no cross-group effect.
- Durable records are distinct from live events: session history (turn/*, step/*, tool/call, compaction/*) is a persisted log observed through a single session/event bus listener, not a set of same-named in-process events.
- The framework itself obeys its own rules: HMR is a plugin with its own inject dependencies (logger, timer) and sits PENDING without them; even infrastructure gets no special-case lifecycle.

### [development.md] Host/Client two-aggregate TypeScript architecture
The repo compiles as two isolated aggregate programs (tsconfig.host.json, tsconfig.client.json) because BOTH sides declaration-merge the Cordis Context interface under the same keys with different services — one ts.Program seeing both merges reports a collision. The collision exists only inside a ts.Program (module resolution never triggers it), so the solution root may reference both aggregates and one paths facade (tsconfig.base.json, no include so its paths apply to every importer) may span both sides. Three disciplines follow: (1) tsconfig.base.json never gains include/files; (2) any script building a repo-wide ts.Program seeds a face config, never the root solution; (3) every new package registers in exactly one aggregate — having both a Node loader entry and a browser entry is NOT a reason to split a package.

Explicit instruction: 'Do not copy this structure to other packages.'

### [development.md] Build pipeline and DSH_BUILD_FACE
Root build order: tsc -b host → tsdown (host face) → tsc -b client → tsdown (client face) → build:web. Both tsdown passes use the same complete workspace match — no artifact scanning, no Host/Client filter list; package-local tsdown configs select entries per phase via the DSH_BUILD_FACE env var (api-remotes uses hostPhase: true). Tsdown consumes only the JavaScript tsc emitted to lib/types. Typert (the type-graph generator) runs only during Host tsdown, seeded by tsconfig.host.json, generating Host reflection artifacts and the Host-for-Client Remote projection; Client tsdown never starts Typert — hence typecheck runs the complete Host lib phase before the Client TS check.

### [development.md] @Remote/@RemoteScope RPC generation
Business services declare callable methods on the Host with @Remote or @RemoteScope decorators; the Host build generates Host-for-Client types and runtime contributions, and the Client's api-remotes composition loads those contributions under ctx.remote and scoped agentCtx.remote namespaces. The client/server API surface is generated from Host types (via Typert reflection), not hand-maintained — docs/api-gateway.md covers artifacts, assembly, the SRC development fallback, and Web build order.

### [development.md] Source plane vs artifact plane
Static analysis and tests resolve workspace imports through the base paths map to src and must pass on a clean tree; gates that consume built lib/ output declare that dependency explicitly. The generated Host-for-Client Remote declarations are the one deliberate exception (public typecheck/lint/doc-typecheck generate them first; internal *:contracts-ready scripts assume a prior gate produced them). Reproducibility: pnpm run build embeds the caller's exact DSH_CLIENT_* environment; each successful complete build writes a gitignored record binding those values to the Vite output and dynamic client bundles, and release packing plus built-Web tests REJECT a missing record or artifacts changed by a later partial build.

### [development.md] Git hooks as thin checkpoints, i18n merge driver
Lefthook hooks are deliberately minimal: pre-commit verifies staged translation-pairing records, lints staged files with a project-free Oxlint profile (fixes with one bounded retry), regenerates THIRD_PARTY_NOTICES.md when inputs are staged, checks whitespace, and runs the vendor manifest guard (changes under vendor/*/src must be staged with the matching vendor/README.md manifest update); pre-push runs only typecheck. 'Apart from the scoped staged-record verification, the hooks intentionally do not run tests, snapshots, documentation checks, builds, or hygiene.' A custom dsh-translation-pairing Git merge driver auto-derives conflicted .i18n.yaml records for the bilingual doc pairs and FAILS CLOSED on owner conflicts, non-text merge configuration, or invalid records, with a Node-independent fallback launcher and a documented recovery path. pnpm run check:all exists but 'is not an agent instruction'.

### [development.md] Self-referential demos
Three source-checkout demos: pnpm dsh --profile headless "task" (one-shot headless coding agent); pnpm run demo:cordis — 'the self-referential cordis demo can inspect and modify its live plugin runtime' (the agent operating on its own harness); pnpm run demo:acp — ACP automation server exposing fresh agent sessions over JSON-RPC stdio. All need DEEPSEEK_API_KEY from env or gitignored root .env; a set ANTHROPIC-style credential is never committed and e2e suites self-skip without the key.

### [development.md] Documented types stay source-equivalent (type-equiv gate)
Subsystem docs paste source-equivalent type declarations with their original JSDoc; blocks are fenced ```ts type-equiv and registered in scripts/type-equiv.manifest.json with {doc, symbol, source}. pnpm run verify-type-equiv extracts the symbol's declaration+JSDoc from source via the TypeScript parser and asserts the doc block matches both (whitespace-insensitive but every original JSDoc comment required). A public-api projection variant checks classes with bodies and private members omitted. The gate enforces 1:1 correspondence by document/symbol/projection, with a byte-identity rule letting paired .zh.md translations reuse the sibling's manifest entry. Changing a documented declaration fails the gate until the paste is updated — docs cannot drift from source.

### [development.md] Documentation workflow rules
Docs are gated work: pnpm run doc-sync runs all documentation gates; documentation changes use doc-sync, package-public behavior changes also update the owning README or JSDoc. TODO markers are a three-level urgency taxonomy: FIXME (release blocker — a release should not ship with an open FIXME unless reviewers explicitly agree), TODO (fix soon), XXX (someday-maybe, no commitment).

### [development.md] CI organization
The keyless CI workflow groups independent gates into broad lanes and runs a smaller compatibility signal across Node 22.19/24/26; artifact consumers wait for one build within their lane. A separate real-API workflow runs test:e2e with a configured worker bound. scripts/run-gates.ts owns the current gate inventory (single source of truth for what gates exist). pnpm run hygiene = knip + publint + workspace constraints + NodeNext consumer check; pnpm run duplication = cross-file TypeScript clone detection.

### [both] Division of authority between the two files
AGENTS.md is the normative rulebook (conventions, invariants, policies) with every rule linking its owning deep doc or Agent Note; development.md is the contributor tutorial + reference (setup, TS layout, daily workflow, CI) that likewise pushes 'design rationale and implementation details' out to linked Agent Notes and scripts. Facts have exactly one home ('one home per fact' per docs/AGENTS.md), and gates enforce the docs rather than prose exhortation — a documentation architecture worth noting for a design charter.

## Design principles
- Everything is a plugin: model adapter, tool registry, session log, and the agent loop itself are Cordis plugins, replaceable from configuration (cordis.yml); the kernel (@deepseek-ai/cordis) is a peerDependency of every package, vendored and pinned.
- Plugins, not loop changes: new behavior lands on documented extension points; editing agent-loop is exceptional and requires updating docs/architecture.md in the same change.
- Registrations are effects: every contribution goes through ctx.effect()/ctx.on() and returns a disposer — all composition is reversible by construction, which is what makes live self-modification safe.
- Model-visible ⟺ logged: anything that reaches a model request must be reconstructable from the session log; adding a model-visible input obligates adding a session event. The session log is the reconstruction authority (plan mode is 'logged state'; unknown non-ignorable events make a build refuse the log).
- A capability seam is three roles — Service Definition / Service Provider / Consumer — and is complete or it isn't a seam; roles split into separate packages only when they evolve independently. Subagents/delegation, LLMs, shell, web, etc. are all instances of this one pattern.
- Agent definitions are declarative, layered data: per-session composition from preset cordis.yml files, profiles as installable patch-layer bundles, conditional composition via overlays (executable YAML tags confined to plugin config and disabled fields only).
- Self-modification is an ordinary capability, not a privileged mode: the agent inspects and mounts its own plugins through the same plugin system (packages/self-modification; demo:cordis modifies its live runtime).
- Foundation over blast radius (pre-release): no compatibility shims, free renames with every reference updated together, backends reject old on-disk formats, version numbers monotonic with no promises — and the policy itself is scheduled for deletion at the first tagged release.
- Explicit > implicit at package boundaries: defaulting is an explicit resolve(request): Spec step in the owning implementation, never a hidden ?? default inside run().
- Configurability is a validated Config field changeable from cordis.yml — a DEFAULT_* constant or test hook is not configurability — while protocol constants, external specs, and security invariants stay fixed.
- Misconfiguration fails loud at load, or at the earliest resolvable point; never silently skip a missing referent.
- Trust the type system inside a typed same-process boundary; validate only at real boundaries, which are enumerated: parser/config, queued, model/tool JSON, durable/file, worker, process, wire. Opaque cross-boundary ids are branded types, never bare strings.
- Source plane vs artifact plane, never mixed: static gates and tests resolve to src via tsconfig paths and pass on a clean tree; anything consuming built lib/ declares that dependency explicitly.
- Isolation by compiler face: Host and Client are two aggregate ts.Programs because both declaration-merge the Cordis Context under the same keys — a structural collision is prevented by program topology, not by naming discipline.
- Docs are gated artifacts, not prose: type pastes are parser-verified against source (type-equiv), JSDoc presence is gated (verify-export-jsdoc), word budgets are gated (verify-doc-budgets), doc-sync is a first-class check, and every non-trivial change ships an Agent Note in the same PR; archived notes are frozen history, never current authority.
- Tests describe behavior, not correctness; the canonical evidence for model- or user-visible change is a keyless snapshot through a real runnable assembled example — mocks and package tests do not substitute for the application transcript; fix fixtures, not normalizers.
- Both SDKs project the loop: any change to agent-loop, session lifecycle, or the event map updates the TypeScript and Python SDK expected outputs atomically in the same PR.
- CI owns exhaustive coverage and the platform matrix; local checks are the smallest set matching the changed surface, run once — never default to the full suite.
- A tool's UI render intent is part of its design, decided up front; presentation methods are pure functions of the tool's args.
- Waterfall (middleware) listeners must call next() to delegate; returning without it deliberately short-circuits the chain — chain semantics are explicit, not accidental.
- Runtime invariants assert owned relationships against authoritative event streams or mutable data — never presence checks or fixed examples; an explained empty invariant is preferred over a vacuous one.
- Prefer symmetry for parallel values; unexplained asymmetry usually signals a missed extraction.
- Prefer maintained dependencies over hand-rolling when they genuinely delete owned code and tests; vendor by pinned source copy with a SHA manifest and logged local modifications.
- Prose discipline: comments and docs state complete contracts, not reasoning transcripts; no metaphors; exact terms over vague ones ('contract'/'boundary'/'shape' reserved for their literal meanings); mechanically checkable invariants get wired into an executed gate with a proven rejection path.
- One instruction source for all coding agents: CLAUDE.md symlinks AGENTS.md; the repo's own contributing agents get skills and notes under .agents/, and rules are self-contained but link their owning deep doc — one home per fact.

# guide-pages
Source: DeepSeek Harness (dsh) docs — providers guide + python-sdk guide (deepseek-harness.github.io) + Safe Use Policy (deepseek.com/harness/en/privacy/)

## Key points
### providers: provider abstraction
Providers are the abstraction layer for LLM endpoints. Two classes exist: catalog providers (pre-installed/pre-configured — Anthropic, OpenAI, Bedrock, Vertex, Azure, Codex) and custom providers (self-hosted or gateway). Catalog providers resolve from their installed catalog with no network request; custom providers fetch model candidates from an OpenAI-compatible GET /models endpoint on the base URL, or models are entered by hand.

### providers: immutable provider ID
Provider ID is lowercase and permanent/immutable once created, because requests, saved sessions, model defaults, and credential references all key on it — this is a reproducibility invariant for historical sessions. Renaming a provider is not supported: you add a new provider and delete the old one. Display name, base URL, protocol, credential, and model list remain editable post-creation.

### providers: hot reconfiguration
Model changes take effect on the next request without restarting the server — provider/model configuration is hot-reloaded, not boot-time. Default model selection persists per session but can be overridden; a deleted provider's defaults block input rather than silently falling back.

### providers: credential isolation
Credentials are write-only from the UI's perspective: after saving, the page receives a redacted descriptor, never the literal secret. Secrets live in $DSH_HOME/.credentials.yaml while settings.yaml retains only credential references (settings/secrets split). Environment-variable indirection is supported via apiKeyEnv fields. Some catalog providers use non-API-key auth: AWS credentials + region, ADC project, api-version, or OAuth.

### providers: input-modality declaration model
Modalities are declared via input: [text, image] at model or route level in settings.yaml; route-level defaultInput is the fallback, model-level input overrides per model; catalog providers narrow modality via modelOverrides keyed by model ID. Omitting the field (or writing an empty list, which means the same) keeps whatever the installed catalog records. A hand-entered model is treated as text-only until it declares otherwise (conservative default). Image attachments to a model declaring no image support are refused client-side before transmission, naming the model; a model that over-declares images its endpoint does not serve is not caught client-side — the provider rejects the request instead (validation is layered: local checks enforce declared capability, the endpoint stays the authority on actual capability).

### providers: request compatibility profile (compat)
The pi-ai adapter decides the request shape from the endpoint's URL, and an unrecognized address is addressed as though it were OpenAI itself — but most OpenAI-compatible gateways refuse at least one OpenAI-accepted request shape. The compat section holds explicit per-endpoint switches: supportsDeveloperRole (whether the system prompt is sent as role "developer" — reasoning models default to developer role, which gateways often reject), maxTokensField (max_tokens vs max_completion_tokens), thinkingFormat (reasoning-model format). Route-level compat sets defaults; model-level compat overrides field-by-field. Switches are claims about the endpoint, not behavior toggles: setting one your gateway does not actually need simply sends a different request. A named switch left empty is refused rather than ignored (no silent nulls). The chosen API protocol determines which compat switches are accepted; invalid switches are rejected with the available options listed.

### providers: plugin-shaped LLM layer
Even the LLM/provider layer is a plugin: the dsh-llm-pi-ai plugin owns the provider section this guide configures, and dsh-llm-deepseek is a sibling plugin; their generated configuration references cover direct settings, catalog resolution, reasoning controls, credentials, and adapter errors. Fallback chain for unspecified switches/modalities: explicit config → installed catalog → protocol defaults.

### python-sdk: embeddability
The harness is explicitly scriptable/embeddable: the Python SDK tutorial is stated to be "the programmatic alternative to the Web UI". The core class DeepSeekHarness is a context manager (enter/exit) constructed with provider, model, max_tokens, cwd, session_root, and cordis (a YAML composition file); run(task_description, session_id) returns a result object with final_response. The bundled runtime starts lazily and is reused until the context manager exits — the installed runtime needs no system Node.js (self-contained distribution), and reusing the harness instance preserves the runtime across multiple run() calls.

### python-sdk: session semantics
Sessions are identified by caller-supplied session_id. Reusing the same harness and session id preserves the session-owned Bash process, including its working directory, exported variables, and shell functions — session = durable conversation plus durable shell state. Fresh session IDs create independent tasks. Session state persists as uncompressed JSONL under DSH_SESSION_ROOT (transparent, inspectable persistence). The stated rule (emphasized twice on the page): use a fresh session id for an independent task; reuse an id only when the next call should continue the same conversation and persistent shell state.

### python-sdk: minimal model-facing tool surface
The model-facing tool stack in the minimal composition is exactly two tools: a persistent bash (PTY-backed, POSIX only — Windows unsupported; 300s timeout) and str_replace_editor (output capped at 16,000 characters). Filesystem is a bare local backend; absolute editor paths may address any path visible to the runtime process. Everything else — harness identity, workspace prompt text, skills, one-shot Bash, task tools, context compaction, "every other model-facing plugin" — is an omittable plugin, confirming everything-is-a-plugin down to individual prompt fragments and tools.

### python-sdk: Cordis composition
The agent's composition is specified declaratively via a Cordis YAML file passed as the cordis constructor parameter (example: examples/jsonrpc-agent/minimal.cordis.yml); the Cordis primer covers composition syntax. Configuration/composition — not a code-level plugin interface — is the primary extension point exposed at the SDK level. Sandbox-policy facts are logged as runtime user context rather than appended to the system prompt (policy metadata kept out of the prompt channel). The example composition uses danger-full-access and the docs instruct running it only inside a disposable checkout or container. Env config: DEEPSEEK_API_KEY, DEEPSEEK_BASE_URL (OpenAI-compatible proxies), DSH_MODEL (default deepseek-v4-flash), DSH_SYSTEM_PROMPT (default "You are a helpful software engineer assistant"). Event/streaming model is not documented on this page — the GitHub Python SDK reference covers lifecycle, results, notifications, runtime selection, and configuration.

### safe-use-policy: capability acknowledgment
The policy openly acknowledges the harness "has the ability to run code and execute actions on your machine", can access various systems and perform operations locally, and that "the Agent may execute commands embedded in content, even if those conflicts with the assigned task" — an explicit prompt-injection admission: foundation-model safeguards are acknowledged as insufficient on their own.

### safe-use-policy: operator-side safety posture
The declared posture is recommendations to the operator rather than mandated in-harness enforcement: use dedicated VMs or containers with limited privileges (isolation recommended, not built in); always carefully review agent-generated code and test content; avoid providing sensitive/confidential information; always require human approval for any system or operation that could result in significant changes; break complex instructions into smaller isolated operations; only install and run plugins, MCP servers, Skills, Hooks, and their dependencies from trusted sources (the plugin surface is explicitly the trust boundary). Notably, no data-handling or telemetry commitments are stated anywhere on the page.

### safe-use-policy: prohibited uses and reporting
Section 2 bans, each qualified "in any manner": military purposes; cyberattacks or chemical/biological attacks; harmful manipulation of individuals or groups; exploiting or harming others; generating/disseminating verified-false information or content intended to harm; inappropriate content violating regulatory requirements; PII without authorization; defaming/disparaging/harassing; and any use violating national or international law. Both security vulnerabilities and policy violations report to harness-privacy@deepseek.com. The page links to the Cordis paper repo and to community plugins under the dsh-plugin GitHub topic.

### cross-source: plugin ecosystem surface
Across the three pages the plugin taxonomy that emerges: LLM adapters (dsh-llm-pi-ai, dsh-llm-deepseek), model-facing tool/prompt plugins (skills, task tools, one-shot bash, compaction, identity, workspace prompt text), plus externally-sourced plugins/MCP servers/Skills/Hooks named in the Safe Use Policy as the trust-sensitive install surface; community plugins are discoverable via the dsh-plugin GitHub topic. Composition of all of these is Cordis YAML.

## Design principles
- Everything is a plugin, all the way down: the LLM/provider layer itself (dsh-llm-pi-ai, dsh-llm-deepseek), each model-facing tool, context compaction, skills, and even the harness identity and workspace prompt text are individually omittable plugins composed via a Cordis YAML file — the minimal agent is just persistent bash + editor.
- Composition over code extension: at the SDK level the extension point is the declarative Cordis composition file, not a programmatic plugin API; the Python SDK is a thin embedding shell (context manager + run()).
- Identity immutability for reproducibility: provider IDs are permanent because sessions, requests, defaults, and credential references key on them; rename = create new + delete old.
- Hot reconfiguration: model/provider changes take effect on the next request, never requiring a server restart.
- Secrets never round-trip: credentials are write-only, stored separately ($DSH_HOME/.credentials.yaml) from settings, which hold only references; the UI only ever sees a redacted descriptor.
- Explicit claims over silent guessing: compat switches and input modalities are declarations about the endpoint; a named-but-empty switch is refused rather than ignored, invalid switches are rejected with options listed, and hand-entered models default conservatively to text-only until declared otherwise.
- Layered fallback for the unspecified: explicit config → installed catalog → protocol defaults; omitting a field defers rather than zeroing.
- Validation lives where authority lives: the client refuses only what the declaration provably forbids (image to a text-only model); the endpoint remains the authority on actual capability (over-declaration fails at the provider).
- Session = durable conversation + durable shell state, keyed by caller-owned session_id; fresh id per independent task is the stated contract, and session state is transparent uncompressed JSONL on disk.
- Lazy, reusable, self-contained runtime: bundled runtime starts lazily, is reused across run() calls per harness instance, and needs no system Node.js.
- Policy metadata stays out of the prompt: sandbox-policy facts are logged as runtime user context rather than appended to the system prompt.
- Safety is delegated to the operator, and honestly so: the harness admits it can execute injected commands that conflict with the assigned task, and mandates nothing in-process — it prescribes VM/container isolation, human approval for significant changes, decomposed instructions, and trusted-source-only plugins/MCP/Skills/Hooks; the plugin install surface is explicitly named as the trust boundary.
