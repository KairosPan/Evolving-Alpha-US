# Runbook: the dsh 0.2.0-rc.2 go-live of kairos-face

**Owner:** the operator. This document is the operator's: every step below acts on the
operator's harness home `~/.dsh`, or on a copy of it, by hand. The face code never touches HOME
on its own; the one tool that reads a home it was not started on, `face/scripts/check-home.ts`,
refuses the live home and works on a copy.
**Pins:** the face re-hosted on dsh `0.2.0-rc.2` (cordis `4.0.4`, cordis-plugin-include `1.0.9`)
by `3bbaa25` (S0, the dependency bump) and `8f0dedb` (S1-S8), branch `worktree-dsh-0.2.0-rc.2`.
The home today is a 0.1.1-rc.2 home: every session log is format V0.
**Decision ids** are the upgrade plan's operator decisions (D1-D16, plus D17 and D18 from its
critique); §4 restates each one that needs an answer before go-live, and lists the ones the code
already defaulted.

The first 0.2.0 boot on a home writes state that 0.1.1 cannot fully read back, and 14 of the 39
sessions in this home cannot be read by 0.2.0 at all (measured on a copy, §3). There is no
per-session undo; the undo is a full restore from the backup of §2 (§6). Take the steps in order.

   `~/.local/bin/dsh`) in TUI, `dsh web` (port 3080) or headless mode. Check:

   Counts as of 2026-09-30. `check:fixture` runs `scripts/validate-fixture.mjs`: the client's

## §2 Backup

```bash
cp -a ~/.dsh ~/.dsh.bak-pre-0.2.0-$(date +%Y%m%d)
diff -rq -x node_modules ~/.dsh ~/.dsh.bak-pre-0.2.0-YYYYMMDD    # expect no output
ls -l ~/.dsh.bak-pre-0.2.0-YYYYMMDD/.credentials.yaml            # expect -rw-------
```

- `cp -a` keeps modes (`.credentials.yaml` stays `0600`), times, and symlinks as symlinks.
- `-x node_modules` leaves out `profiles/node_modules`, the 0.1.1 link farm (433 symlinks into
  package trees, D13): `diff` would walk every linked package. The backup still holds the links.
- 0.2.0 keeps its own state nowhere else: outside `~/.dsh` it writes only `tmpdir()` scratch (and
  the agent writes its work in the repository, which is the repository's). dsh-base's path-bearing
  rows are `sessions` and `storages` under the home, plus the sandbox root `process.cwd()`.
- **The backup is stale the moment anything 0.1.1 runs on `~/.dsh` again** - the old face is the
  daily product, and the drills of §7 can take days. §7 C.1 re-takes it (or diffs it) immediately
  before the first live boot, with every old process stopped at that moment.

## §3 Dry run on a copy

```bash
SCRATCH=$(mktemp -d)
cp -a ~/.dsh "$SCRATCH/dsh-dryrun"
touch "$SCRATCH/dsh-dryrun/DRY-RUN-COPY"
cd <the 0.2.0 checkout>/face
npx tsx scripts/check-home.ts "$SCRATCH/dsh-dryrun"
# read the summary, then "$SCRATCH/dsh-dryrun.check-home.json"
rm -rf "$SCRATCH/dsh-dryrun"        # the report beside it stays
```

Run it with `DSH_HOME` unset (or pointing at the live home). `DRY-RUN-COPY` is created in the
copy and nowhere else.

**What the tool does** (`face/scripts/check-home.ts`, header and `runCheckHome`):

1. **Refuses, exit 2, before it loads any dsh plugin or writes anything**, when the argument is
   missing, does not exist, is the live harness home (`$DSH_HOME` as dsh resolves it, and
   `~/.dsh`), lies inside it or contains it, carries no `DRY-RUN-COPY` file, or has no
   `profiles/face/package.json`. The live-home test compares device and inode, not path strings:
   `realpath` keeps the caller's letter case on a case-insensitive APFS volume, so `~/.DSH` would
   pass a string comparison (measured; `tests/check-home.test.ts` pins it). A `DSH_HOME` pointing
   at the copy makes the copy "the live home", and the tool refuses it.
2. Reads, without booting: an inventory of every file in the copy (path, size, mtime, inode,
   SHA-256; symlinks recorded, never followed), each session directory's raw log (the highest
   canonical generation, every Zstandard frame decoded - `node:zlib` alone decodes only the first),
   the link farm, and `settings.yaml`'s `agent-default-model` section.
3. Boots the face's own composition on the copy - `bootFace`, as `main.ts` boots the live home -
   with three differences: the copy is the home, `DSH_TELEMETRY_DISABLED=1`, and every MCP client
   row (the operator's `mcp-alpaca-kit`, the face's `mcp-akshare`, any other) is disabled by an
   in-memory patch layer, `FaceBootOptions.extraPatches` in `face/src/boot.ts`. No patch file of
   the copy is written, no MCP server is spawned, no key leaves the machine.
4. Lists `sessionPersistence.list()` and opens every session read-only: `open(id, "read")`,
   `read()`, `close()` - the in-memory V0..V4 migration the host runs before it can page or follow a
   session. It records `{id, cwd, agentPreset, eventCount}` or the refusal's `{name, message}` and
   its class (`classifyRefusal`), and each session whose header preset is not in the roster.
5. Disposes the tree, writes `<copy>.check-home.json` (mode `0600`, no credential values) beside
   the copy, prints a summary, and ends with the reminder to delete the copy.

Exit codes: `0` the scan completed - a refused session is a finding, not a failure; `1` the boot or
the scan did not complete (the live boot composes the same patch files and would hit the same
failure); `2` refused to run.

**Expected on this home.** From the 2026-09-30 read-only probe of a copy (the same installed
persistence, the same read-open), and the home inventory of the same day:

| Finding | Expected |

**Stop conditions** - do not go live until each is explained and signed off:

- exit `1` (the boot failed);
- any refusal in the class `OTHER`, or any refused session not in the table above;
- any change under `sessions/` in the scan window ("Scan window: ... UNEXPECTED");
- a warning `MCP row ... is ENABLED in the dry-run tree`.

**Delete the copy** right after reading: it holds `.credentials.yaml` (`DEEPSEEK_API_KEY`, and the
browser-session signing secret the dry run's boot wrote into it) and every session log. Keep the
report until sign-off - somewhere durable if that takes days, since macOS purges `mktemp`'s
directory.

After §4's D2 edit, a second dry run on a fresh copy confirms the row: the summary then reads
`the face would run deepseek-official/deepseek-v4-pro, effort max` (verified on the fixture home,
Appendix A).

## §4 Decisions to make first

### D2 - the default model (required)

The 0.2.0 face does not read `settings.yaml` (no `profileContext`, D1), so without a profile row it
runs dsh-base's `deepseek-official/deepseek-flash`. Add this row to
`~/.dsh/profiles/face/cordis.patch.yml`, by hand - as a new list item at column 0 after the
existing rows (or in place of a bare `[]`):

```yaml
- id: agent-default-model
  config: { provider: deepseek-official, model: deepseek-v4-pro, reasoningEffort: max }
```

- A patch that names `config` replaces the row's whole config; `provider` and `model` are
  required (`@deepseek-ai/dsh-agent-default-model`, `AgentDefaultModelConfig.Config`).
  `deepseek-v4-pro` and `reasoningEffort: max` are valid at 0.2.0; `deepseek-v4-flash` is gone
  (now `deepseek-flash`).
- This row is the only way to set the face's default. The model picker (`session/selectModel`)
  switches the session's model and then saves the default in the background through
  `agentDefaultModel.saveSelection`, which writes nothing without a config editor - and the face
  mounts none (D1).
- The file's comment header is still 0.1.1's prose; `face/src/setup.ts` `PATCH_HEADER` is the
  current text, to copy over optionally.
- The 0.1.1 schema accepts the row (checked against the installed 0.1.1-rc.2
  `@deepseek-ai/dsh-agent-default-model`, whose schema has no `reasoningEffort` key and keeps it
  unvalidated), so the edit can be made while the old face still runs.

### D11 and D17 - the 14 sessions 0.2.0 cannot read

10 room sessions (D11), 3 subagent children with a version-2 descriptor and 1 log with a seq gap
(D17). Under 0.2.0 their files stay on disk byte-identical: migration never moves, replaces or
deletes a committed generation, and a refused read publishes nothing. The face tolerates them - a
legacy room member session surfaces as a failed turn, a refused read is reported once and not
retried - but it cannot show them. Options, per class:

- **Leave them.** The raw V0 logs stay readable outside dsh:
  `zstd -dc ~/.dsh/<items[].raw.dir>/<items[].raw.log>`, with the report's paths (relative to the
  home; the refusal message's `raw log:` names the same file in the deleted copy). The backup holds
  them too.
- **Export first.** Before go-live, while the primary checkout is still 0.1.1 and the old face
  still runs on the old home, open each one in the 0.1.1 face and save what is worth keeping. The
  0.1.1 face is the only renderer that may still show them; whether it reads the seq-gap log is
  unverified. This has to happen before §2's backup is retaken for the last time and before the
  primary checkout is upgraded.
- **Wait** for an upstream migration edge that admits them.

### D12 - the global CLI and the old face

Both are 0.1.1 and both boot on `~/.dsh`. Pick one before go-live:

- **Upgrade the CLI**: `npm i -g @deepseek-ai/dsh@0.2.0-rc.2`. Its first run of any profile
  imports `settings.yaml` into that profile's `cordis.patch.yml` and renames the file
  `settings.yaml.imported`. The face never reads either (D1); the D2 row stands on its own.
- **Isolate it**: give 0.1.1 tools their own home (`DSH_HOME=~/.dsh-cli-0.1.1 dsh ...`).
- **Stop using it** on this home.

Whatever the choice, 0.1.1 never runs again on a home 0.2.0 has written: its reader sees only
`session.jsonl.zstd`, so a resume appends to V0 while 0.2.0 reads V4 (a silent fork); it takes
no `session.lock`; and every workspace write it makes drops the sessions it cannot see from
`storages/workspace.json` (§6).

### D13 - the link farm

`~/.dsh/profiles/node_modules` is 433 symlinks the 0.1.1 face and CLI re-heal on every boot.
0.2.0 resolves through its runtime resolution and never writes the farm, but a row naming a
package outside the face's dependency closure would still resolve through a stale link into
0.1.1 code. After D12:

```bash
rm -rf ~/.dsh/profiles/node_modules     # symlinks only: removes the links, never their targets
```

### D18 - the tool-result spill budget

dsh-base moved `spill-policy` from `maxInlineBytes: 50000` to `maxInlineTokens: 12500`, tokens
estimated as UTF-16 length / 4. ASCII results keep about 50 KB inline, as before; CJK-heavy
results (AKShare) now stay inline up to about 50,000 characters - about 150 KB of UTF-8, 3x the old
byte budget - which grows context and cost. The default follows upstream. To restore roughly the
old CJK budget, one row (its only key; the row replaces the whole config):

```yaml
- id: spill-policy
  config: { maxInlineTokens: 4200 }     # about 16,800 characters: ~50 KB of CJK, ~17 KB of ASCII
```

## §5 What the first 0.2.0 boot writes, and what it does not

| Path in `~/.dsh` | What happens | When |
|---|---|---|
| `.credentials.yaml` | gains `records: client-connection/browser-session` (a grant holding the cookie-signing secret); `refs` untouched, mode stays `0600`. The 0.1.1 parser accepts a `records:` section. | first boot (Connection activation, `BrowserAuth.create` in `@deepseek-ai/dsh-client-connection`) |
| `storages/session_projcache/sessions/<id>.json` | a per-record tree, bootstrapped from the v3 single file `storages/session_projcache.json`, which stays in place | first boot |
| `storages/workspace.json` | may gain `pinnedSessionIds` / `defaultWorkspaceId` (the v2 spec's defaults); the fixture boot left it untouched, and the dry run says whether this home's changes | first boot, or the first workspace write |
| `profiles/face/cordis.yml` | rewritten, as on every face boot; its comment text changed, so the first boot shows it modified | every boot |
| `settings.yaml` | untouched (no `profileContext`, D1) | never |
| a session's `session.v4.jsonl.zstd` + `session.lock` | published BESIDE the V0 `session.jsonl.zstd`, which stays byte-identical; never rolled back | the session's first WRITE-open: a prompt, a command, a rename (it resumes the source), an `@` or a room dispatch to it — never a view, and not a fork (a fork reads the source cold and writes only the new session) |

Not on a read. Listing and read-opens publish nothing (§3's scan window). And not on a mere open in
the chat: the client opens a cold session page-only (`session/projections` + `session/page`, D16,
`activeView` in `face/client/chat.js`), because a follow would promote it and a resume write-opens
the log. A paged session becomes a follow only when this tab writes to it, or when the host reports
it live.

On the fixture home of Appendix A the dry run's own boot wrote exactly the first two rows plus
`profiles/face/cordis.yml`, and nothing under `sessions/` or in `workspace.json` or
`settings.yaml`.

## §6 Rollback: a full restore, never one session

```bash
# stop the 0.2.0 face first
mv ~/.dsh ~/.dsh.failed-0.2.0 && cp -a ~/.dsh.bak-pre-0.2.0-YYYYMMDD ~/.dsh
diff -rq -x node_modules ~/.dsh.bak-pre-0.2.0-YYYYMMDD ~/.dsh    # expect no output
```

- Then run the 0.1.1 face only from a 0.1.1 checkout with its own `node_modules` (the commit before
  the merge, `npm ci`): the 0.2.0 code on a restored home is a new go-live, not a rollback.
- `~/.dsh.failed-0.2.0` holds everything done under 0.2.0; a session created there exists only as
  `session.v4.jsonl.zstd`, which 0.1.1 cannot read.

Why deleting one session's `session.v4.jsonl.zstd` and `session.lock` is not a rollback:

1. Every turn taken under 0.2.0 lives only in the V4 file; 0.1.1 reads only `session.jsonl.zstd`.
2. A session created under 0.2.0 has no V0 file, and every 0.1.1 workspace write (attach, rename,
   reorder, detach) filters each workspace's `sessionIds` through the sessions it can see and
   persists the result (0.1.1 `packages/workspace/workspace/src/entity.ts`, `mutate`): each
   0.2.0-born session is detached from its channel in `storages/workspace.json`, permanently.
3. 0.1.1 takes no `session.lock`, so nothing stops it appending to a V0 file 0.2.0 no longer reads.

A fixture home built to look like this one, under the session scratchpad (never `~/.dsh`):
`setup.ts`'s profile plus an operator `mcp-alpaca-kit` insert; `settings.yaml` with the

`npx tsx scripts/check-home.ts <copy>` then printed (paths shortened):

